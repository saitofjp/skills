# レビュー結果：予約システム 仕様書 v0.9 / 設計書 v0.3

仕様を状態遷移表・権限マトリクス・ドメインルール・障害表に書き起こして確認しました。書けなかったセルは「抜け」、書けたが成り立たなかったものは「矛盾」か「リスク」として挙げています。特に重いのは 1〜4 で、どれも二重予約か、払ったのに枠がない状態につながります。

---

## 指摘（影響の大きい順）

### 1. 矛盾/リスク：支払い中に30分が過ぎたらどうなるか
- **場所**：仕様 §3.3「30分以内に支払いが完了しなければ失効し、枠は空く」、§5「決済処理中となり、完了の通知が届いた時点で支払い済み」、設計 §2 status enum、§4.2、§4.5
- **モデル**：状態表の (決済処理中, 30分経過) が空欄です。設計の enum には決済処理中がありません。そのため §4.2 のバッチは、カード入力の済んだ予約も `tentative` として `cancelled` にします。一方 §4.5 は、Webhook が来れば予約の状態を見ずに `paid` にします。
- **起きること**：29分目にカードを入力し、通知が31分目に届いたとします。この間に枠は空き、別の利用者が `tentative` で押さえられます。そこへ通知が来て元の予約も `paid` になるので、同じ枠に `paid` と `tentative` が並び、§2 の一意ルールが崩れます。逆に、決済処理中を失効させたまま通知を捨てると、課金したのに予約がない状態になります。
- **問い**：決済処理中は30分タイマーの対象外ですか？　失効した予約や取り消した予約に完了通知が届いたら、自動で返金しますか、それとも枠を復活させますか？　決済処理中は §3.2 の状態一覧に入れますか？

### 2. リスク：Webhook を誰が送ったか確かめていない
- **場所**：設計 §3「POST /webhooks/payment　呼べる人：決済サービス」、§4.5
- **モデル**：信頼境界をまたぐ経路のうち、ここだけ制御が書かれていません。署名の検証、対象予約の特定方法、金額との突き合わせのどれもありません。
- **起きること**：URL を知っている人なら誰でも、払わずに予約を `paid` にできます。通知が二重に届いた場合の扱いも決まっていません。
- **問い**：署名検証、冪等キー、金額と予約IDの照合は、設計に必須として書きますか？

### 3. リスク：受付開始の瞬間に二重予約が起きる
- **場所**：設計 §2「1件だけとする（アプリで確認する）」、§4.1「SELECT で調べる → INSERT」、仕様 §11
- **モデル**：確認（SELECT）と書き込み（INSERT）の間が空いています。2つのリクエストが同時に SELECT すると、どちらも空きと判断し、どちらも `tentative` を INSERT します。
- **起きること**：§9 の 9:00 には同じ枠にアクセスが集中するので、最も起きやすい時刻にこの競合が起きます。
- **問い**：部分ユニークインデックス（`UNIQUE (facility_id, date, slot) WHERE status IN ('tentative','paid',…)`）か排他ロックで、DB に保証させますか？

### 4. 矛盾：繰り上がった予約がすぐ失効する
- **場所**：仕様 §8「通知から30分以内に支払う」、設計 §4.2「`created_at` から30分」、§4.3「waiting を tentative にし」
- **モデル**：繰り上げでは既存の行の status を書き換えるだけなので、`created_at` はキャンセル待ちに登録した時刻のままです。
- **起きること**：繰り上がった予約は、次の5分バッチで失効します。利用者はメールを開く前に枠を失います。
- **問い**：期限の起点（例：`tentative_since` や `expires_at`）を別の列で持ちますか？

### 5. 抜け：キャンセル以外で枠が空いたとき、キャンセル待ちは繰り上がるか
- **場所**：仕様 §3.3「失効し、枠は空く」、§8「予約がキャンセルされて枠が空くと」、設計 §4.2
- **モデル**：(キャンセル待ち, 枠が空く) のセルを、空いた理由ごとに見ると次のとおりです。
  - 利用者のキャンセル：§8 で定義されている
  - 仮予約の失効：書かれていない。設計のバッチも繰り上げをしない
- **起きること**：§4.1 では、仮予約で埋まっている枠にもキャンセル待ちができます。その仮予約が失効すると枠は空きますが、待っている人は繰り上がりません。後から来た人が普通に予約でき、待っていた人より先に枠を取れてしまいます。
- **問い**：失効でも繰り上げますか？　キャンセル待ちを利用者が自分で取り消す方法や、利用日を過ぎたら終わるといった、キャンセル待ちの終わり方は決めますか？

### 6. 矛盾/抜け：「同じ日に2件まで」と団体予約「5件まで」の関係
- **場所**：仕様 §3.1、§6「同じ日に複数の団体予約を作ることができる（最大5件）」
- **モデル**：ルールは「利用者×日 ≤ 2」と「代表者×日の団体予約 ≤ 5」の2つです。団体予約が §3.1 の「予約」に入るなら、この2つは両立しません。キャンセル待ちが2件に数えられるかも書かれていません。設計にはどちらの上限の確認もなく、予約が団体予約かどうかを区別する列もありません。人数上限20人の確認もありません。
- **問い**：団体予約は §3.1 の件数に入りますか？　キャンセル待ちは数えますか？　設計で団体予約をどう見分け、どこで上限を確かめますか？

### 7. 抜け/リスク：権限マトリクスの一部が API に落ちていない
- **場所**：仕様 §4、§7、設計 §3
- **モデル**：付録Bの空欄を参照してください。
  - **当日の利用確認**（§3.3、§4）に当たる API がないため、利用済みには遷移できません。
  - **利用者が自分の予約を確認する** API がありません。
  - **管理者「すべての操作」** を許す API がひとつもありません。
  - **施設スタッフの「担当施設」** を表すデータ（スタッフと施設の対応）がありません。そのため、どのスタッフでも任意の施設の休館を登録できます。休館を登録するとその日の予約がすべて取り消され、返金されるので、ここを誤ると影響が大きいです。
- **問い**：スタッフと施設の対応表は持ちますか？　管理者の「すべて」は、他人の予約の作成やキャンセル、休館の取り消しまで含みますか？　電話や窓口の受付は続けますか（§1）。続けるなら、職員が代わりに予約を作る操作が必要になります。

### 8. リスク：臨時休館の処理が途中で失敗したとき
- **場所**：仕様 §7、設計 §4.4「処理の中で…順に cancelled にし…一件ずつ返金 API を呼び、メールを送る」
- **モデル**：失敗のケースが書かれていません（付録C）。
  - リクエストの中で同期的に、件数分の外部呼び出しをしています。途中でタイムアウトすると、一部の予約だけが取り消された状態になります。
  - そこで再実行すると、返金が二重に行われるおそれがあります。
  - 決済処理中の予約は、休館後に完了通知が届くと `paid` になり、返金されません。
  - 休館を登録した後も、§4.1 にはその日の新しい予約を拒む確認がありません。
  - キャンセル待ちの人に知らせるかどうかも書かれていません。
- **問い**：返金とメールは非同期のジョブにして、冪等キーを付けて再試行しますか？　休館日の新規予約は拒否しますか？

### 9. 抜け：キャンセル時の返金が失敗したとき
- **場所**：設計 §4.3
- **問い**：返金 API が失敗したら、`cancelled` にした変更を戻しますか？　それとも `cancelled` のまま返金を再試行しますか？　繰り上げとメールも同じ処理の中にあるので、どこまでを1つのトランザクションにするかを決める必要があります。決済が失敗した通知への対応（決済処理中から仮予約に戻すのか）も書かれていません。

### 10. 抜け：キャンセル期限と利用確認の条件
- **場所**：仕様 §3.4「前日まで、いつでも」、§3.3「当日、施設スタッフが利用を確認すると」
- **抜けている点**：
  - 「前日まで」が前日の何時までなのか書かれていません。
  - 利用日当日のキャンセルは拒否するのか書かれていません。
  - 仮予約の利用者が当日来たとき、利用確認できるのか書かれていません。§3.3 の書き方では、支払っていなくても確認できるように読めます。
  - 支払い済みのまま来なかった場合、状態が終わらずに残り続けます。
  - 夜遅くのキャンセルで繰り上がった人も、深夜に30分以内で支払う必要があります。
- **問い**：利用確認は支払い済みの予約に限りますか？　当日の深夜に繰り上げた場合の期限は特別に扱いますか？

### 11. 抜け：受付開始日の計算
- **場所**：仕様 §9「利用日の1か月前の午前9時」
- **問い**：3月31日の予約は、2月の何日に受付を始めますか？　時刻はどのタイムゾーンで、どの時計を基準にしますか？

### 12. 抜け：非機能要件に数字がない
- **場所**：仕様 §11「すぐに予約できること」
- **モデル**：容量モデルに入れる負荷（同時に来る人数）も目標（応答時間）もないため、書けません。設計にもピーク時の対策は書かれていません。定期メンテナンスの間に30分の期限やバッチがどう扱われるかも書かれていません。
- **問い**：9:00 のピーク時の想定人数と目標の応答時間は決めますか？

### 13. 抜け：個人情報の保存期間と見える範囲
- **場所**：仕様 §10
- **問い**：住所を集める目的は何ですか？　保存期間と退会したときの扱いはどうしますか？　施設スタッフの一覧画面に電話番号や住所まで表示しますか？

> 補足：利用料金の額と計算方法、団体予約の料金は、仕様にも設計にも書かれていません。これらを別の文書で決める前提で、上の指摘からは外しています。

## 付録C　ドメインルールと障害表

**ドメインルール**
- R1：同じ (施設, 日, 枠) で有効な予約は1件まで。設計 §2 でアプリが確認するだけで、競合すると崩れる（指摘3）。決済処理中と失効の組み合わせでも崩れる（指摘1）。
- R2：利用者ひとりにつき同じ日に2件まで（§3.1）。設計では確認していない。
- R3：代表者ひとりにつき同じ日に団体予約5件まで（§6）。R2 とぶつかる。設計では確認していない。
- R4：団体のメンバーは20人まで（§6）。設計では確認していない。
