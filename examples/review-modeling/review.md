# 仕様書 v0.9 と設計書 v0.3 のレビュー

**結論：重大な問題が5つあります。** そのうち4つは二重予約になる経路で、1つは利用者に請求したのに予約がない状態になる経路です。どれも、仮予約の失効・キャンセル待ちの繰り上げ・決済完了通知の3つが、互いを考えずに書かれていることから起きています。もう一つの大きな傾向として、仕様にあるルールの多くを設計がまだ扱っていません（回数の上限、受付期間、キャンセル期限、利用確認、管理者、担当施設）。

以下の指摘は、仕様と設計をそれぞれ状態遷移表や権限表などに書き起こし、突き合わせた結果です。書き起こした表は末尾の付録にあります。すべて文書を読んで検討した結果で、ツールによる検証（TLA+ など）はしていません。

---

## 指摘（影響の大きい順）

### 🔴 F1. 矛盾：支払いが失効の後に完了したらどうなるか
**場所：** 仕様 §3.3、§5 ／ 設計 §4.2、§4.5

- 仕様 §5 には「決済処理中」という状態があります。しかし §3.2 の状態一覧にも、設計の `status` にもありません。
- 設計 §4.2 のバッチは、`created_at` から30分を過ぎた `tentative` を `cancelled` にします。決済が処理中かどうかは見ていません。
- 設計 §4.5 は Webhook を受けると「対象の予約を `paid` にする」とだけ書いていて、その時点の状態を確認しません。

**問題になる流れ：** 29分にカード情報を入力 → 30分過ぎにバッチが `cancelled` にする → 枠が空き、別の人が `tentative` で取る → Webhook が届いて元の予約が `paid` に戻る。結果は、同じ枠に予約が2件で、どちらにも料金が発生している状態です。Webhook を `paid` に戻さないように直しても、今度は「請求したのに予約がない」状態が残ります。

状態遷移表では、(決済処理中, 30分経過) と (終端の状態, 決済完了通知) のマスが空いています。

> **質問：** 決済処理中は30分の失効の対象外にしますか。対象外にしないなら、失効した後に届いた完了通知は、自動で返金しますか、それとも枠が空いていれば予約を戻しますか。

### 🔴 F2. 危険：受付開始の時刻に同じ枠を2人が取れる
**場所：** 設計 §2「アプリで確認する」、§4.1 ／ 仕様 §11

§4.1 は「SELECT で空きを確認してから INSERT する」流れで、一意性はデータベースで保証していません。仕様 §11 が想定している9時ちょうどのアクセス集中では、2つのリクエストが同時に「空き」と判断して、両方とも `tentative` になります。同じ形の競合は次の場面でも起きます。

- 新規予約と、キャンセルに伴う繰り上げが同時に走ったとき（付録 C3）
- 新規予約と、臨時休館の登録が同時に走ったとき（付録 C4）

> **質問：** (facility_id, date, slot) の一意性を、`status IN (tentative, paid)` を条件にした部分一意インデックスなど、データベース側で保証しますか。

### 🔴 F3. 矛盾：繰り上がった人の仮予約が、すぐに失効する
**場所：** 仕様 §8「通知から30分以内」 ／ 設計 §4.2「`created_at` から30分」、§4.3

繰り上げは、`waiting` の行を `tentative` に書き換えるだけです。そのため `created_at` には、キャンセル待ちに登録した時刻（数日前のこともあります）が残っています。次のバッチ（最大5分後）で即座に失効してしまい、仕様 §8 の「通知から30分」は実質守られません。

> **質問：** 失効の起点として、仮予約になった時刻を保持する列を設けますか。

### 🔴 F4. 危険（設計の不具合）：キャンセル待ちをやめると、埋まっている枠に別の人が繰り上がる
**場所：** 設計 §4.3

§4.3 は、キャンセルされた予約の状態を見ずに、`waiting` の先頭を `tentative` にします。

- `waiting` の人が待つのをやめると、枠はまだ埋まっているのに次の人が繰り上がり、二重予約になります。
- `tentative` のキャンセルでも同じ処理が走ります。ここは仕様どおりなので問題ありません。

> **質問：** 繰り上げを行うのは、`tentative` か `paid` がキャンセルされたときだけでよいですか。

### 🔴 F5. 抜け：失効で枠が空いてもキャンセル待ちが動かず、後から来た人が先に取れる
**場所：** 仕様 §3.3「枠は空く」、§8「予約がキャンセルされて枠が空くと」 ／ 設計 §4.1、§4.2

- 仕様 §8 で繰り上げのきっかけになっているのは「キャンセル」だけです。失効や臨時休館の取り消しで枠が空いたときにどうするかは書かれていません。
- 設計 §4.2 は失効時に繰り上げをしません。
- 設計 §4.1 は `waiting` がいるかどうかを見ずに、空いていれば新しく来た人を `tentative` にします。

結果として、キャンセル待ちの人がいるのに、後から来た人が先に枠を取れます。

> **質問：** 失効で枠が空いたときも繰り上げますか。キャンセル待ちの人がいる枠への新規予約は、キャンセル待ちに回しますか。

### 🟠 F6. 抜け：決済完了の通知の信頼性と、決済が失敗したとき
**場所：** 仕様 §5 ／ 設計 §3、§4.5

- `/webhooks/payment` で送信元をどう確認するか（署名の検証など）が書かれていません。偽の通知で、払っていない予約を `paid` にできてしまいます。
- 同じ通知が2回届いたときに、何度処理しても結果が変わらないか（冪等性）が書かれていません。`used` の予約に通知が届くと `paid` に戻ってしまいます。
- 決済が失敗したとき、つまり 決済処理中 → ? が、仕様にも設計にもありません。
- 仕様 §5 では、利用者が「支払い画面でカード情報を入力」します。この画面が自前の SPA なのか、決済サービス側のページなのかが決まっていません。自前の画面なら、§5 の「保持しない」だけではカード情報の取り扱いに関する範囲（PCI DSS）から外れません。

> **質問：** 通知の送信元の確認、2回目以降の通知の扱い、決済失敗時の遷移、カード入力画面がどちらのものか。この4点を決めてもらえますか。

### 🟠 F7. 抜け：臨時休館
**場所：** 仕様 §7 ／ 設計 §3、§4.4

- 設計には臨時休館を記録する表がありません。登録した後も、その日の新しい予約を受け付けてしまいます。
- 仕様 §7 の「すべて取り消し」に、キャンセル待ちと決済処理中が含まれるかが書かれていません。決済処理中が含まれる場合、F1 と同じ問題が起きます。
- 仕様 §8 を文字どおり読むと、取り消しもキャンセルの一つなので、休館日にキャンセル待ちの人が繰り上がることになります。
- 設計 §4.4 は、リクエストの中で返金とメール送信を一件ずつ行います。途中で失敗したりタイムアウトしたりすると一部の予約だけが取り消された状態になり、再実行したときに二重に返金するおそれもあります。
- 一日のうち一部の時間だけ休館する場合や、休館の取り消しも書かれていません。

> **質問：** 臨時休館を記録として持ちますか。取り消す対象はどの状態の予約までですか。返金とメールは非同期にして、再実行しても二重にならないようにしますか。

### 🟠 F8. 抜け：返金とメールが失敗したとき
**場所：** 設計 §4.3、§4.4

- 返金 API が失敗したとき、予約を `cancelled` に戻しますか、それとも返金だけ後で再実行しますか。
- 繰り上げのメールが届かないと、利用者は気づかないまま30分が過ぎて失効します。
- 返金状況を記録する列がないので、問い合わせを受けても答えられません。

> **質問：** 返金を記録するか、失敗したら再実行するか、メール失敗時に仮予約をどう扱うか。

### 🟠 F9. 抜け：キャンセルの期限と、状態ごとの扱い
**場所：** 仕様 §3.4、§9 ／ 設計 §4.3

- 「前日まで」がいつの何時までなのか（前日の23:59か、営業終了時刻か）が決まっていません。
- 設計の DELETE は期限を確認していません。
- キャンセルできるかどうかが状態ごとに書かれていません。
  - 決済処理中：書かれていません。
  - 利用済み：書かれていません。当日扱いで不可、とも読めます。
  - キャンセル待ち：期限なしでやめられるかが書かれていません。

> **質問：** 期限の境目の時刻、期限の確認を設計に入れるか、状態ごとにキャンセルできるか。

### 🟠 F10. 抜け：「利用済み」に遷移する手段がない
**場所：** 仕様 §3.3、§4 ／ 設計 §3

利用確認の API がないので、`used` には遷移できません。次のことも書かれていません。

- 来なかった人の扱い：`paid` のまま残り続けます。
- 未払いの予約で当日来た人の扱い

> **質問：** 利用確認の API と、無断欠席時の状態を決めますか。

### 🟠 F11. 抜け：権限が API に反映されていない
**場所：** 仕様 §4 ／ 設計 §3

- 仕様の「管理者：すべての操作」に当たる API がありません。
- 「担当施設」かどうかを確認する手段がありません。スタッフと施設の関係を持つデータがないため、どのスタッフも全施設の予約一覧を見られ、休館も登録できます。
- 仕様で利用者ができる「確認」（自分の予約を見る）に当たる GET がありません。
- スタッフの一覧で、電話番号や住所まで見えるかどうかが決まっていません。

> **質問：** 担当施設の関係をデータに持ちますか。管理者の操作と、利用者の参照 API を追加しますか。

### 🟡 F12. 矛盾候補：1日に持てる予約の数
**場所：** 仕様 §3.1「2件まで」、§6「団体予約は最大5件」 ／ 設計：どちらも未実装

- 団体予約は §3.1 の2件に数えますか。それとも別枠ですか。後者の場合、代表者は1日に7件まで持てます。
- キャンセル待ちや決済処理中は2件に数えますか。
- 繰り上げによって上限を超える場合はどうしますか。

> **質問：** 何を何件まで数えるかを決めてもらえますか。

### 🟡 F13. 抜け：団体予約のデータ
**場所：** 仕様 §6 ／ 設計 §2、§3

- 団体予約かどうかを区別する列がありません。そのため、個人の予約にもメンバーを追加できてしまいます。
- メンバー20人の上限が設計で確認されていません。
- メンバーを削除・変更する手段がありません。
- 料金を人数で計算するかどうか、料金そのものがどこにも書かれていません。

### 🟡 F14. 抜け：受付期間
**場所：** 仕様 §9 ／ 設計：未実装

- 「1か月前の9時」を、月末の日付にどう当てはめるかが決まっていません。例えば3月31日の1か月前は2月に存在しない日付です。
- キャンセル待ちも9時より前は登録できないのか。
- 当日の予約を受け付けるのか。

### 🟡 F15. 危険：アクセス集中の想定と、仮予約による枠の占有
**場所：** 仕様 §11

- 「すぐに予約できる」に、具体的な数値（想定の同時アクセス数や応答時間）がありません。
- 仮予約は支払いなしで30分間枠を押さえられます。アカウントを複数作れば、2件の上限があっても人気の枠を占有できます。

> **質問：** 目標とする数値と、仮予約による占有への対策は必要ですか。

### 🟡 F16. 抜け：個人情報
**場所：** 仕様 §10 ／ 設計

- 利用者のデータを持つ表が設計にありません。
- 保存期間と、退会したときの扱いが決まっていません。
- アカウントを持たないメンバーの氏名の扱いが決まっていません。
- メール配信サービスに渡すデータの範囲が決まっていません。

### 🟡 F17. 用語：「キャンセル・失効・取り消し」が設計ではすべて `cancelled` になる
**場所：** 仕様 §3.3、§3.4、§7 ／ 設計 §2

この3つは、返金するか、繰り上げるか、どのメールを送るかが違います。それなのに設計では区別できず、後から理由も追えません。また、仕様 §3.1 の「予約」にキャンセル待ちが含まれるかどうかもはっきりしていません（F12 の原因です）。

### F. データの流れと信頼の境目

- **ブラウザ → API：** 氏名・電話番号・住所・メールアドレス・メンバーの氏名。入力をどこで検証するかが書かれていません。
- **ブラウザ → 決済サービス：** カード情報。自前の画面を経由するかどうかが書かれていません（F6）。
- **決済サービス → API（通知）：** 外部から入ってくる信頼できない入力ですが、確認方法が書かれていません（F6）。
- **API → メール配信サービス：** メールアドレスと予約内容。渡すデータの範囲が書かれていません。
- **データベース → スタッフ画面：** 個人情報がどこまで見えるかが書かれていません（F11）。
- **保存：** 保存期間が書かれていません（F16）。
