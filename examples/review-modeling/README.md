# 作例: 施設予約システムの仕様・設計レビュー

> Sample output of `review-modeling` (in Japanese): a review of a made-up specification and design document with planted defects.

題材は、このスキルの evals のために書いた**架空の**仕様書と設計書（市民スポーツ施設の予約システム）である。実在のシステムではない。状態遷移、権限、ドメインのルール、障害、並行性のそれぞれに、欠陥をわざと仕込んである。

- 仕様書: [spec.md](../../skills/review-modeling/evals/files/spec.md)
- 設計書: [design.md](../../skills/review-modeling/evals/files/design.md)
- レビュー結果: [review.md](review.md)

[review.md](review.md) は、二つの文書を置いて「spec.md（仕様）と design.md（設計）をレビューして」と頼んだときの出力である。手を加えていない。末尾にあった、共有用のページにするかを尋ねる一文だけを除いた。

## 見どころ

- **モデルどうしの突き合わせから出る指摘。** 指摘4（繰り上がった予約がすぐ失効する）は、仕様 §8 の「通知から30分」と、設計 §4.2 の「`created_at` から30分」と §4.3 の繰り上げを並べて初めて見える。指摘5（失効では繰り上がらず、後から来た人が先に枠を取れる）も同じである。
- **空いたマスを埋めない。** 付録Aの状態表では、本文に書かれていないマスを `?` のまま残している。（決済処理中, 30分経過）のように、もっともらしい既定値で埋めると隠れてしまうマスが、そのまま指摘1になっている。
- **作者が答えられる問い。** 指摘は直し方の提案ではなく、まだ誰も下していない決定を問う形で終わる。
- **見た範囲。** 書いたモデル、軽く見たモデル、書かなかったモデルとその理由を挙げている。検査は読んだ結果であって証明ではない、とも述べている。

## スキルなしとの比較

同じ頼み方を、スキルを入れずにも走らせて比べた。仕様だけの場合を1種類のモデルで、仕様と設計の場合を3種類のモデルで、条件ごとに1回ずつ走らせた。

| 見たこと | スキルなし | スキルあり |
|---|---|---|
| 仕込んだ主な欠陥（決済処理中の抜け、件数上限の矛盾、二重予約、繰り上げ直後の失効など） | 見つけた | 見つけた |
| 作者が答えられる問いの形 | 一部（多くは修正案） | すべての回 |
| 見た範囲（書いたモデル、書かなかったモデル） | 無し | すべての回 |
| モデルの付録（本文に無いマスは `?` のまま） | 無し | すべての回 |
| 長さと時間 | 基準 | 長さはおよそ2倍、時間は1.5〜4倍 |

この小さな文書では、見つかった欠陥の数はスキルの有無でほとんど変わらなかった。違いは主に形で、指摘ごとに根拠のモデルと本文の箇所が付き、作者がそのまま答えられる。長くて散らかった実際の仕様書での違いは、まだ確かめていない。
