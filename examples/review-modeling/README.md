## 作例1: 施設予約システムの仕様・設計レビュー

題材は、このスキルの evals のために書いた**架空の**仕様書と設計書（市民スポーツ施設の予約システム）である。実在のシステムではない。状態遷移、権限、ドメインのルール、障害、並行性のそれぞれに、欠陥をわざと仕込んである。

- 仕様書: [spec.md](../../skills/review-modeling/evals/files/spec.md)
- 設計書: [design.md](../../skills/review-modeling/evals/files/design.md)
- レビュー結果: [review.md](review.md)
- 確認項目のチェックリスト: [checklist.md](checklist.md)

[review.md](review.md) は、二つの文書を置いて「spec.md（仕様）と design.md（設計）をレビューして」と頼んだときの出力である。末尾でチェックリストを作れると提案しているので、「うん」と返した。そのときの出力が [checklist.md](checklist.md) である。どちらも手を加えていない。構成系のモデル（構成、データの持ち主、インターフェースの契約、移行）を足す前の版で作った。

### 見どころ

#### レビュー

- **モデルどうしの突き合わせから出る指摘。** 指摘3（繰り上げた仮予約が数分で失効する）は、仕様 §8 の「通知から30分」と、設計 §4.2 の「`created_at` から30分」と §4.3 の繰り上げを並べて初めて見える。指摘5（失効で空いた枠では繰り上がらず、後から来た人が追い越す）も同じである。指摘4（キャンセル待ちを取り下げると、空いていない枠で繰り上げが起きる）は、付録A2の設計の状態遷移から出ている。
- **空いたマスを埋めない。** 付録A1の状態表では、本文に書かれていないマスを `?` のまま残し、書かれてはいないが読み取れるマスは斜体で分けている。（決済処理中, 30分経過）のように、もっともらしい既定値で埋めると隠れてしまうマスが、そのまま指摘2になっている。
- **作者が答えられる問い。** どの指摘も、直し方の提案ではなく、まだ誰も下していない決定を問う形で終わる。
- **見た範囲と、書いたモデルのすべて。** 「どのモデルを書いたか」で、書いた8つのモデルと、書かなかったモデルとその理由を挙げ、書いたモデルはすべて付録A1〜A9に載せている。並行性やドメインのルールはツールで検査しておらず、読んだ結果だとも述べている。

#### チェックリスト

- **決まっているマスだけが項目になる。** 各項目は、作ったシステムで確かめられる一文と、出どころの節でできている。仕様から読み取っただけの項目には「（読み取り）」と付け、作者に確かめてから印を付けるよう断っている。
- **決まっていないマスは「回答待ち」。** チェックボックスを付けず、どの指摘の答えを待っているかを添えている。数値の無い「すぐに予約できる」も、項目にせずここに入っている。
- **境目を避けて、決まっている側だけを項目にする。** 「前日まで」が何時までかは決まっていない（指摘10）。そこで項目は「前々日以前ならキャンセルできる」とし、前日の扱いは回答待ちに回している。
- **数え違いが一つある。** 末尾の「チェック項目は計51件（仕様46件、設計5件）、回答待ちは39件」は数え違いで、実際は項目が43件（仕様35件、設計8件）、回答待ちが34件である。

### スキルなしとの比較

同じ頼み方を、スキルを入れずにも走らせて比べた。仕様だけの場合と、仕様と設計の場合を、モデルを変えた4つの条件で比べている。条件ごとの回数は1〜2回と少ない。

| 見たこと | スキルなし | スキルあり |
|---|---|---|
| 仕込んだ主な欠陥（決済処理中の抜け、件数上限の矛盾、二重予約、繰り上げ直後の失効など） | 見つけた | 見つけた |
| 作者が答えられる問いの形 | 一部（多くは修正案） | すべての回 |
| 見た範囲（書いたモデル、書かなかったモデル） | 無し | すべての回 |
| モデルの付録（本文に無いマスは `?` のまま） | 無し | すべての回 |
| 長さと時間 | 基準 | 長さは2〜3倍、時間は2〜4倍 |

この小さな文書では、見つかった欠陥の数はスキルの有無でほとんど変わらなかった。違いは主に形で、指摘ごとに根拠のモデルと本文の箇所が付き、作者がそのまま答えられる。長くて散らかった実際の仕様書での違いは、まだ確かめていない。

## 作例2: 図書館の貸出システムのサービス分割設計のレビュー

題材は、構成系のモデルを足したときの evals のために書いた**架空の**設計書である。市立図書館の貸出システムを、貸出、会員、検索、通知の四つのサービスに分け、旧システムから移行する。実在のシステムではない。持ち主のいない業務、二つのサービスからの書き込み、同期の呼び出しの輪、再送で二重になる貸出、移行の途中で旧と新の両方に書き込まれることなどを、わざと仕込んである。

- 設計書: [architecture.md](../../skills/review-modeling/evals/files/architecture.md)
- レビュー結果: [architecture-review.md](architecture-review.md)

[architecture-review.md](architecture-review.md) は、「architecture.md の設計書をレビューして」と頼んだときの出力で、手を加えていない。

### 見どころ

- **構成のモデルから出る指摘。** 付録Aの「システムがすること → 担当」の表で、期限超過の通知、電話の会員への連絡、書誌と蔵書の管理の担当が空いている。そこから指摘6（期限超過を誰も知らせない）と指摘7（検索インデックスの書誌の出どころが無い）が出ている。指摘7は仕込んだものではなく、モデルを書いて初めて見つかった抜けである。
- **CRUD 表から出る指摘。** 付録Bで、loans.status の列に書き手が二つ（貸出と会員）あり、検索と会員のサービスが loans DB に直接入っていることが見える。指摘8（退会で `returned` にすると本の行方が消える）と指摘9（チームごとに独立してリリースできない）がそこから出ている。
- **インターフェースの契約から出る指摘。** 付録Eで、状態を変える API の「繰り返して安全か」は埋まらないか「安全でない」になり、どの API も「認可」の列が埋まらない。前者と端末の5秒の再送から指摘5（二重の貸出）が、後者から指摘3が出ている。「足りない API」の表からは、指摘11（窓口が貸出 ID や会員の uuid を知る手段が無い）が出ている。
- **移行と互換性から出る指摘。** 付録Iの手順表には「書き込み先」と「戻し方」の空欄が、互換性の表には手順3の1週間に出会う旧と新の組み合わせのうち壊れるものが並ぶ。指摘1（旧と新の両方に書き込まれる）と指摘2（コピーの後の書き込みが移らない）が出ている。所見がいちばん多かった観点である。
- **数え方の揺れが一つある。** 同じ呼び出しの連なり（端末 → 貸出 → 会員 → 貸出）を、指摘5は「2段重なる」、付録Aは「3段つながる」と書いている。

### スキルなし、構成系を足す前のスキルとの比較

同じ頼み方を、スキルなし、構成系のモデルを足す前のスキル（変更前）、足した後のスキル（変更後）で1回ずつ走らせ、仕込んだ欠陥と形について20項目で採点した。回数が少ないので、傾向として読んでほしい。

| 見たこと | スキルなし | 変更前 | 変更後 |
|---|---|---|---|
| 仕込んだ欠陥（12項目） | 11 | 12 | 12 |
| 付録に書いたモデル | 無し | データの持ち主と依存（一つの表）、移行など。インターフェースの契約は無し | 構成、データの持ち主、インターフェースの契約、移行を含む11 |
| 作者が答えられる問いの形 | 一部（多くは修正案） | すべて | すべて |
| 採点（20項目） | 12 | 19 | 20 |
| 時間 | 基準 | 約3倍 | 約3.5倍 |

この文書では、仕込んだ欠陥はスキルなしでもほとんど見つかった。違いは主に形と、モデルの揃い方である。変更前のスキルも、文書が明らかに求めるデータの持ち主と移行のモデルは自分で書いた。

構成系のモデルを足した効果がはっきり出たのは、構成を前面に出していない [design.md](../../skills/review-modeling/evals/files/design.md) を単体でレビューしたときだった。§4.2 のバッチが §1 の構成に出てこないことを指摘し、構成と CRUD のモデルを書いたのは変更後だけで、採点は変更後 13/14、変更前 12/14、スキルなし 7/14 だった。仕様と設計を突き合わせる作例1と同じ頼み方も変更後で走らせ、13項目すべてを満たした。
