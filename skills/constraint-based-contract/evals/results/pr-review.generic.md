# PR Review

プルリクエストをレビューし、マージしてよいかを判断する。

## いちばん大事なこと

レビュー結果を読む人は、それを見て「自分でも見直すか、このままマージするか」を決める。だから「確認しました」「問題ありません」とだけ書かれたレビューは、役に立たないどころか害になることがある。本当に確認したのかを読み手が判別できず、実は確認していなかった場合は誤ったマージにつながるからだ。

そこで、次の2つを守る。

- **「確認した」と書くなら証跡をつける。** 証跡とは、読み手が同じものを見に行ける具体的なもののこと。ファイル名と行番号、実行したコマンドとその出力、仕様書の該当箇所の引用、検索に使ったコマンドとヒット件数などが当たる。証跡を示せない「確認済み」は、未確認として扱う。
- **できなかったことは「確認できなかった」と書く。** 仕様書が見つからない、テストを実行できない、diff しか渡されていない、といったことはよく起きる。そのとき確認したふりをするより、何ができなかったかを正直に書くほうがレビューとしてずっと価値が高い。読み手は、そこを自分で確認すればよいと分かる。

## 手順

各手順に「何をすれば終わりか」と「レポートに何を残すか」を書いた。レポートに残すものを出せない手順は、まだ終わっていない。

小さな PR（typo 修正、ドキュメントだけの変更など）では各項目を短くしてよい。ただし証跡と「確認できなかったこと」は省かない。手順が当てはまらないときは「対象外（ドキュメントのみの変更のため）」のように理由を添えて書く。

### 1. 変更の目的を把握する

PR のタイトル・説明・紐づく Issue を読み、この変更で何を実現しようとしているかを1〜2文で自分の言葉にまとめる。説明に書かれていない変更が diff に混ざっていれば、それも記録する。

- 残すもの: 目的の要約。説明が無い・曖昧な場合はそう書く（それ自体を指摘にしてよい）。

### 2. 仕様と照合する

PR 説明のリンク、紐づく Issue、リポジトリ内のドキュメント（`docs/` など）から、この変更に関係する仕様を探す。見つかったら仕様の要件を箇条書きに分け、要件ごとに実装箇所を対応づける。

- 残すもの: 参照した文書名とセクション、要件ごとの照合結果（「要件 → 実装箇所 `file:line`」「実装が見当たらない」「仕様と異なる」のいずれか）。
- 見つからなかったとき: 探した場所を書き、「仕様書は見つからず、照合は行っていない。PR 説明の記述を仕様とみなしてレビューした」のように書く。仕様書を読んでいないのに「仕様を確認しました」とは書かない。

### 3. 変更された全ファイルを読む

diff に含まれるファイルを一覧にし、1つずつ読む。diff の行だけでなく、変更された関数の全体と、必要ならその周辺も読む。変更行だけを見ても、その関数が何を前提にしているかは分からないからだ。

- 残すもの: 変更ファイルの一覧と、それぞれ「読んだ」か「読まなかった（理由）」か。ロックファイルや自動生成ファイルのように意図的に飛ばしたものも、飛ばしたと書く。
- PR が大きくて全部を丁寧に読めないとき: リスクの高いもの（ロジックの変更、認証・課金・データ削除まわり、公開 API）から読み、読めなかったファイルを明記する。

### 4. 影響範囲を調べる

変更された関数・クラス・API・設定値・DB スキーマなどについて、それを使っている箇所を検索する。シグネチャ・戻り値・副作用が変わったものは特に、呼び出し元がその変化に対応しているかを見る。

- 残すもの: 調べた対象、検索に使ったコマンドやキーワード、見つかった呼び出し元（`file:line`）、それぞれへの影響の有無。
- 例: `calcPrice` の戻り値が `number` から `number | null` に変わった → `grep -rn "calcPrice(" src/` で3件。`cart.ts:41` と `invoice.ts:88` は null を考慮している。`report.ts:120` は考慮していない → 指摘 #1

### 5. テストを実行する

テストの実行方法を `package.json` の scripts、`Makefile`、CI 設定、README などで確かめてから、既存テストを実行する。

- 残すもの: 実行したコマンドそのものと、結果の要約行（例: `Tests: 212 passed, 1 failed`）。要約行は実際の出力からそのまま写す。失敗があればテスト名とエラーの要点も残す。
- 失敗したとき: その失敗が PR の変更によるものか、もともと失敗していたものかを切り分け、そう判断した根拠を書く。テストを通すためにコードやテストを書き換えてはいけない（下の「守ること」を参照）。
- 実行できなかったとき（環境が無い、diff だけ渡された、依存関係が入らない、など）: 試したコマンドとエラー、または実行しなかった理由を書く。結果を推測で書かない。
- あわせて、今回追加・変更された振る舞いにテストがあるかを見る。無ければ指摘する。

### 6. 例外ケースを洗い出す

変更されたロジックごとに、壊れやすい入力や状況を具体的に挙げ、それぞれをコードがどう扱っているかを確かめる。観点の例は次のとおり。

- 空・null・未定義、0・負数・最大値、空配列・1件・大量件数
- 不正な形式の入力、文字コード・タイムゾーン・丸め
- 外部呼び出し（API・DB・ファイル）の失敗、タイムアウト、リトライによる二重実行
- 並行実行・競合、権限のないユーザーからのアクセス
- 既存データとの互換性（マイグレーション前のデータ、古いクライアント）

すべてを機械的に埋める必要はない。その変更に関係するものを選ぶ。

- 残すもの: 「ケース / 該当コード `file:line` / 扱い（処理済み、未処理 → 指摘 #n、対象外ならその理由）」の表。

### 7. 判定してレポートを書く

下の「出力形式」に沿ってレポートを書き、次の基準で判定する。

- **Approve（LGTM）**: 必須の指摘が0件で、かつ「確認できなかったこと」に判定を左右するものが無い。
- **Request changes**: 必須の指摘が1件以上ある。
- **判断保留**: 必須の指摘は見つかっていないが、仕様との照合やテストの実行など、判定に必要な確認ができていない。何を確認できれば Approve できるかを書く。

判定を左右する確認が残っているのに Approve にしない。「おそらく問題ない」は Approve の根拠にならない。diff だけ渡された場合も同じ基準で判定する。

## 出力形式

```markdown
## 判定: Approve / Request changes / 判断保留

（判定の理由を1〜3行で。必須の指摘の件数と、確認できなかった重要な項目があればそれも）

## 変更の目的
（手順1の要約）

## 指摘事項
### #1 [必須] path/to/file.ts:42 — 問題を一言で
- 何が起きるか: （どんな入力・状況で、どんな誤った結果になるか。具体的に）
- 根拠: （該当コード、仕様の該当箇所の引用、テスト結果など）
- 修正案: （コード片やコメントで示す。ファイルは書き換えない）

### #2 [推奨] ...
### #3 [軽微] ...

（指摘が無ければ「指摘なし」と書く。何を見たうえでの結論かは「確認したこと」で分かるようにする）

## 確認したこと
- 仕様との照合: （文書名・セクション、要件ごとの照合結果）
- 読んだファイル: （n/n ファイル。読まなかったものとその理由）
- 影響範囲: （対象、検索方法、呼び出し元と影響の有無）
- テスト: `実行したコマンド` → （結果の要約行）
- 例外ケース:

  | ケース | 該当箇所 | 扱い |
  |---|---|---|

## 確認できなかったこと
- （項目 — できなかった理由 — 誰が何をすれば確認できるか）
（無ければ「なし」）
```

重大度の目安:

- **必須**: マージ前に直すべきもの。バグ、仕様違反、データ破損やセキュリティのリスク、既存機能を壊す変更。
- **推奨**: 直したほうがよいが、マージを止めるほどではないもの。保守性、テスト不足、分かりにくい命名など。
- **軽微**: 好みの範囲のもの、typo など。

## 出す前の自己チェック

レポートを出す前に次を見直す。

- 「確認しました」「問題ありません」「十分に検討しました」のような文が、証跡なしで書かれていないか。あれば証跡を足すか、「確認できなかったこと」に移す。
- どの指摘にも、ファイルと行番号、そして「何が起きるか」の具体的なシナリオがあるか。「エラーハンドリングを検討してください」のように、何が問題なのか読み手に分からない指摘になっていないか。
- 実際には実行していないコマンドの結果を書いていないか。
- 判定が判定基準と食い違っていないか（例: 判定を左右する項目が確認できていないのに Approve にしていないか）。

## 守ること

- レビュー対象のファイルを書き換えない（テストを通すための変更も含む）。commit や push もしない。修正案はコメントとして示す。
