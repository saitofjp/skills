# PR Review

プルリクエストをレビューし、マージしてよいかを判断する。

レビュー結果には判定だけでなく、判定までに何を見て、何を見ていないかを書く。結果を読んだ人が確認の中身を自分で確かめられるようにするため。調べ方や進める順番は PR に合わせて選んでよい。

## 守ること

- レビュー対象のファイルを書き換えない（テストを通すための変更も含む）。commit や push もしない。修正案はコメントとして示す。

## レビュー結果に含めるもの

見出し、並び順、詳細度は PR に合わせてよい（判定を先頭に置いてもよい）。次の情報が入っていれば足りる。

1. **レビューした範囲**
   - 見たファイル・変更箇所
   - 見ていない部分があれば、その箇所と理由（生成ファイル、diff が大きく一部だけ見た、など）
2. **変更の目的**
   - PR の説明から読み取った目的
   - 説明と実際の差分が食い違う点（あれば）
   - 説明が無ければ「PR 説明なし」と書き、差分から推測した目的は推測と分かるように書く
3. **関連する仕様**
   - 参照した仕様（文書名と該当箇所）
   - 変更が仕様と整合する点・矛盾する点
   - 仕様に書かれていない挙動を変更が含む場合は、その挙動
4. **影響**
   - 影響を受ける機能やコード（呼び出し元、データ、外部 API など）と、どう影響するか
   - 影響を探した範囲
5. **テスト**
   - 実行したテスト（他の人が同じものを実行できる程度に）とその結果。失敗があればその内容
   - 結果の出どころ（自分で実行した／CI などの結果を参照した）
   - 変更のうちテストで覆われていない挙動と、その扱い（別の方法で確かめた／未検証）
6. **例外ケース**
   - 想定した例外ケースと、それぞれの扱い（変更で対応済み／未対応／対象外とその理由）
7. **指摘**
   - 指摘ごとに：場所（ファイルと行）、問題の内容、問題だと判断した根拠、マージを止める指摘か任意の改善提案か、修正案（あれば）
   - 根拠が、実行や再現で確かめた事実か、コードを読んでの推測か
   - 指摘がなければ「指摘なし」
8. **判定**
   - マージしてよいか（例：LGTM／要修正／判断保留）と、その理由
   - 判定の前提になっている未確認事項。LGTM の場合も書く

### 確認していないことを「問題なし」と書かない

確認して何もなかった状態と、確認していない状態を書き分ける。

| 状態 | 書き方 |
|---|---|
| 確認して該当しなかった | 「該当なし（確認した範囲）」 例：「該当なし（docs/api.md の認証の節と照合）」 |
| 確認していない・できなかった | 「未確認（理由）」 例：「未確認（テストの実行環境がない）」 |
| 確認したが判断できない | 「判断不能（足りない情報）」 |

- 該当なしの項目は一行でよい。小さな PR では複数の項目をまとめてよい（例：「仕様・影響・例外ケース：該当なし（README の誤字修正のみ）」）。
- 指摘に挙げた問題は、他の項目で繰り返さず、指摘を参照すればよい。
