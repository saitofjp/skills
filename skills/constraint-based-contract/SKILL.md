# Constraint-Based Contract

既存の Skill を読み、行動指示に偏って成果物への要求が足りない箇所を見つけ、成果物に含めるべき情報のチェックリストへ変える。

**行動を規定するのではなく、成果物に何が含まれていなければならないかを規定する。**

「仕様を確認する」とだけ書くと、確認したかどうかは AI の自己申告になる。「関連する仕様を記述する」と書けば、成果物を読んだ第三者が確かめられる。一方で、どう調べ、どう考えるかは固定しない。固定しないから、AI は状況に合った方法を選べる。

| 行動指示 | 出力に対する要求 |
|---|---|
| 仕様を確認する | 関連する仕様を記述する |
| 影響範囲を調査する | 影響を受ける機能・仕様を記述する |
| 整合性を確認する | 整合する点・矛盾する点を記述する |
| 例外ケースを確認する | 想定される例外ケースを記述する |
| テストを実施する | テスト結果と未検証項目を記述する |
| 根拠を確認する | 判断の根拠を記述する |

## 対象

引数で受け取る（ファイルパス、URL、会話中のテキスト）。無ければ聞く。候補が複数あれば選んでもらう。

Skill が別ファイル（references/、テンプレートなど）に成果物の要求を置いていることがある。評価結果には、読んだファイルの範囲を書く。読めなかったものは未確認として書き、「要求なし」と扱わない。

## 評価結果に含めるもの

形式と詳細度は対象に合わせてよい。次の情報が入っていれば足りる。

### 1. 指示と成果物の対応

対象 Skill の指示ごとに、その結果が成果物のどこにどんな情報として残るか、そして次のどれに当たるか。

| 分類 | 状態 |
|---|---|
| 対応あり | 行動の結果として必要な情報が成果物に残る |
| 対応が不十分 | 出力先はあるが、必要な情報や判断の根拠が曖昧 |
| 対応なし | 行動指示はあるが、結果を出力する要求がない |
| 行動指示を維持 | 安全上の手順、禁止事項、ツールの使用条件、実行順序、操作手順など、行動そのものを指定する必要がある |

- 「対応あり」には、成果物のどの要求が受け止めているかを添える。
- 「行動指示を維持」には、出力要件に置き換えると何が損なわれるかを添える。
- 長い Skill では、同じ扱いになる指示をまとめてよい。「対応なし」「対応が不十分」の指示は個別に挙げる。

命令形かどうかでは分類しない。基準は、成果物に残すべき情報が欠けているかどうか。「〜を記述する」と書いてあっても中身が曖昧なら「対応が不十分」、「〜を確認する」でも報告欄で結果を求めているなら「対応あり」になる。

### 2. 不足箇所ごとの問題点と変換案

「対応なし」「対応が不十分」の指示それぞれについて、次の3つ。

- **対象となる指示**：原文の引用
- **問題点**：何が成果物に残らないか、何をもって満たしたと判断できないか
- **変換案**：成果物に含める情報のチェックリスト（満たすべき条件は次の節）

「漏れなく」「十分に」「適切に」のような語は、満たしたかを判断できる情報に置き換える。たとえば「対象にした範囲と、対象外にした範囲とその理由」。

出力形式を過度に固定している指示（見出しの固定、行数の上限など）もここで扱う。情報の欠落を防いでいる制約か、構成の自由を狭めているだけの制約かを書き、後者なら緩める案を出す。

不足が見つからなければ、見つからなかったと書く。成果物への要求が既に十分な Skill では、変換案が少ないことが正しい結論になる。

### 3. 補足

- 判断が分かれる点、ユーザーに決めてもらう必要がある点
- 適用上の注意（出力が長くなる、既存の報告形式と衝突する、など）

### 4. 改善後の Skill（求められたとき）

改善や修正を頼まれたら、変換案を反映した Skill を出す。評価だけを頼まれたなら、変換案の提示にとどめ、対象ファイルは書き換えない。

書き換えるときは、Skill の目的と「行動指示を維持」に分類した指示を残す。行動指示を消して出力要件だけにすると、禁止事項や実行順序が失われる。

## 変換案が満たすこと

変換案のチェックリストは、成果物に含める**情報の種類**を示すもので、回答内容や調査手順を固定するテンプレートではない。

- **情報の種類を指定し、中身・方法・順序は固定しない。** 「関連する仕様を記述する」は情報の種類。「仕様書の第2章と第3章を読み、表にまとめる」は手順の固定になる。
- **未確認・該当なし・判断不能を書き分けられる。** 確認して該当しなかった状態と、確認していない状態を区別できないと、未確認が「問題なし」に化ける。情報が得られなかったときの書き方を含め、推測で埋めさせない。
- **事実と推論と判断を分けられる。** 判断を求めるなら、その理由と根拠も残させる。
- **必須にするのは、タスクに必要な理由がある項目だけ。** 対象・理由・影響・根拠・未確定事項などから、そのタスクに要るものを選ぶ。一律に必須にすると、関係のないタスクでも空欄を埋めるための記述が増える。
- **既にある要求と重複しない。** 報告欄などで既に求めている情報を、別の場所でもう一度求めない。2箇所にあると、どちらに従うか分からなくなる。

項目の型は [references/patterns.md](references/patterns.md) にある（関連情報・差分・影響・判断・例外・検証）。全部を入れるためのものではない。対象とタスクに合うものを選び、言い換えて使う。

## 変換の例

基本形は「〇〇を確認する → 関連する〇〇を記述する」「〇〇を調査する → 調査で判明した〇〇を記述する」「〇〇を検討する → 検討結果と判断理由を記述する」。必要に応じて対象・理由・影響・根拠・未確定事項を足す。

| 対象となる指示 | 問題点 | 変換案 |
|---|---|---|
| 既存テストを実行し、通ることを確認する | 結果の記録先がない。実行していなくても「確認した」と書ける。テストが変更を覆っているかも残らない | ・実行したテストとその結果（失敗があればその内容）<br>・変更のうちテストで覆われていない挙動と、その扱い（別の方法で確かめた／未検証とその理由） |
| 例外ケースを十分に検討する | 「十分に」の基準がない。検討しなかったことと、該当がなかったことの区別がつかない | ・想定した例外ケースと、それぞれの扱い（対応済み／未対応／対象外とその理由） |
| 本番環境でコマンドを実行しない | なし | 維持する。出力要件に置き換えると、実行してから報告することを許してしまう |
