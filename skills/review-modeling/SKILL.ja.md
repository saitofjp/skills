# モデル化レビュー

目的は、コードを書く前に、仕様や設計が決めていないことと、同時には成り立たないことを見つけることである。

人は読み飛ばせるが、モデルは読み飛ばせない。状態遷移の表には状態とイベントのすべての組に、権限の表にはロールと操作のすべての組にマスがある。だから文書をモデルに書き起こす。本文からモデルが書けないところは、文書の抜けである。書けても、一つのモデルの中やモデルどうしで辻褄が合わないところは、矛盾かリスクである。

ユーザーが頼むのはレビューだけである。モデルは見るための道具であり、指摘の根拠であって、頼まれたものそのものではない。だから結果は、根拠が添えられた良い仕様レビューとして読めるようにする。

どこまでやるか、どのモデルをどの深さで書くかは、目の前の文書を見て判断してよい。

## 文書に必要なモデルを選ぶ

文書を読み、そこに書かれているものから、書くモデルを決める。兆候の例:

- 状態、ステータス、「〜中」「キャンセル」「期限切れ」→ 状態遷移
- ロール、「管理者」「本人のみ」、チーム、共有 → 権限マトリクス
- エンティティ、件数、「必ず」「一意」「最大」→ ドメインモデルとそのルール（不変条件）
- 外部サービス、メール、決済、バックグラウンド処理 → 障害と、それらをまたぐシーケンス
- 同時編集、再送、締め切り、リトライ → 並行性と順序
- 「すぐに」「大量」、上限、利用者数 → 容量
- 個人情報、アップロード、外からの入力 → データの流れと信頼境界
- 画面、手順、ユーザーがたどる流れ → 画面遷移とシナリオ
- 同じ言葉があちこちに出てくる → 用語と、それが同じ意味か

[references/models.md](references/models.md) に、モデルごとの書き方、書けなくなりやすいところ、検査すること、そこから得られるものをまとめた。選択肢であって、順に埋める一覧ではない。ログインフォームの仕様に容量のモデルは要らないし、載っていないモデルが必要な文書もある。

書いたモデルと、検討したが書かなかったモデルとその理由を、それぞれ一行で述べる。「あらゆる断面で見た」は、どの断面で見たかが読み手に見えて初めて信じられる。

## 本文からモデルを書く

モデルは文書に書いてあることから書き、要素ごとに出どころ（節、見出し、引用した言葉）を示す。そのつながりがあるから作者が確かめられ、空いたマスが指摘になる。

本文に書いていないマスは、空けたまま印を付ける。ふつうのシステムならこうするだろう、で埋めない。もっともらしい既定値こそ、このレビューが見つけるべき抜けを隠すものであり、作者は書かれたモデルを自分の仕様として読んでしまう。答えが示唆されているが明記されていないときは、示唆として書き、想定ではなく確認の対象にする。

人が読めて、ツールでも検査できる形を使う。表、Mermaid の図、短いルールの箇条書き。モデルの大きさは、それが示すものに合わせる。

## モデルを検査する

書けたら、文書が材料をくれる範囲で、三つの方向から見る。

- **一つのモデルの中。** 到達できない状態や抜け出せない状態、結果が決まっていないイベント、ある操作が破るルール、誰も意図していないことができるロール。
- **モデルどうし。** 複数の視点を持つ価値はここにある。二つの視点のすき間は、どちらか一方からは見えない。状態遷移のイベントは、どれかのシナリオに出てくるか。権限マトリクスの操作は、API に実在するか。状態を変える操作は、すべてドメインのルールを守るか。シーケンスの外部呼び出しには、すべて失敗時の扱いがあるか。
- **設計との対応。** 仕様と設計の両方が渡されたら、それぞれをモデルにして比べる。仕様の状態遷移を、設計はすべて扱えているか。仕様の権限ルールを、設計の API は守らせているか。

読むのではなく実行できる検査、たとえば TLA+ での並行プロトコルや Alloy でのドメインモデルがあり、ツールが使えるなら、実行する。そうでなければ、その検査は丁寧に読んだ結果であって証明ではないと述べる。

## 作者に伝える

指摘から始め、利用者とシステムへの影響の大きい順に並べる。それぞれを、作者が答えられる問いの形にする。仕様の指摘の多くは、間違いではなく、まだ誰も下していない決定だからである。

指摘ごとに、できる範囲で次を示す。

- 種類: 抜け（本文が述べていない）、矛盾（二つの記述が同時には成り立たない）、リスク（書かれたとおりには成り立つが、ある条件で壊れる）。
- 場所: 文書の該当箇所。
- それを示すモデルの抜粋: 空いたマス、ぶつかる二つのルール、壊れる経路。
- いつ問題になるか: 条件と、誰に何が起きるか。
- 問い。

たとえば、役に立つ細かさはこの程度である。

> **抜け: 採点中に取り消された試験はどうなるか？**
> §3.2 は `採点中 → 採点済み` を定め、§3.4 は受験者が「いつでも」取り消せるとしているが、`採点中` での取り消しが何をするかはどこにも書かれていない。状態表のマス（`採点中`, 取り消し）が空いている。取り消しの後に採点が終わると、受験者は辞退したつもりの試験に結果が保存されうる。採点が始まったら取り消しを拒むか、取り消したら結果を捨てるか、どちらにしますか？

指摘の後に、見た範囲（書いたモデルと書かなかったモデル）。その後に、モデル本体を付録として付ける。モデルはこのレビューの外でも、仕様の補足として、またテストの元として作者の役に立つ。

問題の無かったマスを一つずつ説明しない。見つけたことが埋もれる。文書がしっかりしているなら、そう述べ、なぜそう言えるかを数行で書けばよい。

## 根拠と確からしさ

本文に書いてあることと、そこから自分が判断したことを分ける。明記されていることと、示唆されているだけのことも分ける。

指摘の重さは、文書の書きぶりではなく影響で判断する。言い回し、構成、好みは、二通りに読める原因にならない限り欠陥ではない。一つの用語が二つの意味で使われているのは指摘であり、ぎこちない文はそうではない。

文書が目指す範囲を超えた改善を、欠陥として挙げない。文書が述べていないシステムの前提に依って指摘するときは、その前提を述べる。

## このスキルの範囲

このスキルは文書をレビューする。コードの変更、PR、ブランチは、`review-birds-eye` がコードから設計までを読んで見る。仕様とコードの両方があるなら、ここで書いたモデルをそのレビューに渡すことも、テストにすることもできる。
