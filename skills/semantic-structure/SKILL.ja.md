# Semantic Structure

> 英語版 [SKILL.md](SKILL.md) と同じ内容の日本語版。

文章が意味していることを、図にする。意味を1つずつ塊にし、塊どうしがどう効くかを線で結び、原文を読んでいない人がたどれて、原文の言葉で確かめられる図にする。この図が意味構造（Semantic Structure）で、`model.json` に入れる。そのうえで、原文の隣に1枚のページで見せる。

塊は、熟練した読み手がノートを作るやり方で作る。文章を塊に巻き、塊ごとにメッセージを言う見出しと、落とせない要点を付ける。初心者は頭から部分ごとに判断し、要らなそうなところを削って残りを写すので、文章の区切りが意味に合っていてもいなくても、ノートはその区切りのままになる。熟練した読み手は全体を見て判断する。文章自身の見出しや節から始め、意味に合っていればそのまま使い、合っていなければ切り直す。部分のメッセージを言う文を選び、無ければ自分で書き、細部は目立つかどうかではなく全体の中で果たす役割で残す（Brown & Day, 1983）。熟練した読み手のノートを目指す。全体から見るといっても、細部を読み飛ばすわけではない。すべてを細部まで読んだうえで、全体を俯瞰する。あなたは文章全体を一度に読んで見渡せるので、それができる。ノートの書き方は意味を見つけるための手段で、目的は意味どうしの線である。（線形のノートはページの表現の1つであって、目的ではない。）

1. **構造を作る。** ユーザーに文章があり、それがどう組み立てられているかを見たいとき。報告したら、ページを勧める。
2. **構造を見せる。** ユーザーが見たいとき。`model.json` がまだ無ければ先に作る。構造をページの側で考え出さない。

## 良い構造とは

原文を読んでいない人に向けて作る。文章を読むのはあなたなので、どう塊にするか、何と呼ぶか、何を残すかはあなたが決める。このスキルが定めるのは目標とファイルの形式だけで、手順は決めない。

- **塊は1つの意味で、一目で分かる。** 見出しは話題ではなくメッセージを短く言う。「2026年度の見通し」ではなく「2026年度：原油高が重しでも成長」。要点には、メッセージが依って立つ数字・条件・時期・主体・理由を残し、大事なことが原文の中にだけ残っている状態にしない。見出しを順に読めば話が通り、塊ごとに1セクションで発表を組み立てられる。
- **線が構造を担う。** 線は、ある意味が別の意味に何をするか（押し上げる、理由になる、ペースを左右する、答える、覆す）を言い、向きがあれば符号を付ける。原文の接続語は線がある証拠であって、線の名前ではない。線をたどれば、文章がなぜその結論に至るのかが分かる。線の無い塊は、見落とした線を探すきっかけにする。背景は線が無くてもよい。
- **いちばん大事なことが分かる。** 原文の結論には `role: "conclusion"` を付ける。ただし、読み手にとっていちばん大事なことが結論とは限らない。途中で示された規範、原文がとくに取り上げた事実、それまでを覆す転回などである。その塊には `role: "key"` を付け、原文のどこにその重みが表れているか（割かれた分量、一般論としての言明、「もっとも」、結論には要らないのにあえて述べていること）を `note` に書く。要約でもその重みを与える。ある規範を示したうえで別の理由で請求を退ける判決が典型で、棄却が結論、規範が key になる。key を結論にすり替えないこと。重みは原文の外の知識で決めないこと。
- **一言にまとまる。** `summary` で文章全体が何を言っているかを一文にし、各語句がどの塊を指すかを示す。
- **確かめられる。** 見出し・要点・線はどれも、拠り所の言葉を指す。原文が言っていることは `explicit`、あなたが推論したことは `inferred` にして `note` に理由を書く。原文の外から何も持ち込まない。

熟練した読み手のノートが目指すところ。ルールではなく方針である（Kintsch & van Dijk, 1978 のマクロ構造による）。

- **塊**　文章全体を理解したうえで、その意味のまとまりとして切る。
  - 1つの塊は、何を言っているかが1つの命題（マクロ命題）にまとまる範囲。同じマクロ命題に収まらなくなったところから、次の塊になる。
  - 塊も、細部と同じく、全体の中で果たす役割で分ける。同じことを言っていても、ほかの塊との関係で役割が違えば別の塊にする。まとめるのは、同じ役割を果たすときだけ。
  - 粒度は文章全体に合わせる。2文の文章なら句が1つの塊になり、長い報告書なら節が1つの塊になって、その部分が下の塊（`parent`）になる。報告書の冒頭の要約と、それを展開する節は同じ塊で、一節を2つ持つ。
- **要点**　抜けると、塊の意味やほかの塊とのつながりが分からなくなる細部。
- **線**
  - 塊どうしが、全体の意味をどう作っているかを表す。
  - 塊の中の細かな関係は、塊と要点の側に任せる。
  - 同じ事物に触れていることは関係の手がかりであって、関係そのものではない。
  - 読み手が補った関係も構造の一部。補ったことが分かるようにしておく。
  - 線の無い塊は、文章の中での役割がまだ見えていない表れかもしれない。
- **見直し**　一言の要約は中心の塊をたどっているか。最初の印象に引きずられて、後を読んでいないか。

## 構造を作る

最初の下書きを書く前に、`model.json` の形式 [references/semantic-structure.md](references/semantic-structure.md)（英語）を読む。

**入力と出力。**

- 文章は引数から受け取る（貼り付け・ファイルパス・URL）。
- 指定が無ければ、会話セッションを文章にする。ユーザーがタイトル・ID・リンクで別のセッションを挙げない限り、この会話を使う。原文は [references/conversation.md](references/conversation.md)（英語）のとおり会話から作る。まだ構造にするほどの会話が無ければ、文章を尋ねる。
- 1万字程度までなら1つの `model.json` に収まる。それより長いときは、どの部分を扱うか尋ねるか、部分ごとに作る。
- 原文はそのまま出力フォルダの `source.txt` に保存する。保存先はユーザー指定が無ければ `.semantic/<YYYYMMDD>-<slug>/`。
- PDFやWebページからは本文をそのまま取り出す。取り除くのは抽出のゴミ（ページ番号、柱、文中の改行）だけにし、取り除いたものを `metadata.source` に書く。スパンはこの本文を指すので、言い換えない。

**ツール**は `scripts/semantic_structure.py`（Python 3、標準ライブラリのみ）。

- `sentences source.txt` は文に番号を振る。下書きでは、一節を `{"sentences": [31, 39]}`、1文を `{"sentence": 2}` と書き、要点は言葉を引用して書ける。
- `resolve draft*.json --source source.txt -o model.json` は、下書きをまとめ、引用と文番号をオフセットに変え、形式を検査する。エラーがある間は何も書き出さない。
- `outline model.json` は構造を読み上げる。要約、続いて塊ごとに、一節の位置（S31–39）・要点・線を出す。原文を見ていない人のつもりで読み、原文の説明になっていない、または大事なことが欠けていれば、構造を直す。
- `summary model.json` は根拠の一覧を出す。各要素とその引用、明示されていないもの、どのスパンも触れていない文を並べる。

`resolve` がエラーを出さなくなり、読み上げだけで原文の説明になるまで、`resolve` と `outline` を繰り返す。

会話セッションには `scripts/session_transcript.py` を使う。記録を読み込み、ターンごとに見せ、抄録が一字一句会話にあるかを確かめる。詳しくは [references/conversation.md](references/conversation.md)。

**報告**では、`model.json` のパス、読み上げ（outline）、そして `inferred` と `uncertain` の一覧を渡し、ユーザーが確かめられるようにする。どの塊が結論で、どの塊が key か、key の重みが原文のどこに表れているかも伝える。結論と key が同じ塊なら、そう言う。そのうえでページを勧める。

## 構造を見せる

ページは固定のテンプレート [assets/viewer.html](assets/viewer.html) で、`scripts/build_viewer.py` が `model.json` を埋め込む。ページでは、ゲージが原文から塊へ、塊が持ち場について線が伸びるモデルへ、さらにその表現へと進む。ユーザーにページの一部の働きを尋ねられたとき、またはテンプレートを変える前には、[references/transform-view.md](references/transform-view.md)（英語）を読む。

1. **ページの開き方を選ぶ。** どれも見せ方の選択であり、構造は変えない。
   - `--stage`：つまみの初期位置。`text`（既定）は文章が構造になる様子を見せる。読んで探るなら `model`・`summary`・`linear`・`slides`・`table` から始める。
   - `--anchor`：構造の列の向き。ふつうは `auto` のままでよい。向きが読みにくいときだけ、`end`（結論から並べる。判決のように根拠が結論に集まる文章）か `start`（入ってくる線のない塊から並べる。問いから枝分かれする文章）を指定する。
   - `--theme`：`dark`（既定）・`light`・`auto`・`dopa`。ドパガキ風の見た目や、録画して見せるショーにしたいとき、またはユーザーが dopa やドパガキを求めたときは `dopa` にする。
2. **ビルドする。**
   `python3 scripts/build_viewer.py model.json -o view.html [--stage …] [--focus ID] [--theme …] [--anchor …] [--no-autoplay]`
   `model.json` を検証し、エラーがある間は何も書き出さない。保存先はユーザーの指定が無ければ `model.json` と同じ場所。オプションはJSONファイルにして `--view` で渡してもよい。
3. **ブラウザで確認する**（NodeとPlaywrightが使える場合）：`NODE_PATH="$(npm root -g)" node scripts/check_viewer.cjs view.html`。ページを開き、ゲージ・▶・各表現・カーソル操作・テーマ・スマホ幅を確かめる。そのうえで自分でも原文からモデルまでゆっくり動かし、線が文章の組み立てを示しているか、要約がきちんと着地しているかを見る。
4. **渡す。** パスと使い方を伝える。
   - 開くと自動で再生が始まる。▶（またはSpace）で原文から要約まで再生してモデルに戻る。ゲージのつまみをドラッグすると部品が動く様子が見え、ラベルをクリックする（または←→）と即座に切り替わる。モデルでは↑↓で表現を切り替える。
   - カーソルを重ねると原文と構造がつながり、クリックすると反対側がそこまでスクロールする。ヘッダーの light / dark / dopa でテーマを切り替える。
   - dopa では ▶ がショーになる。動画にするなら、ページを全画面にして ▶ を押し、画面録画する。

   ユーザーがローカルのファイルを開けない環境（リモート実行など）では、Artifactとして公開する。公開前に `artifact-design` スキルを読み込む。

## しないこと

- **見た目のために構造を直さない。** 構造が分かりにくいなら、構造を直す。見せ方だけの問題なら、ビューオプションを変える。
- **ページに原文の解析を足さない。原文ごとにページを書き起こさない。** ページが表示するものはすべて `model.json` から来て、テンプレートが実装である。テンプレートを改良したときは、[references/transform-view.md](references/transform-view.md) もテンプレートに合わせる。
- **コミットはユーザーに求められたときだけ行う。**
