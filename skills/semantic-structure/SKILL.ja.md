# Semantic Structure

> 英語版 [SKILL.md](SKILL.md) と同じ内容の日本語版。

文章の意味構造、つまり文章が意味していることのモデルを作り、よくできる学生が教科書から作るノートとして書き表し、原文の隣に1枚のページで見せる。仕事は2つに分かれ、1つのファイル `model.json`（[references/semantic-structure.md](references/semantic-structure.md)、英語）でつながる。

1. **ノートを作る。** ユーザーに文章があり、理解したい・ノートにしたい・構造化したいとき。報告したら、表示を勧める。
2. **ノートを見せる。** ユーザーが見たいとき。モデルがまだ無ければ先に作る。構造をページの側で考え出さない。

## 良いノートとは

原文を読んでいない人に向けて書く。文章を読むのはあなたなので、どう塊にするか、何と呼ぶか、何を残すかはあなたが決める。このスキルが定めるのは目標とファイルの形式だけで、手順は決めない。

- **一目で分かる。** 見出しは塊の話題ではなくメッセージを短く言う。「2026年度の見通し」ではなく「2026年度：原油高が重しでも成長」。塊を順に読めば話が通る。`dopagaki-generator` がスライド1枚に1メッセージを置くように、塊ごとに1セクションで発表を組み立てられる。
- **大事なことを落とさない。** メッセージが依って立つ数字・条件・時期・主体・理由を要点に残す。大事なことが原文の中にだけ残っている、という状態にしない。
- **塊どうしの効き方が分かる。** 線は、ある塊が別の塊に何をするか（押し上げる、理由になる、ペースを左右する）を言い、向きがあれば符号を付ける。原文の接続語は線がある証拠であって、線の名前ではない。
- **いちばん大事なことが分かる。** 原文の結論には `role: "conclusion"` を付ける。ただし、読み手にとっていちばん大事なことが結論とは限らない。途中で示された規範、原文がとくに取り上げた事実、それまでを覆す転回などである。その塊には `role: "key"` を付け、原文のどこにその重みが表れているか（割かれた分量、一般論としての言明、「もっとも」、結論には要らないのにあえて述べていること）を `note` に書く。要約でもその重みを与える。ある規範を示したうえで別の理由で請求を退ける判決が典型で、棄却が結論、規範が key になる。key を結論にすり替えないこと。重みは原文の外の知識で決めないこと。
- **一言にまとまる。** `summary` で文章全体が何を言っているかを一文にし、各語句がどの塊を指すかを示す。
- **確かめられる。** 見出し・要点・線はどれも、拠り所の言葉を指す。原文が言っていることは `explicit`、あなたが推論したことは `inferred` にして `note` に理由を書く。原文の外から何も持ち込まない。

塊の大きさは文章に合わせる。段落ほどの一節が1つの塊になることが多く、はっきり分かれる部分を持つ節は、部分を持つ塊（`parent`）にする。2文の文章なら、句が1つの塊になってもよい。報告書の冒頭の要約と、それを展開する節は同じ塊で、一節を2つ持つ。

## ノートを作る

**入力と出力。**

- 文章は引数から受け取る（貼り付け・ファイルパス・URL）。
- 指定が無ければ、会話セッションを文章にする。ユーザーがタイトル・ID・リンクで別のセッションを挙げない限り、この会話を使う。原文は [references/conversation.md](references/conversation.md)（英語）のとおり会話から作る。まだモデルにするほどの会話が無ければ、文章を尋ねる。
- 1万字程度までなら1つのモデルに収まる。それより長いときは、どの部分を扱うか尋ねるか、部分ごとにモデルを作る。
- 原文はそのまま出力フォルダの `source.txt` に保存する。保存先はユーザー指定が無ければ `.semantic/<YYYYMMDD>-<slug>/`。
- PDFやWebページからは本文をそのまま取り出す。取り除くのは抽出のゴミ（ページ番号、柱、文中の改行）だけにし、取り除いたものを `metadata.source` に書く。スパンはこの本文を指すので、言い換えない。

**ツール**は `scripts/semantic_structure.py`（Python 3、標準ライブラリのみ）。

- `sentences source.txt` は文に番号を振る。下書きでは、一節を `{"sentences": [31, 39]}`、1文を `{"sentence": 2}` と書き、要点は言葉を引用して書ける。
- `resolve draft*.json --source source.txt -o model.json` は、下書きをまとめ、引用と文番号をオフセットに変え、形式を検査する。エラーがある間は何も書き出さない。
- `outline model.json` はノートを読み上げる。要約、続いて塊ごとに、一節の位置（S31–39）・要点・線を出す。原文を見ていない人のつもりで読み、原文の説明になっていない、または大事なことが欠けていれば、ノートを直す。
- `summary model.json` は根拠の一覧を出す。各要素とその引用、明示されていないもの、どのスパンも触れていない文を並べる。

会話セッションには `scripts/session_transcript.py` を使う。記録を読み込み、ターンごとに見せ、抄録が一字一句会話にあるかを確かめる。詳しくは [references/conversation.md](references/conversation.md)。

**報告**では、`model.json` のパス、読み上げ（outline）、そして `inferred` と `uncertain` の一覧を渡し、ユーザーが確かめられるようにする。どの塊が結論で、どの塊が key か、key の重みが原文のどこに表れているかも伝える。結論と key が同じ塊なら、そう言う。そのうえで表示を勧める。

## ノートを見せる

ページは固定のテンプレート [assets/viewer.html](assets/viewer.html) で、`scripts/build_viewer.py` がモデルを埋め込む。ページが何をするか（原文から塊・モデル・表現へ進むゲージ、▶、結論と key の印、テーマ）は [references/transform-view.md](references/transform-view.md)（英語）にある。

1. **見せ方を選ぶ。** どれも見せ方の選択であり、モデルは変えない。
   - `--stage`：つまみの初期位置。`text`（既定）は文章が構造になる様子を見せる。読んで探るなら `model`・`summary`・`linear`・`slides`・`table` から始める。
   - `--anchor`：構造の列の向き。ふつうは `auto` のままでよい。向きが読みにくいときだけ、`end`（結論から並べる。判決のように根拠が結論に集まる文章）か `start`（入ってくる線のない塊から並べる。問いから枝分かれする文章）を指定する。
   - `--theme`：`dark`（既定）・`light`・`auto`・`dopa`。ドパガキ風の見た目や、録画して見せるショーにしたいとき、またはユーザーが dopa やドパガキを求めたときは `dopa` にする。
2. **ビルドする。**
   `python3 scripts/build_viewer.py model.json -o view.html [--stage …] [--focus ID] [--theme …] [--anchor …] [--no-autoplay]`
   モデルを検証し、エラーがある間は何も書き出さない。保存先はユーザーの指定が無ければモデルと同じ場所。オプションはJSONファイルにして `--view` で渡してもよい。
3. **ブラウザで確認する**（NodeとPlaywrightが使える場合）：`NODE_PATH="$(npm root -g)" node scripts/check_viewer.cjs view.html`。ページを開き、ゲージ・▶・各表現・カーソル操作・テーマ・スマホ幅を確かめる。そのうえで自分でも原文からモデルまでゆっくり動かし、見出しを順に読んで話になっているか、要約がきちんと着地しているかを見る。
4. **渡す。** パスと使い方を伝える。
   - 開くと自動で再生が始まる。▶（またはSpace）で原文から要約まで再生してモデルに戻る。ゲージのつまみをドラッグすると部品が動く様子が見え、ラベルをクリックする（または←→）と即座に切り替わる。モデルでは↑↓で表現を切り替える。
   - カーソルを重ねると原文とノートがつながり、クリックすると反対側がそこまでスクロールする。ヘッダーの light / dark / dopa でテーマを切り替える。
   - dopa では ▶ がショーになる。動画にするなら、ページを全画面にして ▶ を押し、画面録画する。

   ユーザーがローカルのファイルを開けない環境（リモート実行など）では、Artifactとして公開する。公開前に `artifact-design` スキルを読み込む。

## しないこと

- **見た目のためにモデルを直さない。** ノートが分かりにくいなら、ノートを直す。見せ方だけの問題なら、ビューオプションを変える。
- **ページに原文の解析を足さない。原文ごとにページを書き起こさない。** ページが表示するものはすべてモデルから来て、テンプレートが実装である。テンプレートを改良したときは、[references/transform-view.md](references/transform-view.md) もテンプレートに合わせる。
- **コミットはユーザーに求められたときだけ行う。**
