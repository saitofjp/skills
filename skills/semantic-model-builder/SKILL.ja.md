# Semantic Model Builder

> 英語版 [SKILL.md](SKILL.md) と同じ内容の日本語版。

Semantic Modelは、注意深い読み手が文章から理解したことを書き出したものである。3つの部分からなる。

- **文章が扱っている対象：** 文章が論じている物事・数量・主体・出来事と、それぞれの状態と変化（いつ、どうなるか）
- **それらがどう作用し合うか：** 仕組み
- **著者が何を結論しているか、その根拠は何か**

どの部分も、根拠となる原文の言葉を指す。

モデル化するのは**文章**ではなく、文章が扱う**対象**である。文章は証拠である。文・接続語・節は、著者が理解を届けるための容れ物であって、理解そのものではない。句ごとにNodeを作り、「こうしたもとで」ごとにRelationを作り、文書の章をNodeにしたモデルは、言葉を写しただけで、理解する仕事を読み手に残している。

**試験。** モデルを結論から理由へとたどって読み上げる（`semantic_model.py outline` がこれを行う）。原文を読んでいない人に、原文より分かりやすく説明できていなければならない。何が起きているか、何がそれを動かしているか、何が導かれるか。原文を1文ずつ言い換えたように聞こえたら、下の手順1からやり直す。

出力はJSONファイル1つで、[references/semantic-model.md](references/semantic-model.md) の契約に従う。契約が決めているのは、表示側に必要なことだけである。それ以外は判断に任せる。

[`semantic-model-viewer`](../semantic-model-viewer/SKILL.ja.md) がこのファイルをHTMLで表示する（Two PaneとFormation）。

## 入力

- 原文は引数で受け取る（貼り付けたテキスト／ファイルパス／URL）。無ければ聞いてから始める。
- 数文から約1万字（10ページ前後のレポート）までは1つのモデルに収まる。それより長いときは、どの部分をモデル化するか聞くか、部分ごとにモデルを作る。
- 原文はそのまま出力フォルダの `source.txt` に保存する。保存先はユーザー指定があればそこ、無ければ `.semantic/<YYYYMMDD>-<slug>/`。コミットはユーザーに求められたときだけ行う。
- PDFやWebページからは本文をそのまま取り出す。取り除くのは抽出で混ざったものだけ（ページ番号、柱、脚注番号、文の途中の改行。日本語なら空白を入れずにつなぐ）。取り除いたものは `metadata.source` に書く。言い換えない。spanはこのテキストを指す。

## この順で作る

先に理解し、原文への対応付けは最後にする。文から始めると、文のモデルができる。

1. **何を言っている文章かを言う。** 全文を読む。そのあと原文を見ずに、何を結論していて、なぜそう言えるのかを数行で書く。モデルが語れなければならないのはこれである。報告用に取っておき、モデルには入れない。
2. **対象を挙げる。** 文章が論じている物事・数量・主体・出来事・仕組みを挙げる。原文の言い回しがいくつあっても、読み手が呼ぶ名前で1つずつにする。「原油高」「原油価格上昇」「原油価格の下落」のどれで書かれていても、原油価格は1つのNodeである。
3. **対象ごとに状態を付ける。** いまどうなっていて、どう変わるのか、いつのことか。「足もと：２％に近づく」「2026年度後半〜2027年度：目標と整合的な水準」「リスク：２％を超えて上振れ」。状態は対象に属する（`states`）。新しいNodeにしない。設備投資について3つの時期を述べた3つの文は、状態を3つ持つ1つのNodeになる。
4. **つなぐ。** 対象どうしがどう作用するかを、対象の言葉で書く。押し上げる、押し下げる、引き起こす、可能にする、打ち消す、必要とする。向きを持たせ、符号があるものには `polarity` を付ける。Relationは、それが何をするかで名付ける。接続語（「こうしたもとで」「踏まえると」「したがって」）は、関係がある証拠であって、関係の名前ではない。
5. **著者の結論を書く。** 文章が論じて示す見通し・判断・リスク・決定を、少数の主張Nodeにする。それぞれを、それを支えるものとつなぐ。主たる結論には `"role": "conclusion"` を付ける。
6. **根拠を付ける。** ここで初めて原文に戻る。すべての要素と状態にspanを付ける。言い換えや指示語も含めて、言及ごとに1つ。どう得たかを `provenance` に書く。
7. **試験する。** outlineを、初めて読むつもりで読む。直すのはモデルであって、outlineではない。

## 粒度

Nodeの大きさは文章の規模で変わる。情報は細切れの中にだけあるのではない。2文なら、単位は語や句である。10ページのレポートなら、そのレポートが論じている対象と、それが下す少数の主張である。仕組みや論証は、部分を子（`parent`）に持つ大きなNodeにしてよい。`parent` は対象の中の全体と部分に使う（物価指数とその構成要素、政策パッケージとその施策、仕組みとその環）。文書の章には使わない。

## 入れないもの

- **文書そのもの：** 節、見出し、「第１の柱」、「概要で述べたとおり」。必要なら `metadata` に入れる。
- **文章についての関係：** 「説明する」「言及する」「点検する」。
- **言い直し：** 概要と本文で同じ主張をしているなら、spanを2つ持つ1つの主張である。
- **すべての文：** 前置き・留保・繰り返しには、それ自身の要素は要らない。全文に触れているモデルは、丁寧なのではなく疑わしい。

## 変えないこと

- **原文にない事実を足さない。** 自分の知識は読むために使うものであって、出典ではない。モデルが主張するものは原文から来ていなければならない。それ以外は、根拠を示した `inferred` にするか、入れない。
- **推論を明示として扱わない。** 迷ったら `inferred`。原文が2通りに読めるなら `uncertain` にし、両方の読みを `note` に書く。
- **見栄えのために意味を落とさない。** 原文が重要だと言っているものは、モデルに入っている。
- **すべて原文に戻れる。** `explicit` の要素と状態はspanを持つ。それ以外はspanか `derivedFrom` を持つ。

## ツールを使った手順

ツールはこのスキルのフォルダにある `scripts/semantic_model.py`（Python 3、標準ライブラリのみ）。

1. `python3 scripts/semantic_model.py sentences source.txt`：文に番号を振る。引用の位置を探すために使う。モデルを組み立てる道筋にはしない。
2. `draft.json` を書く。`nodes`（`states` つき）・`relations`・`metadata` を書き、`sourceText` は書かない。spanは引用で書く：`"sourceSpans": ["原油高"]`。同じ引用が複数回出るときは文番号を添える：`{"quote": "原油高", "sentence": 3}`。長い文章は、同じidを使い回す複数のファイルに分けて書いてよい。統合される。
3. `python3 scripts/semantic_model.py resolve draft*.json --source source.txt -o model.json`：下書きを統合し、引用をオフセットに変え、契約を検証する。エラーがある間は何も書き出さない。
4. `python3 scripts/semantic_model.py outline model.json`：試験。モデルを結論から読み上げ、言葉をモデルにしている兆候を挙げる（関係の名前が接続語、文章についての関係、文書構造のNode、1つの対象が複数のNodeに分裂）。「この順で作る」の手順1で書いた数行と見比べる。
5. `python3 scripts/semantic_model.py summary model.json`：根拠を点検する。すべての要素と状態を引用つきで並べ、明示されていないものと、どのspanも触れていない文を挙げる。触れていない文ごとに、モデルに欠けていることを言っていないか考える。ほとんどは前置きか繰り返しである。
6. **報告する。** `model.json` のパス、手順1の数行、outline、provenance別の件数、原文に明示されていないものの一覧（ユーザーが確認すべきもの）を伝える。表示には `semantic-model-viewer` を勧める。
