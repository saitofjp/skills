# aidoc-less-is-more

目的に必要な情報を選び、要素ごとに重要度を設定して、構造と書き方を決め直す。結果として無駄が消える。

| フェーズ | ステップ | その工程の判定 |
|---|---|---|
| **目的の確認** | 1〜2 | この文書は誰に何をさせるためのものか |
| **文の整形** | 3 | その文を消して、読み手の動作が変わるか |
| **構造の把握** | 4 | 一言に揃えたとき、同じことを2回言っていないか |
| **重要度の設定** | 5〜8 | どちらがより核心に近いか |
| **情報の削除** | 9〜10 | これが無いと読み手は間違うか |
| **推敲** | 11 | 頭から読んで、意味が確定していくか |

## 目的の確認

### ステップ 1: 目的と読み手を決める

**まず全文を読む。** 部分だけ見て書き換え始めると、離れた場所にある重複も、結論が後ろにあることも見えない。

その文書が何のために書かれ、誰が読むのかを確認する。目的が変われば核心は入れ替わる — 同じ障害報告でも、再発防止を決める文書なら対策が核心で経緯は裏付けに下がり、原因を共有する文書なら経緯そのものが核心になる。文書の種類で決めない。読み取れなければユーザーに確認する。

**読み手が実行時に何にアクセスできるかも、ここで決める。** 読み手が自分で取れる情報は、文書に書く価値が下がる。

### ステップ 2: 意味単位に分解する

「1つのことを言っている塊」に分け、それぞれが何を言っているかを**一言で書き出す**。段落単位とは限らない。一言で言えないなら、意味が混ざっている（分ける）か、文が重い。

## 文の整形

### ステップ 3: 装飾を落とし、読めない文を読み解く

構造を見る前に、一文ずつの表現を整える。読めるようになったら止め、仕上げない。

**落とす。** 装飾とは、書き手が「ここは重要だ」と表明しているだけの文である。判定は「**その文を消して、読み手の動作が変わるか**」。変わらないなら装飾。

具体的な失敗を名指ししている文は装飾ではない。「ここを飛ばすと以降がすべてぶれる」は装飾、「部分だけ見て書き換え始めると、離れた場所にある重複が見えない」は避けるべき動作を伝えている。

**whyが判定を通ったときは、理由の説明ではなく禁止に変換し、違反が起きる場所へ移す。** 破りたくなる工程に「ここではやらない」と置く。

語の単位でも落とす。ここで落とすのは**文と語**である。

**読み解く。** 残った文のうち、頭から読んで意味が確定しないものを扱う。読み手に仕事をさせている3つの機構 — **計算**（入れ子の否定で結論の向きを計算させる）、**保持**（長い修飾を係り先が来るまで抱えさせる）、**復元**（名詞化で誰が何をするかを組み直させる）。

**否定を畳むときは向きを確認する。** 「負荷の増大を招かないとは言えない」は「増えることがある」であって「増えない」ではない。

**ここでは足さない。**

装飾の類型と、3機構に当たる言い回しの一覧 → [references/diagnostics.md](references/diagnostics.md)

## 構造の把握

### ステップ 4: アウトライン化する

一言を並べ、文書全体の構造を俯瞰する。**並べるのは原文ではなく、ステップ2で書いた一言である。** 原文のまま並べると、同じ内容を別の言い回しで2回書いていても、別のことに見えて生き残る。

## 重要度の設定

### ステップ 5: 段階を割り当てる

段階に名前や固定の基準を与えない。目的に照らして要素同士を**相対比較**し、「どちらがより核心に近いか」で順位を付ける。最上位は「これだけ読めば伝わる」もの、最下位は落としても核心の理解が変わらないもの。間に何段置くかは文書による — 増やすほど差は見えなくなる。

外しやすいのは、見た目と段階が逆になっている要素である。**補足に見えて核心** — 制約・前提条件は控えめに紛れ込んでいても、落とせば読み手が誤る。**核心に見えて補足** — 見出し・コードブロック・太字・分量は、重要さの証拠ではない。

### ステップ 6: 重要度の差を検証する

**最上位に置いた要素だけを、順番どおりに取り出して読む。** それが読み手の受け取る冒頭である。

問いは「**ここで読むのをやめた読み手が、誤った判断をしないか**」。読み進めれば分かる、では冒頭が成立していない。

- **動けない** → 最上位が足りない。下から1つだけ引き上げる
- **ほとんどの要素が最上位にある** → 重要度の差がない。「これだけ読めば伝わる」に本当に残るものへ絞り直す
- **最上位以外がすべて最下位** → 差が急すぎる。核心を支える理由が抜けていて、読み手は納得できない
- **最も高い要素が後ろにある** → 前に出す

**量に上限は置かない。** 上の2つで両側から挟めば、その文書での量は決まる。行数や画面で決めない。

**冒頭は要約ではない。** 冒頭のために新しく文を書き起こしているなら、それは本文の要約であり、同じことを二度言う文書になる。核心の文そのものを上に移し、本文からは消す。

### ステップ 7: 文章で説明するか、構造で示すか

**見出し・並列・順序によって理解できる情報は、文章で逐一説明せず構造に移す。** 並ぶ項目は箇条書きへ、順序は番号付きリストへ、対応関係は表へ。「なお」「また」「ただし」の連打は、構造で示すべき関係を文章で肩代わりしている。

削れる言い回しの一覧 → [references/diagnostics.md](references/diagnostics.md)

### ステップ 8: 再構成する

- **高い** → 一文で独立させ、前に出す。修飾を削って言い切る
- **中間** → 上位の要素にぶら下げる。1主張1説明にまとめ、言い換えの重複を統合する
- **低い** → 主張から分離し、注記か構造（表・リスト）へ移す

**段階を強調記法で表現しない。** 太字を増やすほど、文書全体の重要度の差は小さくなる。**ここで文を仕上げない。**

## 情報の削除

### ステップ 9: 落とす候補を洗い出す

**ここでは守りを考えない。** 「でもこれは必要かもしれない」は次の照合でまとめて判断する。落とす理由が言えるものは全部挙げる。

- **読み手はそれを自分で取れるか** — 実行時にアクセスできるもの（コード、設定、別ドキュメント）の転記は情報ではなく複製である。参照先を指せば足りる。しかも転記は元が変わると古くなるので、残す方が有害になりうる
- **文書が自分で「重要でない」と申告していないか** — 「（任意）」「参考」「ちなみに」
- **判定手順があるのに例示が並んでいないか** — 基準を示したなら、事例の列挙は要らない
- **同じ値・同じ事実が2箇所にないか** — どちらを正とするか決めて、他方を消す
- **理由の説明が結論と同じ分量ないか** — 1文で足りることに1段落使っていないか
- **文書が宣言したスコープの外か** — 判定方法と「別を見よ」の一行だけ残す
- **前提・引数・環境を先に全部書いていないか** — 読んでから聞けるものは、書かなくてよい

**その文書に効く問いを都度見つける。** 最初の問いが効くかどうかは、読み手が実行時に何にアクセスできるかによる。

### ステップ 10: 保護対象と照合する

候補を次の3つと照合する。**当たらないものは落とす。**

- **誤動作を招くもの** — 制約、前提条件、禁止事項、順序依存、間違えやすい類似物の区別
- **他に情報源がないもの** — 事故の実例、症状と原因の対応、明文化されていない慣習
- **目的そのもの** — 文書の核心

基準は「**これが無いと読み手は間違うか**」。「あった方が親切か」では判断しない。

**保護対象をこの3つより増やさない。** 増やせば全部が保護対象になり、この工程が機能しなくなる。

## 推敲

### ステップ 11: 仕上げる

**対象は再構成で生まれた文である** — 統合してできた文、前に出した文、構造に移した見出しやセル。計算・保持・復元の3機構を当てる。

足さない（説明を足すと、落としたものが別の形で戻る）。重要度の差を壊さない（構造に逃がした要素を散文へ戻さない）。装飾を作らない（再構成の途中で書き足していないか）。

## 評価基準

成否は**削った文字数ではなく、1回の読解で得られる情報量が増えたか**で判断する。

- **冒頭だけで成立しているか** — そこで読むのをやめた読み手が、正しく動けるか
- **重要度の差が見て分かるか** — 見出しも項目も全部が同じ大きさ・同じ形なら、差は無い
- **無駄が残っていないか** — 落とす工程の問いに当てはまるのに残っている要素
- **装飾が残っていないか** — 消しても読み手の動作が変わらない文
- **情報が落ちていないか** — 保護対象3つ。項目を名指しで数える
- **読解コストが残っていないか** — 一度で意味の取れない文

「無駄が残っていないか」と「情報が落ちていないか」は相反する。**片方だけを見た場合の失敗は、情報落ちより無駄残りの方が起きやすい。**

## 適用範囲

`docs/` 配下のMarkdownに限らず、チャット内の長い説明、PR説明、Issueコメントなど、AIが書いた文章全般に使える。ファイルなら書き換えた上で構造の観点から説明し、チャット内なら再構成した文章を出力する。

報告には**落としたものとその理由**を含める。構造をどう直したかだけを報告すると、落とす工程を飛ばしたことが表に出ない。文字数の増減は補助情報にとどめ、成果として提示しない。
