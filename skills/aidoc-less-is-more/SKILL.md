# aidoc-less-is-more

ドキュメントを、"Less is More" に従って再構成する。

"Less is More" はもともとデザインの考え方である。余分な装飾と不要な複雑さを取り除くと、見た目の美しさだけでなく、使いやすさと理解のしやすさが上がる。

**ドキュメントもデザインが必要。** 目的に必要な情報を選び、要素ごとに重要度を設定して、構造と書き方を決め直す。**「削る」のではなく「デザインする」。その結果として無駄が消える。**

| フェーズ | ステップ | その工程の判定 |
|---|---|---|
| **目的の確認** | 1〜2 | この文書は誰に何をさせるためのものか |
| **文の整形** | 3 | その文を消して、読み手の動作が変わるか |
| **構造の把握** | 4 | 一言に揃えたとき、同じことを2回言っていないか |
| **重要度の設定** | 5〜8 | どちらがより核心に近いか |
| **情報の削除** | 9〜10 | これが無いと読み手は間違うか |
| **推敲** | 11 | 頭から読んで、意味が確定していくか |

**中間出力** — 印のある地点で、その時点の全文と直前の工程の判断を書き出す。以降の工程は、書き出したものに対して行う。自分が次の工程で使うための出力なので、ユーザーの返答は待たない。

## 目的の確認

### ステップ 1: 目的と読み手を決める

**まず全文を読む。** 部分だけ見て書き換え始めると、離れた場所にある重複も、結論が後ろにあることも見えない。

その文書が何のために書かれ、誰が読むのかを確認する。文書の種類で決めない。読み取れなければユーザーに確認する。何を理解／判断／実行してほしいか。

### ステップ 2: もっとも大切な結論を決める

以降の重要度は、すべてこの一文との距離で決まる。

## 文の整形

### ステップ 3: 装飾を落とし、読解コストを下げる

一文ずつの表現を整える。

**消しても読み手の動作が変わらない文は落とす。**

- **避け方を示さない警告** — 「ここを飛ばすと以降がすべてぶれる」「そこを潰すのが一番効く」。悪化を抽象的に述べるだけで、読み手は何も避けられない
- **結論の言い換えでしかない理由** — 「太字を増やさない。増やすとコントラストが下がるからである」。理由が結論の否定形になっていて、情報が増えていない
- **基準のない注意書き** — 「慎重に判断する必要がある」「注意して進めること」。判断の基準を与えないなら、構えさせて終わる

**頭から読んで意味が確定しない文は直す。**

| 機構 | 症状 | 例 |
|---|---|---|
| **計算させている** | 否定や条件が入れ子になり、結論の向きを読み手に計算させる | 「〜ないわけではない」「〜でない限り〜しないことはない」「〜がないとは言い切れない」 |
| **保持させている** | 被修飾語の前に長い修飾が積まれる、一文に複数のメッセージが入る | 「前回の調査で判明した設定ミスに起因する断続的な接続断の再発を防ぐための恒久対策」 |
| **復元させている** | 動作が名詞に固まる、「の」が3つ以上連なる | 「〜の実現」「〜への寄与」「〜の適用による改善」「機能の設定の変更の手順」 |

**否定を畳むときは向きを確認する。** 「負荷の増大を招かないとは言えない」は「負荷が増えることがある」であって「負荷が増えない」ではない。畳んで意味が変わるなら、畳まずに残す。

※むかしにあった日本語特有の表現を削除する適なのをgitから復活させたい

**中間出力** — 整形後の全文と、目的・読み手・結論

## 構造の把握

### ステップ 4: 意味単位に分解して、役割でアウトライン化する

「1つのことを言っている塊」に分け、その塊の役割を**一言で書き出す**。段落単位とは限らない。それらを並べ、文書全体の構造を俯瞰する。

同じことを別の言い方で書いていないか。

```
Why
What
How
Example
Constraint
```

```
主情報
副情報
参照情報
```

## 重要度の設定

### ステップ 5: 重要度の数値化

要素同士を**相対比較**し、「どちらがより結論に近いか」で順位を付ける。最上位は「これだけ読めば伝わる」もの、最下位は落としても結論の理解が変わらないもの。間に何段置くかは文書による。

**補足に見えて核心** — 制約・前提条件は控えめに紛れ込んでいても、落とせば読み手が誤る。
**核心に見えて補足** — 見出し・コードブロック・太字・分量は、重要さの証拠ではない。

### ステップ 6: 重要度の差を検証する

**最上位に置いた要素だけを、取り出して読む。** 「**ここで読むのをやめた読み手が、誤った判断をしないか**」。読み進めれば分かる、では冒頭が成立していない。

- **動けない** → 最上位が足りない。下から1つだけ引き上げる
- **ほとんどの要素が最上位にある** → 重要度の差がない。「これだけ読めば伝わる」に本当に残るものへ絞り直す
- **最上位以外がすべて最下位** → 差が急すぎる。結論を支える理由が抜けていて、読み手は納得できない
- **最も高い要素が後ろにある** → 前に出す

**量に上限は置かない。** 上の2つで両側から挟めば、その文書での量は決まる。行数や画面で決めない。

**冒頭は要約ではない。** 冒頭のために新しく文を書き起こしているなら、それは本文の要約であり、同じことを二度言う文書になる。

**中間出力** — 要素ごとの重要度と、最上位だけを取り出したもの

### ステップ 7: 構造へ移す／削る言い回し

**構造で伝えられるものを文章で説明していないか。** 見出し・並列・順序によって理解できる情報は、文章で逐一説明せず構造に移す。

#### 省略で伝わる関係は書かない

主語・助詞・文脈で伝わるものを明示すると説明過剰になる。

```
本機能では、ユーザーが問題を選択することができます
→ 問題を選択できる
```

#### 並列・順序は構造で示す

| 文章で書いているもの | 移す先 |
|---|---|
| 「まず〜し、次に〜し、最後に〜する」 | 番号付きリスト |
| 並ぶ項目を「〜や〜、および〜」で連ねる | 箇条書き |
| 「Aの場合はX、Bの場合はY、Cの場合はZ」 | 表 |
| 「〜だが、一方で〜」の対比 | 表の2列 |

#### 説明的な前置きを削る

削っても意味が変わらないことが多い。

- 「〜については」「〜における」「〜に関して」
- 「〜という観点で」「〜の観点から」
- 「〜を行う」「〜を実施する」（→ 動詞1語に戻す）

#### 接続の実況をやめる

「なお」「また」「ただし」「そして」の連打は、構造で示すべき関係を文章で肩代わりしている。段落を分ける、見出しを立てる、リストにする。

#### 形式が保証しているwhyを書かない

番号・見出し・禁止リストがすでに読み手を動かしているなら、その理由を文章で説明しても読み手の動作は変わらない。次のステップで説明することを手前で予告するのも同じ。

### ステップ 8: 再構成する

- **高い** → 一文で独立させ、前に出す。修飾を削って言い切る
- **中間** → 上位の要素にぶら下げる。1主張1説明にまとめ、言い換えの重複を統合する
- **低い** → 主張から分離し、注記か構造（表・リスト）へ移す

**段階を強調記法で表現しない。** 太字を増やすほど、文書全体の重要度の差は小さくなる。

**中間出力** — 再構成後の全文。まだ何も落としていない

## 情報の削除

### ステップ 9: 落とす候補を洗い出す

なくても意味が変わらないものはないか。次で照合するために、落とす理由が言えるものは全部挙げる。

- **読み手はそれを自分で取れるか** — 実行時にアクセスできるもの（コード、設定、別ドキュメント）の転記は情報ではなく複製である。参照先を指せば足りる。しかも転記は元が変わると古くなるので、残す方が有害になりうる
- **文書が自分で「重要でない」と申告していないか** — 「（任意）」「参考」「ちなみに」
- **判定手順があるのに例示が並んでいないか** — 基準を示したなら、事例の列挙は要らない
- **同じ値・同じ事実が2箇所にないか** — どちらを正とするか決めて、他方を消す
- **理由の説明が結論と同じ分量ないか** — 1文で足りることに1段落使っていないか
- **文書が宣言したスコープの外か** — 判定方法と「別を見よ」の一行だけ残す
- **前提・引数・環境を先に全部書いていないか** — 読んでから聞けるものは、書かなくてよい

**その文書に効く問いを都度見つける。** 最初の問いが効くかどうかは、読み手が実行時に何にアクセスできるかによる。

### ステップ 10: 保護対象と照合する

候補を次の3つと照合する。**当たらないものは落とす。**

- **誤動作を招くもの** — 制約、前提条件、禁止事項、順序依存、間違えやすい類似物の区別
- **他に情報源がないもの** — 事故の実例、症状と原因の対応、明文化されていない慣習
- **目的そのもの** — 文書の核心

基準は「**これが無いと読み手は間違うか**」。「あった方が親切か」では判断しない。

**保護対象をこの3つより増やさない。** 増やせば全部が保護対象になり、この工程が機能しなくなる。

「削除」ではなく「適切な場所・形式へ移す」。

## 推敲

### ステップ 11: 確認

成否は**削った文字数ではなく、1回の読解で得られる情報量が増えたか**で判断する。

- **冒頭だけで成立しているか** — そこで読むのをやめた読み手が、正しく動けるか
- **重要度の差が見て分かるか** — 見出しも項目も全部が同じ大きさ・同じ形なら、差は無い
- **無駄が残っていないか** — 落とす工程の問いに当てはまるのに残っている要素
- **装飾が残っていないか** — 消しても読み手の動作が変わらない文
- **情報が落ちていないか** — 保護対象3つ。項目を名指しで数える
- **読解コストが残っていないか** — 一度で意味の取れない文

報告には**落としたものとその理由**を含める。構造をどう直したかだけを報告すると、落とす工程を飛ばしたことが表に出ない。文字数の増減は補助情報にとどめ、成果として提示しない。
