# Semantic Structure Reconstructor

> 英語版 [SKILL.md](SKILL.md) と同じ内容の日本語版。

文章のモデルは、そこから文章を書き戻せれば十分によい。このスキルは、ユーザーと一緒にモデルをそこまで持っていき、どこまで来たかを示す。塊どうしの関係をはっきりさせ、モデルだけから文章を書き戻し、原文と塊ごとに並べ、違いを1つずつ手直しか質問に変える。

```
原文 ──builder──▶ モデル ──このスキル──▶ もう一度、文章
                    ▲                        │
                    └──── 手直し・質問 ◀─────┘
```

モデルを作るのは [`semantic-structure-builder`](../semantic-structure-builder/SKILL.ja.md)、表示するのは [`semantic-structure-viewer`](../semantic-structure-viewer/SKILL.ja.md)。このスキルは、ユーザーと一緒にモデルを変え、そこから書く。

モデルはあなたのものであると同時にユーザーのものでもある。壊れている所を見つけて提案するのはあなた、決めるのはユーザー。モデルは文章のモデルのままにする。ユーザーが同意した読みも読みであり、それで原文が言っていることが増えるわけではない。

## 文章が戻ってくるために要るもの

- **流れ。** 順に読んだとき、どの塊も、前にあるものから導かれて出てくる。前の塊への線（理由、対比、帰結、例）、それが部分である塊、あるいは原文がただ次へ進むときの `transition`（`ここから争点`）。何もその塊を導いていなければ、書き手は転じ方を推測するしかなく、しばしば外す。これが最初の質問になる。
- **ユーザーが見た線。** 原文が言っていない線は、モデルを作った人の読みである。拠り所の言葉を見せて尋ねる。同意なら `confirmed: true` を付ける。`inferred` のまま変えない。`uncertain` の読みの1つを選んだら、`inferred` にしてその読みを `note` に書く。違うと言われたら、向き・符号・種類・ラベルを直すか、線を消す。
- **メッセージを運ぶ要点。** 塊が言っていることは、見出しと要点に入っていなければならない。数字・条件・時期・主体・理由。ノートが原文の中に置いてきたものは、書き手には戻せない。
- **重み。** 結論・key・一言の要約が、何が大事かを言う。書き戻した文章で重みが別の所にあれば、文章は戻ってきていない。

## ツール

このスキルのフォルダにある `scripts/reconstruct.py`（Python 3、標準ライブラリのみ）。モデルは `scripts/semantic_structure.py`（意味構造の各スキルが共有する契約のツール）で読み、エラーのあるモデルは受け付けない。

- `flow model.json` は、文章を書き戻す順に塊を並べ、それぞれを何が導いているかと、ユーザーと決めるべき質問（Q1、Q2、…）を出す。
- `brief model.json -o brief-1.md` はブリーフを書く。一言の要約に続いて、塊ごとに、見出し・目印・役割・原文での長さ・何が導くか・要点・線を並べ、冒頭に書き方の決まりを置く。原文の言葉は、ノート自身が使っている分しか含まない。`--style "判決文、である調"` で文体を伝えられる。文体は意味ではないので、何も確かめない。
- `compare model.json rebuilt-1.md -o compare-1.md` は、書き戻した段落を塊ごとに原文の一節の下に置き、塊の要点、書き手の `[?: …]` の問い、長さ、そして片方にあってもう片方に無い数字を出す。
  - 原文にあり、ノートのどこにも無い：ノートが落とした。
  - 塊のノートにあり、その段落に無い：書き手が落とした。
  - 書き戻した文章にあり、どちらにも無い：書き手が作った。
  - 書き戻した文章にあり、原文にだけある：書き手は原文を見たのでは？

  数字は手がかりにすぎない。組を読むこと。
- `diff model.before.json model.json` は、変わったもの（塊、要点、線、一言の要約、順序）を出す。
- `--order text` を `flow`・`brief`・`compare` に付けると、ノートの順ではなく、原文で一節が現れる順に書き戻す。3つとも同じ順にする。

モデルを変えるときは `model.json` を編集し、`python3 scripts/semantic_structure.py resolve model.json --source source.txt -o model.json` を実行する。引用と文番号（`"原油価格"`、`{"sentences": [3, 4]}`）をオフセットに変え、契約を検査し、エラーがある間は何も書き出さない。

このスキルは、契約のうちビューアが使わない2つのフィールドを使う。

- 塊の `transition`：線が言っていないとき、その塊がどう導かれるか。
- 塊・要点・線の `confirmed: true`：ユーザーが確かめて同意した。来歴は変えない。

## ファイル

モデルのフォルダで作業する。ふつうは builder が作った `.semantic/<YYYYMMDD>-<slug>/` で、`model.json` の隣に `source.txt` がある（`source.txt` が無ければ、`resolve` はモデル自身の `sourceText` を使う）。コミット済みの作例のように変えてはいけない場所にあるモデルは、先に新しい `.semantic/` フォルダへコピーし、そう伝える。コミットはユーザーに求められたときだけ行う。

| ファイル | 中身 |
|---|---|
| `model.json` | モデル。その場で手直しする。 |
| `model.before.json` | このスキルが変える前のモデル。最初の変更の前に保存する。 |
| `brief-<n>.md` | n回目：書き手に渡したブリーフ。 |
| `rebuilt-<n>.md` | n回目：書き戻した文章。塊ごとに1段落で、それぞれ目印 `<!-- chunk-id -->` の後に置く。目印はHTMLのコメントなので、Markdownとして表示すると見えない。 |
| `compare-<n>.md` | n回目：原文と書き戻した文章を並べたもの。 |

## 手順

1. **モデルを見つける。** ユーザーが文章しか持っていなければ、先に `semantic-structure-builder` でノートを作る。`model.before.json` を保存する。
2. **流れを見せて尋ねる。** `flow` を実行する。塊の並びを数行でユーザーに伝え、続いて質問を出す。
   - 一度に3〜4問、変わるものが大きい順に尋ねる。流れの切れ目、次に線、それから残り。
   - それぞれに、塊の番号と見出し、関わる原文の言葉（短い引用）、あなたの提案と、ほかの読みを添える。選択式で尋ねるツールがあれば使い、提案を先頭に置く。
   - 原文で決まることは尋ねない。自分で直して、そう伝える。
   - ユーザーの言葉で尋ねる。ツールの出力は英語なので、伝えるときに訳す。
3. **答えでモデルを変え**、`resolve` し、流れの何が変わったかを見せる。新しい線には拠り所の言葉を付けるか、`inferred` にして誰の読みかを `note` に書く。流れに切れ目が無くなるか、ユーザーが文章を見たいと言うまで、2に戻る。
4. **原文を見ずに書き戻す。** `brief` を実行し、原文を読んでいない書き手にブリーフを渡す。書き手が原文を読んでいると、モデルの穴を記憶で埋めてしまい、確かめたことにならない。
   - いちばんよい書き手は、新しいサブエージェント。プロンプトにはブリーフだけを入れ（原文も、モデルのファイルも、この会話も入れない）、返事として文章を書いてもらう。返事を `rebuilt-<n>.md` に保存する。
   - サブエージェントを使えないときは、ブリーフだけから自分で書き、書き手が原文を読んでいたので確かめ方が弱いことを報告で伝える。
   - 書き戻した文章を原文に合わせて直さない。それはモデルが運べたものを示している。直すと、それが見えなくなる。
5. **比べる。** `compare` を実行し、すべての組を読み、違いを仕分ける（下記）。主な違いを、原文の言葉と書き戻した言葉を並べてユーザーに見せ、モデルの側の違いについて尋ねる。
6. **3からもう一周する。** どの塊も戻ってくる（メッセージ、要点、前の塊からの転じ方が、言葉は違っても戻る）か、ユーザーが満足するか、残ったものが意味ではなくなったら止める。たいてい2〜3周で足りる。何が残ったか、なぜかを伝える。

## 比べ方

組は言葉ではなく意味で判断する。モデルを変える前に、その違いがモデルの側か、書き手の側かを決める。

| 見えるもの | どちらの側か | すること |
|---|---|---|
| **落ちた：** 原文は言い、書き戻した文章は言っていない。 | ノートに無ければモデルの側。ノートにあれば書き手の側。ただし要点の書き方が別の意味に読めるなら、モデルの側。 | 大事かどうかユーザーに尋ね、大事なら要点を足す。誤解を招く要点は書き直す。 |
| **足された：** 書き戻した文章が、原文の言っていないことを言う。 | ノートが言っていればモデルの側（言い過ぎの見出し、はっきり書かれてしまった推論の線）。そうでなければ書き手の側。 | 見出し・要点・線を直す。 |
| **転じ方が違う：** 塊が前の塊から原文と違う形で続く。原文が「しかし」の所で「だから」になる。 | モデルの側。線が無い、向きが逆、符号が違う、書きようがないほど種類があいまい。 | ユーザーと線をはっきりさせる。このスキルの目的はここにある。 |
| **重みが違う：** 小さなことが大きく、またはその逆。 | モデルの側。結論、key、一言の要約。 | 何がいちばん大事かユーザーに尋ねる。 |
| **問われた：** 書き戻した文章の `[?: …]`。 | モデルの側。 | ユーザーへの質問、または要点にする。 |

数えないもの：言葉づかい、文の長さ、リズム、塊の中での要点の順序、ノートがわざと落としたもの（事件番号、証拠の引用、定型文）。ユーザーがそれも戻したいなら、要点として足す。

## 報告

- `model.json`、最後の `rebuilt-<n>.md` と `compare-<n>.md` のパス。
- モデルで変わったこと（`diff`）を数行で。どれがユーザーの判断だったかも。
- 塊ごとに、まだ戻ってこないものとその理由。すべて戻ったなら、そう言う。
- 書き戻した文章そのもの。短ければ全文を、長ければ最初のいくつかの塊を。
- そのうえで、手直ししたモデルを見るために `semantic-structure-viewer` を勧める。

## してはいけないこと

- **モデルを一から作り直さない。** 質問と比較が示したものを変える。塊の分け方そのものが違うなら、そう伝えて `semantic-structure-builder` を勧める。
- **書き手に原文を見せない。** 書き戻した文章を原文で直さない。
- **原文に言わせない。** 原文が言っていないことをユーザーがモデルに入れたいなら、`inferred` にして、ユーザーのものだと `note` に書く。比較では、それが足されたものとして出る。それでよい。ユーザーが言ったからといって `explicit` にはしない。
