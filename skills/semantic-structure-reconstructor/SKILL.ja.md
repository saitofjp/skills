# Semantic Structure Reconstructor

> 英語版 [SKILL.md](SKILL.md) と同じ内容の日本語版。

文章を、その意味構造から再構築する。モデルは、文章が何を意味しているかを言っている。塊、それぞれが言っていること、塊どうしの効き方、全体が行き着くところ。それをユーザーと一緒に、関係がはっきりするまで見直し、その流れで文章を書き直す。中身は同じまま、どの塊もあるべき所に置かれ、どのつなぎも言葉になる。

```
原文 ──builder──▶ モデル ──ユーザーと手直し──▶ 設計図 ──▶ 再構築した文章
```

モデルが設計図になる。順序・つなぎ・重みはモデルから、事実と言葉は原文から取る。モデルを作るのは [`semantic-structure-builder`](../semantic-structure-builder/SKILL.ja.md)、表示するのは [`semantic-structure-viewer`](../semantic-structure-viewer/SKILL.ja.md)。このスキルは、ユーザーと一緒にモデルを変え、そこから書く。文章は会話でもよい。builder が会話セッションのノートを作り、このスキルがそれを、会話が行き着いたところをその流れで言う文章にする。

モデルはあなたのものであると同時にユーザーのものでもある。流れが切れている所を見つけて提案するのはあなた、決めるのはユーザー。

## 再構築した文章がすること

- **ノートの流れで進む。** 順に読んだとき、どの塊も、前にあるものから導かれて出てくる。前の塊への線（理由、対比、帰結、例）、それが部分である塊、あるいは原文がただ次へ進むときの `transition`（`ここから争点`）。何もその塊を導いていなければ、文章はなぜそこに来るのかを言えない。書く前にユーザーと決める。
- **つなぎを言葉にする。** 原文が述べている線と、ユーザーが確かめた線は、文章の中で言う。そうすれば、読み手には各部分がなぜそこに来るのかが分かる。原文がほのめかすだけで、誰も確かめていない線は、言わずに順序に運ばせる。`uncertain` なものは決めないままにする。
- **事実を保つ。** ノートの要点はすべて入れ、数字・日付・名前・条件は原文のとおりにする。ノートにも原文にも無いことは足さない。
- **ノートが置いた所に重みを置く。** 結論と key には、必要な分量と位置を与え、key を結論の陰に埋もれさせない。全体は、要約の一言に行き着く。

## ツール

このスキルのフォルダにある `scripts/reconstruct.py`（Python 3、標準ライブラリのみ）。モデルは `scripts/semantic_structure.py`（意味構造の各スキルが共有する契約のツール）で読み、エラーのあるモデルは受け付けない。

- `flow model.json` は、ノートの順に塊を並べ、それぞれを何が導いているかと、ユーザーと決めるべき質問（Q1、Q2、…）を出す。
- `blueprint model.json --style "…" -o blueprint.md` は、文章の設計図を書く。最初に書き方の決まり、次に一言の要約、そして塊ごとに、目印・見出し・役割・原文での長さ・何が導くか・要点・線と、素材としての原文の一節を並べる。`--style` は、誰のための文章で、どう読ませるか（形・文体・長さ）を伝える。設計図に入れ、モデルには入れない。
- `check model.json draft.md -o check.md` は、下書きの段落を塊ごとに、その要点と原文の一節と並べる。欠けている塊や順序の違う塊、塊のノートにあるのに段落に無い数字、ノートにも原文にも無い数字、残っている `[?: …]`、長さを出す。数字は手がかりにすぎない。段落を読むこと。
- `export draft.md -o reconstructed.md` は、目印を外した文章を書き出す。`[?: …]` が残っていれば警告する。
- `diff model.before.json model.json` は、モデルで変わったもの（塊、要点、線、一言の要約、順序）を出す。

モデルを変えるときは `model.json` を編集し、`python3 scripts/semantic_structure.py resolve model.json --source source.txt -o model.json` を実行する。引用と文番号（`"原油価格"`、`{"sentences": [3, 4]}`）をオフセットに変え、契約を検査し、エラーがある間は何も書き出さない。

このスキルは、契約のうちビューアが使わない2つのフィールドを使う。

- 塊の `transition`：線が言っていないとき、その塊がどう導かれるか。
- 塊・要点・線の `confirmed: true`：ユーザーが確かめて同意した。来歴は変えないが、文章ではそれを言ってよくなる。

## ファイル

モデルのフォルダで作業する。ふつうは builder が作った `.semantic/<YYYYMMDD>-<slug>/` で、`model.json` の隣に `source.txt` がある（`source.txt` が無ければ、`resolve` はモデル自身の `sourceText` を使う）。コミット済みの作例のように変えてはいけない場所にあるモデルは、先に新しい `.semantic/` フォルダへコピーし、そう伝える。コミットはユーザーに求められたときだけ行う。

| ファイル | 中身 |
|---|---|
| `model.json` | モデル。その場で手直しする。 |
| `model.before.json` | このスキルが変える前のモデル。最初の変更の前に保存する。 |
| `blueprint.md` | 文章の設計図。 |
| `draft.md` | 書いている途中の文章。塊ごとの段落を、その目印 `<!-- chunk-id -->`（1行に単独で置く）の後に書く。 |
| `check.md` | 設計図と照らし合わせた下書き。 |
| `reconstructed.md` | 目印を外した、再構築した文章。ユーザーに渡すもの。 |

## 手順

1. **モデルを見つける。** ユーザーが文章や会話しか持っていなければ、先に `semantic-structure-builder` でノートを作る。`model.before.json` を保存する。はっきりしなければ、誰のための文章で、どう読ませたいかを尋ねる。原文と同じ読み手向けか、もっと平易にか、地の文か見出しつきか、どのくらいの長さか。それが `--style` になる。
2. **ユーザーと流れを決める。** `flow` を実行する。塊の並びを数行でユーザーに伝え、続いて質問を出す。
   - 一度に3〜4問、文章を大きく変えるものから尋ねる。流れの切れ目、次に線、それから残り。
   - それぞれに、塊の番号と見出し、関わる原文の言葉（短い引用）、あなたの提案と、ほかの読みを添える。選択式で尋ねるツールがあれば使い、提案を先頭に置く。
   - 順序も決める。文章はノートの順に進む。ユーザーが別の順（たとえば結論を先に）を望むなら、`nodes` の中で塊を動かし（部分は親と一緒に動く）、どの塊もまだ導かれているかを確かめる。
   - 何を落とすかも決める。文章はノートが運ぶものを運ぶ。何かを落とすなら、ノートから外す。
   - 原文で決まることは尋ねない。自分で直して、そう伝える。
   - ユーザーの言葉で尋ねる。ツールの出力は英語なので、伝えるときに訳す。
3. **答えでモデルを変え**、`resolve` し、流れの何が変わったかを見せる。原文が述べていない関係をユーザーが決めたら、`inferred` かつ `confirmed` にして、ユーザーの読みであることを `note` に書く。`flow` に質問が残らなくなるか、ユーザーが文章を見たいと言うまで、2に戻る。
4. **設計図を作る。** `blueprint` を実行する。
5. **`draft.md` を書く。** 設計図に従い、塊ごとに順に書く。つなぎはユーザーが決めたことで決まるので、自分で書く。各塊を書く前に、何がそれを導くかを読み、段落をそのつなぎで始める。事実は素材から取り、原文の文がすでにうまく言っているならそのまま使う。ノートにも素材にも無いものが要るときは `[?: 足りないもの]` と書いて先へ進む。
6. **確かめる。** `check` を実行し、すべての段落をその塊と照らして読む。メッセージがはっきりしているか、要点がすべて入っているか、線のとおりに入ってきているか、重みは合っているか、何も足していないか。書き方のせいなら下書きを直す。つなぎが書けなかった所や `[?: …]` を残した所は、モデルのせいである。ユーザーに尋ね、モデルを直し、その塊を書き直す。
7. **書き出す。** `export` を実行し、文章をユーザーに見せる。

## 報告

- `reconstructed.md` のパスと、文章そのもの。短ければ全文、長ければ冒頭。
- モデルで変わったこと（`diff`）を数行で。どれがユーザーの判断だったかも。原文がほのめかすだけだったのに、文章では言葉にしたつなぎを挙げる。
- 残っていること、とその理由。
- そのうえで、手直ししたモデルを見るために `semantic-structure-viewer` を勧める。

## してはいけないこと

- **中身を足さない。** 中身は同じで、流れがはっきりするだけ。当たり前に見える理由でも、ノートか原文に無ければ入れない。
- **文体をモデルに入れない。** 誰のための文章で、どう読ませるかは、設計図のオプションである。
- **原文に言わせない。** ユーザーが決めた関係はユーザーの読みである。モデルでは `inferred` かつ `confirmed` にし、文章がそれを言葉にしたことを報告で伝える。
- **モデルを一から作り直さない。** 質問が示したものを変える。塊の分け方そのものが違うなら、そう伝えて `semantic-structure-builder` を勧める。
