# クイズアプリ リアルタイム対戦 調査まとめ

調査日: 2026-10-17
対象: React SPA（Vercel でホスティング）＋ Supabase（DB・認証）

## 0. 目的と判断の基準

- **主目的: 不正をさせないこと**
  - 相手の答えが見えないこと
  - タイマーをいじれないこと
- 前提: 個人開発なので、管理するサービスを増やさず、費用はできるだけ 0 円にしたい

この文書の選択はすべて「上の2点を確実に守れるか」を最優先にし、次に「運用が楽か」「費用」の順で判断しています。

---

## 1. 結論

**Vercel ＋ Supabase の2つだけで、サーバーが判定する（サーバー権威型）対戦を作る。**

| 役割 | 使うもの |
|---|---|
| SPA の配信 | Vercel（今のまま） |
| 認証 | Supabase Auth（今のまま） |
| ゲームの状態・判定 | Postgres の非公開スキーマ `game` ＋ `security definer` の RPC |
| 部屋内への通知 | Supabase Realtime の Broadcast（private channel） |
| 在席・切断の検知 | Supabase Realtime の Presence |
| 放置された試合の片付け | pg_cron（Supabase Cron） |

一番大事な原則は次の1つです。

> **クライアントには、今の時点で見てよい情報しか渡さない。判定・時刻・スコアはすべてサーバーが決める。**

---

## 2. 守るべきものと対策

### 2.1 相手の答えが見えないようにする

| 漏れる経路 | 対策 |
|---|---|
| 回答テーブルを直接読む | テーブルを API に公開しない `game` スキーマに置く。REST API からはテーブルの存在も見えない |
| Realtime の通知 | 回答時の通知は「答えた」という事実だけ。選んだ選択肢は含めない |
| Postgres Changes（テーブルの変更をそのまま配信する機能） | `game` のテーブルを `supabase_realtime` publication に入れない |
| クライアントからの Broadcast 送信 | `realtime.messages` に broadcast の INSERT ポリシーを作らない。送信は RPC 内の `realtime.send()` だけ |
| 答えの教え合い（Discord など） | 選択肢の並びをプレイヤーごとにシャッフルし、回答は選択肢 ID で受け取る |

相手の回答と正誤は、その問題の締切後に初めて両者へ送ります。

### 2.2 問題と正解を先に見られないようにする

- 正解は `game.question_answers` に分けて保存し、読めるのは RPC の中だけにする
- 問題文は `get_current_question` RPC で、**出題時刻を過ぎてから** 1問ずつ返す（全問をまとめて取得させない）

### 2.3 タイマーをいじられないようにする

- クライアントのタイマーは**表示専用**。判定には一切使わない
- 出題時刻 `q_started_at` と締切 `q_deadline` は DB の `now()` から計算して `game.matches` に保存する
- `submit_answer` は `q_started_at <= now() <= q_deadline` のときだけ受け付ける
- 回答時間は `now() - q_started_at` でサーバーが計算する。クライアントから送られた経過時間は使わない
- `(match_id, user_id, q_index)` のユニーク制約で、二重回答と回答の変更を防ぐ
- `advance`（次の問題へ進める処理）は「両者が回答済み」か「締切を過ぎた」ときだけ状態を進める。早く呼ばれても何も起きないので、**呼ぶタイミングをいじっても得をする方法がない**

### 2.4 スコアとレートを改ざんさせない

- スコアとレートはサーバーだけが計算し、試合を確定させる処理と同じトランザクションで更新する
- クライアントから送られた結果は保存しない

### 2.5 実装ミスで穴を開けないための決まり

- 入口は `public` スキーマに置いた少数の RPC だけにする
- すべての RPC の最初に次を確認する
  - `auth.uid()` がこの試合の参加者か
  - 今の試合の状態でその操作をしてよいか
- 同じ試合への処理は、`select ... for update` で試合の行をロックして1つずつ実行する
- `security definer` の関数には必ず `set search_path = ''` を付け、テーブルは `game.matches` のようにスキーマ名付きで書く
- `revoke execute on function ... from anon` で未ログインのユーザーには呼ばせない
- Dashboard の Security Advisor と、後述の確認用スクリプトを、RPC を変えるたびに実行する

### 2.6 防ぎきれないもの

どの構成を選んでも完全には防げないので、影響を小さくする方向で対応します。

| 不正 | 対応 |
|---|---|
| 別の画面で検索する・人に聞く | 制限時間を短くし、回答の速さもスコアに入れる |
| Bot による自動回答 | 回答時間が全件残るので、極端に速い人や正答率が不自然な人を後から検出してランク戦から外す |
| 回線の速さによる差 | 「正解数で勝敗を決め、同点のときだけ時間で比べる」ルールにする |

## 3. 構成の詳細

### 3.1 全体の流れ

```
[A] ──RPC: submit_answer──▶ Postgres（game スキーマ：締切判定・正誤判定・記録）
                               │ realtime.send()
                               ▼
[A][B] ◀──Broadcast "match:{id}"── Supabase Realtime（private channel）
[A][B] ◀──Presence（在席・切断）──
                pg_cron ──▶ 放置された試合を進める・終了させる
```

### 3.2 スキーマ

```sql
create schema game;   -- Dashboard の API 設定で「公開するスキーマ」に追加しない
revoke all on schema game from anon, authenticated;

-- game.matches, game.match_players, game.questions,
-- game.question_answers, game.match_answers, game.match_queue
```

### 3.3 公開する RPC

| RPC | 役割 | 段階 |
|---|---|---|
| `create_match()` | 部屋を作り、招待コードを返す | ステップ1 |
| `join_match(code)` | 2人目として参加する。そろったら最初の出題時刻を決める | ステップ1 |
| `get_current_question(match_id)` | 出題時刻を過ぎていれば、正解を含まない問題文とシャッフルした選択肢を返す | ステップ1 |
| `submit_answer(match_id, q, choice_id)` | 締切判定・正誤判定・記録をして、`answered` を通知する | ステップ1 |
| `advance(match_id)` | 条件を満たせば次の問題へ進むか試合を終了する。終了時にレートも更新する | ステップ1（レートは後で追加） |
| `find_match()` / `leave_queue()` | ランダムマッチ | 後で追加 |

`submit_answer` の例:

```sql
create function public.submit_answer(p_match uuid, p_q int, p_choice uuid) returns void
language plpgsql security definer set search_path = '' as $$
declare m game.matches;
begin
  select * into m from game.matches where id = p_match for update;
  if not exists (select 1 from game.match_players
                 where match_id = p_match and user_id = auth.uid()) then
    raise exception 'not a player';
  end if;
  if m.status <> 'playing' or m.current_q <> p_q then
    raise exception 'invalid question';
  end if;
  if now() < m.q_started_at or now() > m.q_deadline then
    raise exception 'out of time';
  end if;

  insert into game.match_answers (match_id, user_id, q_index, choice_id, is_correct, elapsed_ms)
  select p_match, auth.uid(), p_q, p_choice, (qa.correct_choice_id = p_choice),
         (extract(epoch from now() - m.q_started_at) * 1000)::int
  from game.question_answers qa
  where qa.question_id = m.current_question_id;   -- 二重回答はユニーク制約でエラーになる

  -- 通知は「答えた」という事実だけ
  perform realtime.send(jsonb_build_object('user_id', auth.uid(), 'q', p_q),
                        'answered', 'match:' || p_match, true);
end $$;

revoke execute on function public.submit_answer(uuid, int, uuid) from anon;
```

### 3.4 Realtime の設定

- 部屋は private channel `match:{match_id}`、マッチング通知は `user:{user_id}`
- サーバーから送るイベントは `started` / `answered` / `question_closed` / `finished` / `matched`
- 受信（SELECT）は参加者だけに許可する。クライアントからの送信は Presence だけに許可する

注意: `realtime.messages` のポリシーはログイン中のユーザーの権限で評価されるので、非公開の `game.match_players` を直接参照すると権限エラーになります。参加者かどうかを調べる `security definer` の関数を、API に公開しないスキーマに用意してポリシーから呼びます。

```sql
create schema private;  -- API には公開しない
grant usage on schema private to authenticated;

create function private.is_match_member(p_topic text) returns boolean
language sql security definer set search_path = '' stable as $$
  select exists (
    select 1 from game.match_players
    where user_id = auth.uid() and 'match:' || match_id::text = p_topic
  );
$$;
revoke execute on function private.is_match_member(text) from public, anon;
grant execute on function private.is_match_member(text) to authenticated;

create policy "match members receive" on realtime.messages
for select to authenticated
using (
  realtime.messages.extension in ('broadcast', 'presence')
  and private.is_match_member((select realtime.topic()))
);

create policy "match members presence" on realtime.messages
for insert to authenticated
with check (
  realtime.messages.extension = 'presence'
  and private.is_match_member((select realtime.topic()))
);
-- broadcast の INSERT ポリシーは作らない
```

クライアント側:

```ts
await supabase.realtime.setAuth()
const ch = supabase.channel(`match:${matchId}`, { config: { private: true } })
  .on('broadcast', { event: 'answered' }, ({ payload }) => { /* 相手が回答した */ })
  .on('broadcast', { event: 'question_closed' }, ({ payload }) => { /* 正誤・相手の回答を表示 */ })
  .on('presence', { event: 'leave' }, () => { /* 相手が切断 */ })
  .subscribe(async (s) => { if (s === 'SUBSCRIBED') await ch.track({ userId }) })
```

### 3.5 問題の進め方

- 通常は、両方のクライアントが締切時刻に `advance` を呼ぶ。2回呼ばれても進むのは1回だけ
- 2人とも切断して止まった試合は、pg_cron で1分ごとに進めるか、放棄として終了させる
- 不正対策としては締切を `now()` で判定しているだけで十分で、進行のタイミングは見た目の問題にとどまる

## 4. マッチングとレート

### マッチング

| 方式 | 内容 | 使う場面 |
|---|---|---|
| フレンド対戦 | 招待コード・リンクで部屋に入る | 最初に作る。**レートは変動させない** |
| ランダムマッチ | `game.match_queue` に入り、レートが近い相手と組む | レート戦 |
| ゴースト対戦 | 他の人の過去の回答記録と非同期で戦う | 同時にオンラインの人が少ないとき |

- `find_match()` では `for update skip locked` を使い、同時に呼ばれても同じ相手を取り合わないようにする
- 待ち時間に応じて許容するレート差を広げる（例: ±100 から始め、5秒ごとに ±50）
- 20〜30秒見つからなければゴースト対戦に切り替える
- 古い待機エントリは除外・削除し、画面を閉じたら列から抜ける

### レート（Elo）

```
期待勝率 E_A = 1 / (1 + 10^((R_B - R_A) / 400))
新レート R_A' = R_A + K × (結果 - E_A)    結果: 勝ち=1、引き分け=0.5、負け=0
```

- 初期値 1500、K=32。最初の10戦ほどは K を 40〜60 にする
- 精度が必要になったら Glicko-2 に移行する

不正対策として決めておくこと:

- レートの更新は `advance` で試合を `finished` にするのと同じトランザクションで行う
- レートが動くのはランダムマッチだけ（サブアカウントでわざと負けるのを防ぐ）
- 途中で切断したら負けにする
- 同じ相手と短時間に何度も当たったら、変動を減らすか止める
- 表示は数値よりランク帯（ブロンズ・シルバーなど）にする

## 5. 制限と費用

Supabase Realtime の上限:

| 項目 | Free | Pro（月 $25〜） |
|---|---|---|
| 同時接続数 | 200 | 500（支出上限を外すと 10,000） |
| メッセージ数 / 秒 | 100 | 500 |
| Presence メッセージ数 / 秒 | 20 | 50 |
| 月間メッセージ数 | 200万件 ※ | 500万件 ※ |

※ 公式ページを直接確認できず、ブログ記事で確認した値

- 1接続はブラウザ1タブ。全員が対戦中なら最大でおよそ100試合を同時に行える
- 先に上限に達しやすいのは Presence の 20件/秒（大勢が同時に入退室したとき）
- 上限を超えると切断されるが、supabase-js が自動で再接続する
- Realtime には対戦中とマッチング待ちのときだけ接続し、終わったら `supabase.removeChannel()` で切る
- Free プランのプロジェクトは、使われない期間が続くと一時停止される
- 個人開発の初期は Free で足りる。同時プレイが数百人規模になったら Pro へ

## 6. 検討して採用しなかった案

| 案 | 採用しなかった理由 |
|---|---|
| WebRTC（P2P） | 判定をどちらかのブラウザで行うため、正解・時刻・スコアを守れない。主目的と両立しない。シグナリングと TURN（中継サーバー）も必要で、費用もほぼ減らない |
| Vercel Functions の WebSocket | 2026年6月に公開ベータになったばかり。関数の実行時間の上限で接続が切れる（約5分で切断という検証報告あり）。部屋への一斉配信や在席管理を自作する必要がある |
| Cloudflare Durable Objects | 対戦ルームには向いている（1試合1オブジェクト、処理が1つずつ実行される、Alarm でサーバーがタイマーを進める、Free プランあり）。ただし不正対策の強さは本案と同じで、管理するサービスが3つに増え、Supabase の JWT 検証や結果の書き戻しも必要になる。本案の非公開スキーマ・行ロック・pg_cron で同等にできるため見送り |
| Ably / Pusher | 大規模配信向けで、この規模には過剰 |

Durable Objects に切り替えたくなる目安: ロジックが PL/pgSQL では書きにくい・テストしにくいほど複雑になったとき、またはサーバー側で秒単位の厳密な進行が必要になったとき。

## 7. 実装の順番

### ステップ1: 招待リンクで1試合を最後まで遊べる（不正対策の土台を含む）

1. DB: `game` スキーマと5テーブル（`matches` / `match_players` / `questions` / `question_answers` / `match_answers`）。問題は既存のものから10問ほどコピー
2. RPC 5つ: `create_match` / `join_match` / `get_current_question` / `submit_answer` / `advance`
3. Realtime: private channel と RLS（3.4 のとおり）、サーバーからの4種類の通知
4. 画面4つ: 部屋を作る / リンクで参加 / 対戦 / 結果。タイマーは表示用だけ

**完了条件**

- 2つのブラウザ（別アカウント）で10問の試合を最後まで遊べる
- 確認用スクリプトで次の操作がすべて拒否される
  - `game` スキーマのテーブルを直接 SELECT する
  - 他人の試合の `get_current_question` を呼ぶ
  - 出題時刻より前に問題を取得する
  - 締切を過ぎてから `submit_answer` を呼ぶ
  - 同じ問題に2回回答する
  - 他人の試合のチャンネルを購読する・クライアントから Broadcast を送る
- Security Advisor で警告が出ない

### その後

1. Presence で切断を表示し、pg_cron で放置された試合を片付ける
2. ランダムマッチ（`find_match`）
3. Elo レート（ランダムマッチのみ、切断は負け）
4. ゴースト対戦（人が少ない時間帯への対策）
