# クイズアプリ リアルタイム対戦 設計まとめ

- 対象: React SPA（Vercel でホスティング）+ Supabase（DB・認証）
- 作りたいもの: 2人が同じ問題を同時に解いて競うリアルタイム対戦
- **最優先: 不正対策**（相手の答えが見える・タイマーをいじられる、は絶対に避ける）
- その次: サービスを増やさない（Vercel・Supabase の2つのまま）

---

## 1. 結論

**Vercel と Supabase だけで作る。判定はすべてサーバー（Postgres の RPC）で行う。**

| 役割 | 使うもの |
|---|---|
| SPA の配信 | Vercel（今のまま） |
| 認証 | Supabase Auth（今のまま） |
| 試合データ（問題・正解・回答・状態） | API に公開しない `game` スキーマ |
| クライアントの入口 | `public` スキーマに置いた少数の RPC（`security definer`） |
| 通知の配信 | Supabase Realtime の Broadcast（RPC 内の `realtime.send()` からだけ送る） |
| 相手の在席・切断の検知 | Supabase Realtime の Presence |
| 放棄された試合の片付け | pg_cron（Supabase Cron） |

不正対策の土台は次の1文にまとまる。

> **クライアントには、今の時点で見えてよい情報しか渡さない。判定・時刻・スコアはすべてサーバーが決める。**

## 2. 不正対策の設計

### 2.1 守るもの・脅威・対策

| 守るもの | 脅威 | 対策 |
|---|---|---|
| 相手の回答 | 回答テーブルを直接読む | テーブルを非公開の `game` スキーマに置く。REST API からは存在も見えない |
| | Realtime 通知から読む | 回答時の通知は「答えた」という事実だけ。選んだ選択肢は入れない |
| | Postgres Changes から読む | `game` スキーマのテーブルを `supabase_realtime` publication に入れない |
| | 偽の Broadcast を送る | `realtime.messages` に broadcast の INSERT ポリシーを作らない。送信は RPC 内の `realtime.send()` だけ |
| | 答えを教え合う（「Bだよ」） | 選択肢の並び順をプレイヤーごとにシャッフルし、回答は選択肢 ID で受け取る |
| 正解 | クライアントに渡ったデータを開発者ツールで見る | 正解は `game.question_answers` に置き、締切を過ぎるまで誰にも返さない |
| 問題文 | 先に取得して調べる | 全問をまとめて渡さない。`get_current_question` が出題時刻（`q_started_at`）を過ぎてから1問ずつ返す |
| 締切・回答時間 | ブラウザの時計や JS を書き換える | 判定は DB の `now()` だけ。クライアントのタイマーは表示用。回答時間も `now() - q_started_at` でサーバーが計算する |
| 回答 | 二重回答・回答の変更 | `(match_id, user_id, q_index)` にユニーク制約 |
| 試合の進行 | `advance` を早く呼ぶ | 「両者が回答済み」か「締切を過ぎた」場合だけ進む。呼ぶタイミングをいじっても得をしない |
| 他人の試合 | 他人の試合 ID で RPC を呼ぶ | どの RPC も最初に「`auth.uid()` がこの試合の参加者か」を確認する |
| スコア・レート | 結果を自己申告する | スコアとレートはサーバーだけが計算する。クライアントから届いた結果は保存しない |
| レート | サブアカウントでわざと負ける | レートが変動するのはランダムマッチだけ。同じ相手と短時間に何度も当たったら変動を減らす |
| | 負けそうになったら切断する | 途中で切断したら負けとして扱う |

### 2.2 実装で必ず守ること

- **データは `game` スキーマに置き、API に公開しない**（Dashboard の API 設定で公開スキーマに追加しない）。`revoke all on schema game from anon, authenticated;`
- **クライアントが呼べるのは `public` の RPC だけ**にする。RPC は「誰でも直接呼べる」前提で書く。
- RPC は `security definer set search_path = ''` で定義し、中では `game.matches` のようにスキーマ名付きで参照する。
- 未ログインのユーザーには呼ばせない: `revoke execute on function ... from anon`
- **同時実行対策**: 各 RPC の最初で `select ... from game.matches where id = p_match for update` で試合の行をロックし、同じ試合への処理を1つずつ実行させる。
- `public` 側にテーブルを残す場合は、すべて RLS を有効にし、クライアントからの書き込みポリシーは作らない。

### 2.3 確認方法

- Dashboard の **Security Advisor** で、RLS が無効なテーブルや `search_path` 未指定の関数がないか確認する。
- **確認用スクリプト**（別アカウントのトークンで `supabase-js` から実行）で、次がすべて拒否されることを確かめる。RPC を変更するたびに流す。
  - `game` スキーマのテーブルを直接 SELECT する
  - 他人の試合の `get_current_question` を呼ぶ
  - 出題時刻より前に問題を取得する
  - 締切を過ぎてから `submit_answer` を呼ぶ
  - 同じ問題に2回回答する
  - クライアントから `match:{id}` に Broadcast を送る

### 2.4 防ぎきれない不正

どの構成でも完全には防げないので、影響を小さくする。

| 不正 | 対応 |
|---|---|
| 別の画面で検索する・人に聞く | 制限時間を短くする。回答の速さをスコアに加える |
| Bot による自動回答 | 回答時間はすべて記録されるので、極端に速い人・正答率が不自然に高い人を後から検出し、ランク戦から外す |
| 通信の速さによる差 | 「正解数で勝敗を決め、同点のときだけ回答時間を比べる」ルールにする |

## 3. 全体構成と試合の流れ

```
[A] ──RPC: submit_answer──▶ Postgres（game スキーマ：正誤・締切判定、記録）
                               │ realtime.send()
                               ▼
[A][B] ◀──Broadcast "match:{id}"（private）── Supabase Realtime
[A][B] ◀──Presence（在席・切断検知）──
                               ▲
                   pg_cron：放棄された試合を片付け
```

### 3.1 テーブル（`game` スキーマ）

`matches` / `match_players` / `questions` / `question_answers` / `match_answers` / `match_queue`（ランダムマッチ用）

レートは `profiles` などに持つ（クライアントからは読み取りのみ）。

### 3.2 RPC（`public` スキーマ）

| RPC | 内容 |
|---|---|
| `create_match()` | 部屋を作り、招待コードを返す |
| `join_match(code)` | 2人目として参加。そろったら最初の問題の `q_started_at` と `q_deadline` を決める |
| `get_current_question(match_id)` | 出題時刻を過ぎていれば、正解を含まない問題文と、このプレイヤー用にシャッフルした選択肢を返す |
| `submit_answer(match_id, q, choice_id)` | 参加者か・今の問題か・締切内かを確認し、正誤と回答時間をサーバーで計算して記録。「答えた」ことだけを通知 |
| `advance(match_id)` | 両者が回答済みか締切を過ぎていれば、正解を公開して次の問題へ進むか試合を終了。試合終了時に同じトランザクションでスコアとレートを確定 |
| `find_match()` / `leave_queue()` | ランダムマッチ（後述） |

### 3.3 1問の流れ

1. `advance` が `q_started_at = now() + 3秒`（カウントダウン分）と `q_deadline = q_started_at + 制限時間` を保存し、Broadcast で通知する。
2. 両クライアントは出題時刻になったら `get_current_question` を呼ぶ。タイマーは `q_deadline` を基準に表示するだけ。
3. 回答は `submit_answer`。相手には「答えた」とだけ通知される。
4. 両者が答えたか締切の時刻になったら、クライアントが `advance` を呼ぶ。2人同時に呼んでも進むのは1回だけ。
5. 2人とも切断して誰も `advance` を呼ばない場合は、pg_cron（1分ごと程度）が締切切れの試合を進めるか、放棄として終了させる。

### 3.4 Realtime の設定

- チャンネル `match:{match_id}` を private にし、`realtime.messages` の SELECT ポリシーで参加者だけが受信できるようにする。
- Presence 用には同じ条件で INSERT ポリシーを作る。broadcast の INSERT ポリシーは作らない。
- 通知の種類: `started` / `answered` / `question_closed` / `finished`、ランダムマッチ用に個人チャンネル `user:{id}` の `matched`。
- Realtime には対戦中とマッチング待ちのときだけ接続し、終わったら `supabase.removeChannel()` で切断する。

```sql
create policy "match members receive"
on realtime.messages for select to authenticated
using (
  realtime.messages.extension in ('broadcast', 'presence')
  and exists (
    select 1 from game.match_players mp
    where mp.user_id = auth.uid()
      and 'match:' || mp.match_id::text = (select realtime.topic())
  )
);
```

## 4. マッチングとレーティング

### 4.1 マッチング

| 方式 | 内容 | 位置づけ |
|---|---|---|
| フレンド対戦 | 招待コード・リンクで部屋に入る | 最初に作る。レートは変動させない |
| ランダムマッチ | 待機列に入り、レートが近い相手と組む | レート戦 |
| ゴースト対戦 / Bot 対戦 | 過去の回答記録と非同期で戦う | 同時にオンラインの人が少ないとき |

- `find_match()` RPC で、待機列から `for update skip locked` で相手を1人確保する（同時に呼ばれても取り合わない）。
- 待ち時間に応じて許容レート差を広げる（例: ±100 から5秒ごとに ±50）。
- 20〜30秒見つからなければゴースト対戦・Bot 対戦に切り替える。
- 古い待機エントリは除外・削除し、画面を閉じたら `leave_queue()` で列から抜ける。

### 4.2 レーティング

- **Elo** から始める（必要になったら Glicko-2 へ）。
  - 期待勝率 `E_A = 1 / (1 + 10^((R_B - R_A) / 400))`
  - 新レート `R_A' = R_A + K × (結果 - E_A)`（勝ち=1、引き分け=0.5、負け=0）
  - 初期 1500、K=32。最初の10戦ほどは K=40〜60。
- 更新は `advance` で試合を `finished` にするトランザクション内でだけ行う（二重加算しない）。
- 不正対策は 2.1 の表のとおり（ランダムマッチのみ変動・切断は負け・同じ相手との連戦は変動を減らす）。
- 表示はブロンズ・シルバーなどのランク帯にすると分かりやすい。

## 5. 制限とコスト

Supabase Realtime の上限（公式の制限ページより。月間メッセージ数はブログ記事で確認）。

| 項目 | Free | Pro |
|---|---|---|
| 同時接続数 | 200 | 500（支出上限を外すと 10,000） |
| メッセージ数 / 秒 | 100 | 500 |
| Presence メッセージ数 / 秒 | 20 | 50 |
| 月間メッセージ数 | 200万件 | 500万件 |

- 1接続はブラウザ1タブ。全員が対戦中なら Free で同時に約100試合。待機中・ロビーの人も接続していれば数に入る。
- 1試合（10問）で数十〜100件と見積もると、月に数万試合までは Free に収まる。実際の値は Realtime Reports で確認する。
- 先に上限に達しやすいのは Presence の 20件/秒。
- 上限を超えると切断される（`tenant_events` エラー）。supabase-js は自動で再接続する。
- Free プランのプロジェクトはしばらく使われないと一時停止される。
- 同時にプレイする人が数百人規模になったら Pro（月額 $25〜）へ。

## 6. 検討して採用しなかった案

| 案 | 不正対策の観点 | その他 | 判断 |
|---|---|---|---|
| **WebRTC（P2P）** | 判定がブラウザ側になり、正解・回答時刻・スコアを改ざんできる。戦績・レートを信用できない | シグナリングと TURN（従量課金）が結局必要で、サーバー代は減らない。今の案も Free で動く | 不採用。ボイスチャットを付けるときだけ、通話部分に使う |
| **Vercel Functions の WebSocket** | — | 2026年6月に公開ベータになったばかり。接続は関数の最大実行時間で切れる（約5分で切断された報告あり）。部屋への一斉配信・在席管理は自作 | 不採用 |
| **Cloudflare Durable Objects** | Supabase 案と同じ強さ（どちらもサーバー権威型）。判定に使うデータがクライアントから届かない場所に置け、処理が1つずつ実行され、Alarm で自分でタイマーを進められる | サービスが3つになる。Worker で Supabase の JWT 検証、Supabase への戦績書き戻しが必要。Free 枠（10万リクエスト/日）で個人規模は足りる | 不採用（サービスを増やしたくないため）。DO の利点は `game` スキーマ・`for update`・`now()` 判定 + pg_cron で代替できる |
| **Ably / Pusher** | — | 大規模配信向けで今回は過剰 | 不採用 |

Supabase だけの構成で DO と比べて残る違い:

- ロジックを PL/pgSQL で書く（TypeScript より書きにくく、テストしにくい）。
- 問題を進めるタイミングは主にクライアントの `advance` 呼び出しに頼る。不正には影響しないが、片方の通信が遅いと画面の切り替わりが少し遅れることがある。

将来、サーバー側で厳密なタイマー進行が必要になったり、大人数の部屋を作ったりする場合は、DO への移行を再検討する。

## 7. 作る順番

### ステップ1: 招待リンクで2人が1試合を最後まで遊べる

**不正対策の仕組み（`game` スキーマ・RPC だけで判定・`now()` で締切判定）は最初から入れる。** 後から入れると、クライアントが DB を直接読み書きするコードを書き直すことになる。

1. DB: `game` スキーマと5テーブル（`matches` / `match_players` / `questions` / `question_answers` / `match_answers`）。問題は既存から10問程度コピー。
2. RPC: `create_match` / `join_match` / `get_current_question` / `submit_answer` / `advance`
3. Realtime: private channel `match:{id}` と RLS、`started` / `answered` / `question_closed` / `finished` の通知
4. 画面: 部屋を作る・リンクで参加・対戦・結果の4画面（タイマーは表示用）

作らないもの: ランダムマッチ、レート、Presence、pg_cron、ゴースト対戦。締切を `now()` で判定しているので、相手が落ちても試合は止まらない。

**完了の目安**

- 2つのブラウザ（別アカウント）で10問の試合を最後まで遊べる。
- 2.3 の確認用スクリプトで、拒否されるべき操作がすべて拒否される。

### ステップ2以降

1. Presence で「相手が切断」を表示し、pg_cron で放棄された試合を片付ける
2. ランダムマッチ（`find_match` / `leave_queue`）
3. Elo レート（ランダムマッチのみ）
4. ゴースト対戦・Bot 対戦

## 8. 実装前に確認すること

supabase.com のドキュメントは調査環境から直接取得できず、検索結果で確認した。次の点は実装前に公式ドキュメントで確かめる。

- `realtime.topic()` を使う RLS ポリシーの正確な書き方
- `realtime.send()` の引数の順序（payload, event, topic, private）
- 公開しないスキーマを `security definer` 関数から参照するときの権限設定
- 月間メッセージ数の上限と、1件の配信が受信者ごとに数えられるか
