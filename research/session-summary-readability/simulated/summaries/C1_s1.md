# クイズアプリ リアルタイム対戦 調査まとめ

前提: React SPA / Supabase（DB・認証）/ Vercel（ホスティング）。個人開発。最優先は**不正対策**（相手の答えが見える、タイマーをいじられる、を防ぐ）。

## 1. 結論

**Vercel + Supabase のまま、サーバー権威型で作る。** サービスは増やさない。

- 配信: Supabase Realtime（Broadcast と Presence、private channel）
- 判定（正誤・締切・スコア・レート）: Postgres の RPC（`security definer`）だけで行う
- ゲームデータ: API に公開しない `game` スキーマに置く
- 進行の後片付け: pg_cron
- Vercel: 今まで通り SPA の配信だけに使う

## 2. 検討した選択肢

| 選択肢 | 評価 | 理由 |
|---|---|---|
| **Supabase Realtime + RPC（採用）** | ◎ | 今の構成のまま。非公開スキーマと行ロックで DO と同じ水準の不正対策ができる |
| Cloudflare Durable Objects | ○ | 対戦ルームには向いている（1試合1オブジェクト、処理が順番に実行される、Alarm で進行）。不正対策の強さは同じだが、サービスが3つになるので見送り |
| WebRTC（P2P） | × | シグナリングと TURN が必要でサーバー代は減らない。判定をクライアントで行うことになり、不正を防げない。ボイスチャットを付けるときだけ検討 |
| Vercel Functions の WebSocket | × | 2026年6月に公開ベータになったばかり。接続が切れる（約5分の報告あり）、一斉配信や在席管理を自作する必要がある |
| Ably / Pusher | △ | 今回の規模には過剰 |

## 3. 全体の構成

```
[A] ──RPC: submit_answer──▶ Postgres（game スキーマ: 正誤・締切判定、記録）
                               │ realtime.send()
                               ▼
[A][B] ◀──Broadcast "match:{id}"── Supabase Realtime
[A][B] ◀──Presence（在席・切断検知）──
                    pg_cron ──▶ 締切切れ・放棄された試合を片付け
```

公開する RPC（`public` スキーマ）:
`create_match` / `join_match` / `get_current_question` / `submit_answer` / `advance`（後で `find_match` / `leave_queue`）

## 4. 不正対策

基本方針: **クライアントには、今の時点で見えてよい情報しか渡さない。判定はすべてサーバーで行う。**

### 相手の答え・正解を見せない
- ゲームのテーブルは `game` スキーマに置き、API に公開しない（`revoke all on schema game from anon, authenticated`）。RLS を書き忘れても漏れない
- 正解は `game.question_answers` に分ける
- 問題文は出題時刻（`q_started_at`）を過ぎてから `get_current_question` で1問ずつ返す。正解は含めない
- 回答時の通知は「答えた」という事実だけ。選んだ選択肢は送らない。正誤はその問題の締切後に返す
- `game` のテーブルは `supabase_realtime` publication に入れない（Postgres Changes で漏れないように）
- `realtime.messages` に broadcast の INSERT ポリシーを作らない。送信は RPC 内の `realtime.send()` だけ。クライアントからは Presence だけ許可
- 選択肢の並び順をプレイヤーごとにシャッフルし、回答は選択肢 ID で受け取る（答えの教え合い対策）

### タイマーをいじらせない
- クライアントのタイマーは表示用だけ
- `q_started_at = now() + 3秒`、`q_deadline = q_started_at + 制限時間` を DB に保存
- `submit_answer` は DB の `now()` が `q_started_at`〜`q_deadline` の間のときだけ受け付ける
- 回答時間は `now() - q_started_at` でサーバーが計算する
- `(match_id, user_id, q_index)` のユニーク制約で二重回答・回答変更を防ぐ
- `advance` は「両者回答済み」か「締切超過」のときだけ条件付き UPDATE で進める。誰がいつ呼んでも得をしない

### 全体
- すべての RPC の最初に「`auth.uid()` が参加者か」「今の状態でその操作をしてよいか」を確認し、`select ... for update` で試合の行をロックする
- `security definer` の関数には `set search_path = ''` を付け、テーブルはスキーマ名付きで参照する
- `revoke execute on function ... from anon`
- スコア・レートはサーバーだけが計算する
- Security Advisor と、別ユーザーのトークンで拒否を確かめる確認用スクリプトを、RPC を変えるたびに流す

### 防ぎきれないもの
- 別画面での検索・他人に聞く → 制限時間を短くし、速さもスコアに入れる
- Bot による自動回答 → 回答時間の記録から極端な人を後で検出し、ランク戦から外す
- 回線の速さの差 → 正解数で勝敗、同点のときだけ時間で比べる

## 5. マッチングとレーティング

### マッチング
- 最初はフレンド対戦（招待リンク）。レートは変動させない
- ランダムマッチは `find_match()` RPC と待機列テーブルで作る。`for update skip locked` で取り合いを防ぎ、待ち時間に応じて許容レート差を広げる（例: ±100 から5秒ごとに +50）
- 待っている側は private channel `user:{id}` で `matched` 通知を受け取る
- 20〜30秒で見つからなければゴースト対戦か Bot 対戦に切り替える（人が少ない対策）
- 古い待機エントリは除外・削除する

### レーティング
- 最初は Elo（初期 1500、K=32、最初の10戦は K=40〜60）
  - `E_A = 1 / (1 + 10^((R_B - R_A) / 400))`、`R_A' = R_A + K × (結果 - E_A)`
- 試合を `finished` にするのと同じトランザクションで更新する（二重加算しない）
- レート変動はランダムマッチだけ。途中切断は負け。同じ相手との連戦は変動を減らす
- 表示はランク帯（ブロンズ・シルバーなど）にすると分かりやすい
- 精度が必要になったら Glicko-2 に移行

## 6. Supabase Realtime の制限（無料枠）

| 項目 | Free | Pro |
|---|---|---|
| 同時接続数 | 200 | 500（支出上限を外すと 10,000） |
| メッセージ数 / 秒 | 100 | 500 |
| Presence メッセージ数 / 秒 | 20 | 50 |
| 月間メッセージ数 | 200万件 | 500万件 |

- 1接続 = ブラウザ1タブ。全員対戦中なら最大でおよそ100試合を同時に行える
- 先に上限に達しやすいのは Presence の 20件/秒
- 上限を超えると切断（`tenant_events`）、supabase-js が自動再接続
- 対戦中とマッチング待ちのときだけ接続し、終わったら `removeChannel()` する
- Free はしばらく使われないとプロジェクトが一時停止される
- 個人開発の初期は Free で十分。同時プレイが数百人規模になったら Pro（月額 $25〜）へ

## 7. 作る順番

### ステップ1: 招待リンクで2人が1試合を最後まで遊べる
不正対策の仕組みは最初から入れる。

1. DB: `game` スキーマと `matches` / `match_players` / `questions` / `question_answers` / `match_answers`。問題は既存から10問ほどコピー
2. RPC: `create_match` / `join_match` / `get_current_question` / `submit_answer` / `advance`
3. Realtime: private channel `match:{id}`、参加者だけ受信できる RLS、`started` / `answered` / `question_closed` / `finished` の4種類
4. 画面: 部屋作成、リンクで参加、対戦、結果

**完了の目安**
- 2つのブラウザ（別アカウント）で10問を最後まで遊べる
- 確認用スクリプトで次がすべて拒否される: `game` テーブルの直接 SELECT、他人の試合の問題取得、締切後の回答、二重回答、出題時刻前の問題取得

### その後
1. Presence で切断表示、pg_cron で放棄された試合を片付け
2. ランダムマッチ（`find_match`）
3. Elo レート
4. ゴースト対戦
