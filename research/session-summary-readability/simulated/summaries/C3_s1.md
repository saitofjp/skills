# クイズアプリ「リアルタイム対戦」実現方法 調査まとめ

調査日: 2026-10-17

## 1. 前提

| 項目 | 内容 |
|---|---|
| アプリ | 個人開発のクイズアプリ（React の SPA） |
| 既存構成 | ホスティング: Vercel / DB と認証: Supabase |
| 追加したい機能 | 2人が同じ問題を同時に解いて競う「リアルタイム対戦」。将来はランダムマッチとレーティングも付けたい |
| 最優先の要件 | **不正対策**。特に「相手の答えが見える」「タイマーを操作される」ことは絶対に避ける |
| 制約・希望 | 利用するサービスは増やしたくない（Vercel・Supabase の2つのままにしたい）。費用はできるだけ抑えたい |

## 2. 結論

**Vercel と Supabase だけで作る。** 対戦の進行と判定は Supabase の Postgres 関数（RPC）で行い、通知は Supabase Realtime で配信する。

- **Vercel**: これまで通り SPA の配信だけに使う。
- **Supabase Realtime**: 部屋の参加者への通知（Broadcast）と、相手がオンラインかの検知（Presence）に使う。
- **Postgres（RPC）**: 出題、締切の判定、正誤判定、スコア計算、マッチング、レート計算をすべてサーバー側で行う。クライアントから送られた結果は信用しない。
- **ゲーム用のデータ**: API に公開しない専用スキーマ（`game`）に置く。クライアントは RPC 経由でしか触れられない。

この構成でも、サーバーがすべてを判定する設計（サーバー権威型）になるため、相手の答えやタイマーを守る強さは専用のゲームサーバーを立てた場合と変わらない。

## 3. 検討した選択肢

| 選択肢 | 評価 | 理由 |
|---|---|---|
| **Supabase Realtime + RPC** | **採用** | 既存構成のまま追加できる。無料枠で足りる。不正対策も十分にできる |
| Cloudflare Durable Objects | 有力だが見送り | 対戦ルームには非常に向いている（後述）。ただし管理するサービスが3つに増える |
| WebRTC（P2P） | 不採用 | 費用が減らず、不正対策がほぼできない |
| Vercel Functions の WebSocket | 不採用 | 2026年6月に公開ベータになったばかり。接続は関数の最大実行時間で切れる（約5分で切断されたという検証報告あり）。部屋への一斉配信や在席管理を自作する必要がある |
| Ably / Pusher | 不採用 | 大規模配信向けで、今回の規模には過剰 |

### 3.1 WebRTC（P2P）を採用しない理由

「P2P ならサーバー代がかからない」という案を検討したが、次の理由で採用しない。

- **費用が減らない**: Supabase 案も無料枠に収まる見込みなので、そもそも節約できる金額がない。さらに P2P でも、接続を始めるための情報交換（シグナリング）にサーバーが必要になる。スマホのキャリア回線や会社・学校のネットワークでは直接つながらないことが多く、その場合は通信を中継する TURN サーバー（通信量に応じた従量課金）が必要になる。
- **不正を防げない**: 正誤判定やスコア計算をどちらかのブラウザで行うことになる。正解をクライアントに渡すので開発者ツールで見られ、時刻やスコアも書き換えられる。戦績やランキングも自己申告になる。
- **切断時の扱いが難しい**: どちらの状態が正しいかを決める調停役がいない。
- **低遅延の利点が活きない**: クイズでは数百ミリ秒の遅延は問題にならない。

対戦中にボイスチャットやビデオを付けたくなった場合は、試合の進行は Supabase のままにして、通話だけ WebRTC を追加する（シグナリングに Supabase Realtime を使う）構成が考えられる。

### 3.2 Cloudflare Durable Objects を見送った理由

Durable Objects（以下 DO）は「1試合 = 1オブジェクト」として扱え、対戦ルームに向いている。

- 問題・正解・回答・タイマーを、クライアントから届かないオブジェクトの中だけに持てる
- 1つのオブジェクトは処理を1つずつ順番に実行するので、同時に回答が来ても競合しない
- Alarms 機能で、締切の時刻にサーバー自身が次の問題へ進められる
- ロジックを TypeScript でまとめて書ける
- Free プランあり（リクエスト 10万件/日、実行時間 13,000 GB-s/日。WebSocket は1接続で1リクエスト、受信メッセージ20件で1リクエストとして数える。Hibernation API を使えば待機中は課金されない）

ただし、DO にすることで不正対策が強くなるわけではない。利点は「同じ守りを、設定ミスが起きにくい形で書ける」ことにある。そして DO の主な利点は、次の表のように Supabase の機能で代わりを用意できる。サービスを3つに増やしたくないという希望を優先し、見送った。

| DO の利点 | Supabase での代わり |
|---|---|
| 守るべきデータがクライアントから届かない場所にある | ゲーム用テーブルを API に公開しないスキーマ（`game`）に置く |
| 処理が1つずつ順番に実行される | 各 RPC の最初で試合の行を `select ... for update` でロックする |
| サーバーが Alarm で問題を進める | 締切は `now()` で判定する。進行は「誰が何度呼んでも安全な RPC」で行い、止まった試合は pg_cron で片付ける |

Supabase 案に残る弱点は次の2点で、いずれも不正にはつながらない。

- ロジックを PL/pgSQL で書くため、TypeScript より書きにくく、テストもしにくい
- 問題を進めるきっかけは主にクライアントからの呼び出しなので、通信が遅い側では画面の切り替わりが少し遅れることがある

将来、サーバー側で厳密に毎秒ゲームを進める必要が出たり、大人数の部屋が必要になったりした場合は、DO への移行を再検討する。

## 4. 全体構成

```
[プレイヤーA] ──RPC: submit_answer など──▶ Postgres（game スキーマ）
                                              │ 締切・正誤判定、記録
                                              │ realtime.send()
                                              ▼
[A][B] ◀──Broadcast "match:{id}"─────── Supabase Realtime
[A][B] ◀──Presence（在席・切断の検知）──
```

### 4.1 試合の流れ

1. **部屋を作る・参加する**: 最初は招待リンク（合言葉）で2人目が参加する形にする。2人そろったら、サーバーが最初の問題の出題時刻を決める。
2. **出題**: 出題時刻 `q_started_at` と締切 `q_deadline` を DB の `now()` 基準で決めて保存し、Broadcast で両者に知らせる（出題前に3秒のカウントダウンを入れるなら `q_started_at = now() + interval '3 seconds'`）。クライアントはその時刻に合わせてカウントダウンを表示するだけ。
3. **問題の取得**: 出題時刻を過ぎてから `get_current_question` で問題文と選択肢を取得する。正解は含めない。
4. **回答**: `submit_answer` で回答を送る。サーバーが締切内か、二重回答でないかを確認し、正誤と回答時間を記録する。相手には「回答した」という事実だけを通知する。
5. **次の問題へ**: 両方のクライアントが、両者の回答がそろったときか締切の時刻に `advance` を呼ぶ。サーバーは「両者が回答済み」または「締切を過ぎた」場合だけ状態を進める。2人が同時に呼んでも進むのは1回だけ。
6. **終了**: 最終問題が終わったら試合を `finished` にし、同じトランザクションの中で結果とレートを確定する。
7. **切断**: 締切を `now()` で判定しているので、相手が落ちても試合は進む。Presence で「相手が切断」を表示する。2人とも切断して止まった試合は pg_cron（Supabase Cron）で定期的に終了させる。

## 5. 不正対策の設計

基本方針: **クライアントには、その時点で見えてよい情報だけを渡す。判定はすべてサーバーで行う。**

### 5.1 データの置き場所

- ゲーム用テーブルは `game` スキーマに置く。Dashboard の API 設定で公開スキーマに追加しないので、REST API からはテーブルの存在すら見えない。RLS のポリシーを書き忘れても、そこから漏れることはない。
- クライアントが呼べるのは `public` スキーマに置いた少数の RPC だけにする。
- 書き込みはすべて RPC 経由にする。

```sql
create schema game;   -- API の公開スキーマには追加しない
revoke all on schema game from anon, authenticated;

create table game.matches (...);
create table game.match_players (...);
create table game.match_answers (...);    -- unique (match_id, user_id, q_index)
create table game.questions (...);
create table game.question_answers (...); -- 正解はここだけに置く
```

### 5.2 相手の答えを見せない

| 漏れる経路 | 対策 |
|---|---|
| 回答テーブルを直接読む | `game` スキーマに置くので API から読めない |
| Realtime の通知 | 回答時の通知は「答えた」という事実だけにし、選んだ選択肢は含めない |
| Postgres Changes（テーブル変更の自動配信） | `game` スキーマのテーブルを `supabase_realtime` publication に追加しない |
| クライアントからの Broadcast 送信 | `realtime.messages` に broadcast の INSERT ポリシーを作らない。送信は RPC 内の `realtime.send()` からだけにする。クライアントからの送信は Presence だけ許可する |
| 外部での答えの教え合い | 選択肢の並び順をプレイヤーごとにシャッフルし、回答は表示上の番号ではなく選択肢 ID で受け取る |

相手の回答と正誤は、その問題の締切を過ぎるまで両者に返さない。

### 5.3 正解と問題文を先に見せない

- 正解は `game.question_answers` にだけ置く。
- 問題文は出題時刻になるまで返さない。全問をまとめて先に渡すと、開発者ツールで読まれて事前に調べられてしまう。

### 5.4 タイマーを操作させない

クライアントのタイマーは表示用で、判定には一切使わない。

- `submit_answer` では、DB の `now()` が `q_started_at` から `q_deadline` の間にあるときだけ回答を受け付ける。ブラウザの時計や JS を書き換えても結果は変わらない。
- 回答時間は `now() - q_started_at` でサーバーが計算する。クライアントが申告した経過時間は使わない。
- `advance` を早く呼んでも、条件を満たさなければ何も起きない。呼ぶタイミングをいじっても得をする方法がない。
- `(match_id, user_id, q_index)` のユニーク制約で、二重回答と回答の変更を防ぐ。

### 5.5 RPC の書き方のルール

- RPC は誰でも直接呼べる前提で書く。どの RPC も最初に「`auth.uid()` がこの試合の参加者か」と「今の試合の状態でその操作をしてよいか」を確認する。
- 最初に試合の行を `select ... for update` でロックし、同じ試合への処理を1つずつにする。
- `security definer set search_path = ''` で定義し、テーブルは `game.matches` のようにスキーマ名付きで参照する（`search_path` を固定しないと、同名のテーブルや関数にすり替えられる危険がある）。
- `revoke execute on function ... from anon` で、未ログインのユーザーには呼ばせない。
- スコアとレートはサーバーだけが計算する。

回答 RPC の例（骨組み）:

```sql
create function public.submit_answer(p_match uuid, p_q int, p_choice uuid) returns void
language plpgsql security definer set search_path = '' as $$
declare m game.matches;
begin
  select * into m from game.matches where id = p_match for update;
  if not exists (select 1 from game.match_players
                 where match_id = p_match and user_id = auth.uid()) then
    raise exception 'not a player';
  end if;
  if m.status <> 'playing' or m.current_q <> p_q then
    raise exception 'invalid question';
  end if;
  if now() < m.q_started_at or now() > m.q_deadline then
    raise exception 'out of time';
  end if;

  insert into game.match_answers (match_id, user_id, q_index, choice_id, is_correct, elapsed_ms)
  select p_match, auth.uid(), p_q, p_choice, (qa.correct_choice_id = p_choice),
         (extract(epoch from now() - m.q_started_at) * 1000)::int
  from game.question_answers qa
  where qa.question_id = m.current_question_id;   -- 二重回答はユニーク制約でエラー

  -- 通知は「答えた」という事実だけ
  perform realtime.send(jsonb_build_object('user_id', auth.uid(), 'q', p_q),
                        'answered', 'match:' || p_match, true);
end $$;

revoke execute on function public.submit_answer(uuid, int, uuid) from anon;
```

### 5.6 Realtime チャンネルの制限

部屋のチャンネル `match:{match_id}` は private channel にし、参加者だけが受信できるよう `realtime.messages` に RLS を設定する。

注意: RLS ポリシーはログイン中のユーザーの権限で評価されるため、ポリシーから `game.match_players` を直接参照すると権限エラーになる。参加者かどうかを判定する `security definer` の補助関数を用意し、ポリシーからはそれを呼ぶ。補助関数は API に公開しないスキーマ（例: `private`）に置き、`authenticated` にはそのスキーマの usage と関数の execute だけを許可する。

```sql
create policy "match members receive"
on realtime.messages for select to authenticated
using (
  realtime.messages.extension in ('broadcast', 'presence')
  and private.is_match_member((select realtime.topic()))
);
-- Presence の送信用に、同じ条件で extension = 'presence' に限った INSERT ポリシーを作る
```

クライアント側:

```ts
await supabase.realtime.setAuth()
const ch = supabase.channel(`match:${matchId}`, { config: { private: true } })
  .on('broadcast', { event: 'answered' }, ({ payload }) => { /* 相手の回答済みを表示 */ })
  .on('presence', { event: 'leave' }, () => { /* 相手が切断 */ })
  .subscribe(async (s) => { if (s === 'SUBSCRIBED') await ch.track({ userId }) })
```

### 5.7 どの構成でも防ぎきれないもの

| 不正 | 対応 |
|---|---|
| 別の画面で検索する、他人に聞く | 制限時間を短くし、回答の速さもスコアに加えて影響を小さくする |
| Bot による自動回答 | 回答時間はすべて記録されるので、極端に速い人や正答率が不自然に高い人を後から検出し、ランク戦から外す |
| 回線速度の差 | 回答時刻はサーバーの受信時刻なので、回線が速い人がわずかに有利。「正解数で勝敗を決め、同点のときだけ時間を比べる」ルールにすると影響が小さくなる |

### 5.8 設定ミスを防ぐ確認

- Dashboard の **Security Advisor** を実行し、RLS が無効なテーブルや `search_path` 未指定の関数がないか確認する。
- 別アカウントのトークンで次の操作を `supabase-js` から実行し、すべて拒否されることを確認するスクリプトを用意する。RPC を変更するたびに実行する。
  - `game` スキーマのテーブルを直接読む
  - 他人の試合の `get_current_question` を呼ぶ
  - 出題時刻より前に問題を取得する
  - 締切を過ぎてから `submit_answer` を呼ぶ
  - 同じ問題に2回回答する
  - 他人の試合のチャンネルを購読する、クライアントから Broadcast を送る

## 6. マッチングとレーティング

### 6.1 マッチング方式

| 方式 | 内容 | 用途 |
|---|---|---|
| フレンド対戦 | 招待コード・リンクで部屋に入る | 最初に作る。レートは変動させない |
| ランダムマッチ | 待機列に入り、レートが近い相手と組む | レート戦 |
| ゴースト対戦 | 他の人の過去の回答記録と非同期で戦う | 同時にオンラインの人が少ないとき |

個人開発で一番の問題は、同時に待っている人が少ないこと。次の2つはほぼ必須になる。

- **待ち時間に応じて許容するレート差を広げる**（例: 最初は ±100、5秒ごとに ±50 広げる）
- **20〜30秒見つからなければゴースト対戦か Bot 対戦に切り替える**（回答記録は DB に残っているので、ゴースト対戦は作りやすい）

### 6.2 ランダムマッチの実装方針

`find_match()` RPC を1つ用意する。常駐サーバーは不要。

- 待機列（`game.match_queue`）から、許容レート差の範囲内で最も長く待っている相手を `for update skip locked` で1人確保する。同時に呼ばれても同じ相手を取り合わない。
- 見つかれば試合を作り、待っていた側には個人用の private channel `user:{user_id}` に `realtime.send()` で通知する（このチャンネルにも RLS が必要）。見つからなければ自分を待機列に入れる。
- クライアントは数秒おきに `find_match()` を呼び直す。これで待っている人同士も、広がったレート差の範囲で組める。
- 古いエントリは `enqueued_at` で除外・削除し、画面を閉じたときは `leave_queue()` で列から抜ける。

### 6.3 レーティング

最初は **Elo** を採用する。計算式が単純で SQL だけで書ける。精度を上げたくなったら Glicko-2 への移行を検討する（新規や久しぶりのプレイヤーの評価が早く落ち着く）。TrueSkill / OpenSkill は3人以上やチーム戦向けなので不要。

```
期待勝率 E_A = 1 / (1 + 10^((R_B - R_A) / 400))
新レート R_A' = R_A + K × (結果 - E_A)    結果: 勝ち=1、引き分け=0.5、負け=0
```

- 初期レート 1500、K は 32 程度。最初の10戦ほどは K を 40〜60 にして本来の実力に早く近づける。
- **レートの更新は、`advance` で試合を `finished` にするのと同じトランザクションで行う。** 状態が変わったときだけ更新するので、二重加算されない。
- **レートが変動するのはランダムマッチだけ。** フレンド対戦も対象にすると、サブアカウント相手にわざと負けてレートを稼げてしまう。
- 途中で切断したら負けとして扱う。
- 同じ相手と短時間に何度も当たった場合は、変動を減らすか変動させない。
- 表示は数値そのものより、ブロンズ・シルバーなどのランク帯にすると分かりやすい。

## 7. Supabase Realtime の制限と費用

| 項目 | Free | Pro |
|---|---|---|
| 同時接続数 | 200 | 500（支出上限を外すと 10,000） |
| メッセージ数 / 秒 | 100 | 500 |
| Presence メッセージ数 / 秒 | 20 | 50 |
| 月間メッセージ数 | 200万件（※） | 500万件（※） |

※ 月間メッセージ数は公式ページを直接確認できず、複数のブログ記事で確認した値。

- 1接続 = ブラウザ1タブ。1つのタブで複数のチャンネルを購読しても1接続。
- 全員が対戦中なら Free でも最大約100試合を同時に行える（待機中・ロビーの人も接続していれば数に入る）。
- 1試合（10問程度）のメッセージを数十〜100件と見積もると、月に数万試合まで Free に収まる計算。1件の配信を受信者ごとに数えるかどうかで実際の数は変わるので、運用開始後に Dashboard の Realtime Reports で確認する。
- 先に上限に達しやすいのは Presence の 20件/秒（多くの人が同時に入退室した場合）。
- 上限を超えると接続が切断される（`tenant_events` エラー）。supabase-js は流量が下がれば自動で再接続する。
- Realtime には対戦中とマッチング待ちの間だけ接続し、終わったら `supabase.removeChannel()` で切断する。
- Free プランのプロジェクトは、しばらく使われないと一時停止される。公開を続ける場合は注意。

個人開発の初期は Free で十分。同時プレイ人数が数百人規模になったら Pro（月額 $25〜）への移行を検討する。

## 8. 作る順番

### ステップ1: 招待リンクで2人が1試合を最後まで遊べる

ランダムマッチやレートは後回しにする。ただし不正対策の仕組み（`game` スキーマ、判定は RPC だけ、締切は `now()` で判定）は**最初から入れる**。後から入れると、クライアントが DB を直接読み書きするコードを書き直すことになる。

- **DB**: `game` スキーマと5テーブル（`matches`、`match_players`、`questions`、`question_answers`、`match_answers`）。問題は既存のものから10問程度コピーする。
- **RPC**（5つ）
  - `create_match()`: 部屋を作り、招待コードを返す
  - `join_match(code)`: 2人目として参加し、2人そろったら最初の出題時刻を決める
  - `get_current_question(match_id)`: 出題時刻を過ぎていれば、正解を含まない問題文と選択肢を返す
  - `submit_answer(match_id, q, choice_id)`: 締切と二重回答を確認して回答を記録する
  - `advance(match_id)`: 両者回答済みか締切後なら、次の問題に進むか試合を終了する
- **Realtime**: private channel `match:{id}` と RLS。`realtime.send()` で `started`、`answered`、`question_closed`、`finished` の4種類を通知する。
- **画面**: 部屋作成、参加、対戦、結果の4画面。タイマーは表示用だけ。

**完了の目安**

- 別アカウントの2つのブラウザで、10問の試合を最後まで遊べる
- 5.8 の確認スクリプトで、不正な操作がすべて拒否される

## 9. 未確認事項（実装前に公式ドキュメントで確認すること）

調査環境から supabase.com のドキュメントを直接取得できず、検索結果をもとにまとめた部分がある。

- `realtime.topic()` を使った `realtime.messages` の RLS ポリシーの正確な書き方
- `realtime.send()` の引数の順番と意味（本資料では `payload, event, topic, private` の順で記載）
- Realtime の月間メッセージ数の上限と、メッセージの数え方
- pg_cron の秒単位スケジュールの指定方法（後片付け用途なので1分間隔でも問題ない）

DO を将来再検討する場合の未確認事項:

- Free プランの1オブジェクトあたりのストレージ上限（資料によって 1GB と 10GB の記載がある。1試合のデータは数KB なので影響しない見込み）
- Worker で Supabase の JWT を検証する方法。JWKS（`/auth/v1/.well-known/jwks.json`）と `jose` ライブラリを使う一般的な手順は使えるはずだが、プロジェクトの鍵方式（非対称鍵か共有シークレットか）によって変わる
