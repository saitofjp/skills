# クイズアプリ リアルタイム対戦 調査まとめ

前提: React SPA / Supabase（DB・認証）/ Vercel（ホスティング）。2人が同じ問題を同時に解いて競う。最優先は不正対策（相手の答えが見える・タイマーをいじられる、を防ぐ）。

## 1. 結論

**Vercel と Supabase の2つだけで作る。** サービスは増やさない。

- 配信: Supabase Realtime（Broadcast と Presence、private channel）
- 判定: Postgres の RPC（`security definer set search_path = ''`）。正誤・締切・スコア・レートはすべてサーバー側で決める
- ゲームデータ: API に公開しない `game` スキーマに置く
- 後片付け: pg_cron（Supabase Cron）
- Vercel: 今まで通り SPA の配信だけ

## 2. 検討して見送った選択肢

| 選択肢 | 見送った理由 |
|---|---|
| Vercel Functions の WebSocket | 2026年6月に公開ベータになったばかり。接続は関数の最大実行時間で切れる（約5分で切れたという検証報告あり）。部屋への一斉配信や在席管理は自作 |
| WebRTC の P2P | Supabase 案も無料枠に収まるので節約にならない。シグナリングと TURN（従量課金）は結局必要。判定をクライアントで行うことになり、正解やスコアを守れない |
| Cloudflare Durable Objects | 対戦ルームには向いており、不正対策の強さも同じ水準。ただし管理するサービスが3つになるのを避けたいので見送り。下の工夫で Supabase でも同等にできる |
| Ably / Pusher | 今回の規模には過剰 |

Durable Objects の利点と、Supabase での代わり:

| DO の利点 | Supabase での代わり |
|---|---|
| 守るべきデータがクライアントから届かない場所にある | 非公開の `game` スキーマに置く |
| 処理が1つずつ順番に実行される | 各 RPC の最初で `select ... for update` により試合の行をロック |
| Alarm でサーバーが問題を進める | 締切は `now()` で判定。進行は誰が呼んでも安全な `advance` RPC と pg_cron |

Supabase 案で残る違い: ロジックは PL/pgSQL で書く。問題の切り替えは主にクライアントからの `advance` 呼び出しに頼る（不正には影響しないが、表示が少し遅れることはある）。

WebRTC は、将来ボイスチャットやビデオを付けるときに、通話部分だけに使う（シグナリングは Supabase Realtime）。

## 3. 不正対策

基本方針: **クライアントには今見えてよい情報だけを渡し、判定はすべてサーバーで行う。**

### 相手の答え・正解を見せない
- テーブルは `game` スキーマに置き、PostgREST から見えなくする。クライアントの入口は `public` の少数の RPC だけ
- `game` のテーブルは `supabase_realtime` publication に入れない（Postgres Changes で漏れない）
- Broadcast は RPC 内の `realtime.send()` からだけ送る。`realtime.messages` に broadcast の INSERT ポリシーは作らない（クライアントから送れるのは Presence のみ）
- 「回答した」通知には選んだ選択肢を含めない。正誤は締切後に両者へ返す
- 問題文は出題時刻を過ぎるまで返さない（`get_current_question` で判定）
- 選択肢はプレイヤーごとにシャッフルし、回答は選択肢 ID で受け取る（答えの教え合い対策）

### タイマーをいじらせない
- クライアントのタイマーは表示専用
- `q_started_at`・`q_deadline` は DB の `now()` 基準で保存。回答はこの範囲内のときだけ受け付ける
- 回答時間は `now() - q_started_at` でサーバーが計算
- `(match_id, user_id, q_index)` のユニーク制約で二重回答・回答変更を防ぐ
- `advance` は「両者回答済み」か「締切を過ぎた」ときだけ条件付き UPDATE で進む。早く呼んでも何も起きない

### 全体
- すべての RPC の最初で「`auth.uid()` がこの試合の参加者か」「今の状態でその操作をしてよいか」を確認
- `security definer` の関数には `set search_path = ''`、テーブルはスキーマ名付きで参照
- `revoke execute on function ... from anon`
- 確認方法: Dashboard の Security Advisor と、別アカウントで不正な操作を試すスクリプト（RPC を変えるたびに実行）

### 防ぎきれないもの
- 別画面での検索・他人に聞く → 制限時間を短くし、速さもスコアに入れる
- Bot による自動回答 → 記録した回答時間・正答率から事後に検出してランク戦から外す
- 回線速度の差 → 「正解数で勝敗、同点のときだけ時間で比べる」ルールで影響を小さくする

## 4. マッチングとレーティング

### マッチング
- フレンド対戦（招待コード・リンク）: 最初に作る。レートは変動させない
- ランダムマッチ: `find_match()` RPC と `match_queue` テーブル。`for update skip locked` で取り合いを防ぎ、待ち時間に応じて許容レート差を広げる（例: ±100 から5秒ごとに +50）。マッチ成立は個人チャンネル `user:{id}` に通知。古い待機エントリは除外・削除
- 人が少ないときの対策: 20〜30秒見つからなければゴースト対戦（過去の回答記録と非同期で戦う）か Bot 対戦

### レーティング
- 最初は Elo。初期 1500、K=32（最初の10戦ほどは 40〜60）
  - 期待勝率 `E_A = 1 / (1 + 10^((R_B - R_A) / 400))`
  - 新レート `R_A' = R_A + K × (結果 - E_A)`
- 必要になったら Glicko-2 へ移行
- 更新は `advance` で試合を `finished` にするのと同じトランザクションで行う（二重加算を防ぐ）
- レートが動くのはランダムマッチのみ。途中切断は負け扱い。同じ相手との連戦は変動を減らす
- 表示はランク帯（ブロンズ・シルバーなど）にすると分かりやすい

## 5. Supabase Realtime の無料枠

| 項目 | Free | Pro |
|---|---|---|
| 同時接続数 | 200 | 500（支出上限を外すと 10,000） |
| メッセージ数 / 秒 | 100 | 500 |
| Presence メッセージ数 / 秒 | 20 | 50 |
| 月間メッセージ数 | 200万件 | 500万件 |

- 1接続 = ブラウザ1タブ。全員対戦中なら最大約100試合を同時に行える（待機中・ロビーの接続も数に入る）
- 先に上限に達しやすいのは Presence の 20件/秒
- 月間メッセージ数は、1試合数十〜100件として月数万試合まで（実数は Realtime Reports で確認）
- 上限超過時は切断され、supabase-js が自動で再接続する
- Realtime には対戦中とマッチング待ちのときだけ接続し、終わったら `removeChannel()` する
- Free プランのプロジェクトは、しばらく使われないと一時停止される
- 同時プレイが数百人規模になったら Pro（月額 $25〜）へ

## 6. 作る順番

### ステップ1: 招待リンクで1試合を最後まで遊べる
不正対策の仕組み（`game` スキーマ、RPC だけで判定、`now()` で締切）は最初から入れる。

- テーブル: `game.matches` / `match_players` / `questions` / `question_answers` / `match_answers`（問題は既存から10問ほどコピー）
- RPC: `create_match()` / `join_match(code)` / `get_current_question(match_id)` / `submit_answer(match_id, q, choice_id)` / `advance(match_id)`
- Realtime: private channel `match:{id}`（参加者のみ受信できる RLS）。通知は `started` / `answered` / `question_closed` / `finished`
- 画面: 部屋作成、リンクで参加、対戦、結果

完了の目安:
- 別アカウントの2ブラウザで10問の試合を最後まで遊べる
- 確認スクリプトで次がすべて拒否される: `game` テーブルの直接 SELECT、他人の試合の `get_current_question`、締切後の `submit_answer`、同じ問題への2回目の回答、出題時刻前の問題取得

### その後
1. Presence で「相手が切断」を表示、pg_cron で放棄された試合を片付ける
2. ランダムマッチ（`find_match`）
3. Elo レート
4. ゴースト対戦
