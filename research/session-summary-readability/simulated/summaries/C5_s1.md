# リアルタイム対戦機能の調査まとめ

## 結論

**サーバーは増やさず、Vercel と Supabase だけで作ります。** 判定はすべて Supabase の RPC で行います。ユーザーが最も重視していた「相手の答えが見える」「タイマーをいじられる」という不正は、この構成で防げます。

- **Vercel**: これまで通り SPA の配信だけに使います。
- **Supabase Realtime**: Broadcast で試合の進行を通知し、Presence で相手の在席を確認します。
- **Postgres**: API に公開しない `game` スキーマにゲームのデータを置きます。クライアントが呼べるのは、`public` スキーマに置いた少数の RPC だけです。正誤、締切、スコア、レートはすべてここで計算します。
- **pg_cron**: 2人とも切断して止まった試合を片付けます。

## 検討して採用しなかった案

| 案 | 採用しなかった理由 |
|---|---|
| Vercel Functions の WebSocket | 2026年6月に公開ベータになったばかりです。約5分で切断されたという報告があり、部屋内への一斉配信も自分で作る必要があります。 |
| WebRTC（P2P） | 今の案も無料枠で動くので、節約できる費用がありません。接続には結局シグナリングと TURN サーバーが要ります。正誤の判定がクライアント側になるため、不正を防げません。通話を付けたくなったときに、通話部分だけ WebRTC にするのは可能です。 |
| Cloudflare Durable Objects | 1試合を1オブジェクトとして扱えて、処理が自動で1つずつ実行され、Alarm でサーバー側からタイマーを進められるので、対戦ルームには向いています。ただ、不正対策の強さは Supabase 案と同じです。ユーザーは管理するサービスを3つに増やしたくなかったので、見送りました。 |
| Ably / Pusher | 今回の規模には過剰です。 |

Durable Objects の利点は、Supabase の次の機能で代わりが用意できます。

| DO の利点 | Supabase での代わり |
|---|---|
| 守るべきデータがクライアントから届かない場所にある | 非公開の `game` スキーマに置く |
| 処理が1つずつ順番に実行される | 各 RPC の最初で `select ... for update` により試合の行をロックする |
| Alarm でサーバーがタイマーを進める | 締切は `now()` で判定し、進行は誰が何度呼んでも安全な `advance` と pg_cron で補う |

ただし、ロジックを PL/pgSQL で書くことになります。また、片方の通信が遅いと、画面が次の問題に切り替わるのが少し遅れる場合があります。

## 不正対策の要点

**相手の答えや正解が漏れないようにする**
- `game` スキーマを API に公開しません。テーブルの存在自体がクライアントから見えなくなります。
- 正解は別テーブル（`question_answers`）に分けます。
- 問題文は出題時刻を過ぎてから `get_current_question` で返します。正誤は締切を過ぎてから返します。
- 回答時の通知は「答えた」という事実だけにして、選んだ選択肢は含めません。
- 選択肢の並び順はプレイヤーごとにシャッフルし、回答は選択肢の ID で受け取ります。こうすると、外部で「Bだよ」と答えを教え合っても役に立ちません。
- Realtime の設定:
  - Broadcast は RPC 内の `realtime.send()` からだけ送ります。
  - クライアントから送れるのは Presence だけにします。
  - `game` スキーマのテーブルは publication に入れません。
  - チャンネルは private にし、RLS で参加者だけが受信できるようにします。

**タイマーをいじられないようにする**
- 出題時刻（`q_started_at`）と締切（`q_deadline`）は DB の `now()` で決めて保存します。
- 回答は、その間の時刻に届いたときだけ受け付けます。
- 回答にかかった時間もサーバーが計算します。クライアントのタイマーは表示専用です。
- 二重回答は `(match_id, user_id, q_index)` のユニーク制約で防ぎます。

**全体の決まり**
- RPC はすべて `security definer set search_path = ''` で定義します。
- どの RPC も最初に「呼び出したのが試合の参加者か」と「今の状態でその操作をしてよいか」を確かめます。
- 未ログインのユーザー（`anon`）からは実行権限を外します。

**完全には防げない不正**
- **検索や他人に聞く行為**: 制限時間を短くし、回答の速さもスコアに入れて影響を小さくします。
- **Bot による自動回答**: 回答時間の記録から後で検出して対応します。
- **回線速度による差**: 正解数で勝敗を決め、同点のときだけ回答時間を比べるルールにすると目立ちにくくなります。

## マッチングとレーティング

- **マッチング**
  - フレンド対戦（招待リンク）から作ります。
  - 次に、待機列と `find_match()` によるランダムマッチを作ります。`for update skip locked` を使い、同時に呼ばれても同じ相手を取り合わないようにします。
  - 待ち時間が長くなるほど、許容するレート差を広げます（例: ±100 から始めて、5秒ごとに +50）。
  - 一定時間（20〜30秒など）見つからなければ、過去の回答記録と戦うゴースト対戦に切り替えます。
- **レーティング**
  - Elo を使います。初期値は 1500、K は 32 で、最初の10戦ほどは 40〜60 に上げます。
  - 試合を終了させる処理と同じトランザクションの中で、サーバーが計算します。
  - レートが変動するのはランダムマッチだけにします（サブアカウントでわざと負けてレートを稼ぐのを防ぐため）。
  - 途中で切断したら負けとして扱います。
  - 画面にはレートの数値ではなく、ランク帯を表示します。

## 無料枠

| 項目 | Free | Pro |
|---|---|---|
| 同時接続数 | 200 | 500 |
| メッセージ数 / 秒 | 100 | 500 |
| Presence メッセージ数 / 秒 | 20 | 50 |
| 月間メッセージ数 | 200万件 | 500万件 |

- 同時に行える試合は約100です。待機中の人やロビーにいる人も、接続していれば数に入ります。
- 月間メッセージ数で見ると、月に数万試合までは収まる見込みです。
- Realtime には対戦中とマッチング待ちのときだけ接続し、終わったら `removeChannel()` で切断します。
- Free プランのプロジェクトは、しばらく使われないと一時停止されるので注意してください。

## 作る順番

**ステップ1: 招待リンクで2人が1試合（10問）を最後まで遊べるようにする**

ランダムマッチやレートは後回しにしますが、不正対策の仕組みは最初から入れます。後から入れると、クライアントが DB を直接読み書きするコードを書き直すことになるためです。

- **DB**: `game` スキーマに5テーブル（`matches`、`match_players`、`questions`、`question_answers`、`match_answers`）を作ります。問題は既存のものから10問ほどコピーします。
- **RPC**: `create_match`、`join_match`、`get_current_question`、`submit_answer`、`advance` の5つです。
- **Realtime**: private channel `match:{id}` で、`started`、`answered`、`question_closed`、`finished` を通知します。
- **画面**: 部屋を作る、参加する、対戦する、結果を見る、の4画面です。

**ステップ1の完了の目安**
- 別アカウントの2つのブラウザで、10問の試合を最後まで遊べること。
- 確認用スクリプトで、次の5つの操作がすべて拒否されること。
  - `game` スキーマのテーブルを直接 SELECT する
  - 他人の試合の問題を取得する
  - 締切を過ぎてから回答する
  - 同じ問題に2回回答する
  - 出題時刻より前に問題を取得する

**その後の順番**
1. Presence による切断表示と、pg_cron による後片付け
2. ランダムマッチ
3. Elo レート
4. ゴースト対戦
