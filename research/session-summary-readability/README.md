# AIの調査まとめが読みにくくなる理由

長い調査セッションの最後にAIへ「まとめて」と頼むと、調査中の分岐を流れのまま残した、読みにくい資料になりやすい。人なら主目的を決めて構成を組み直す。**この資料は、その差がどこから来るかを確かめ、どう頼めば防げるかを決めるためのものである。**

## 結論

1. **差の正体は、資料の読み手と目的が決まっているかどうかである。** 人は「誰が何を決めるための資料か」を先に決め、そこから構成を組む。AIは「まとめて」だけだと読み手も目的も与えられないので、**話した内容の目録**を作る。目録の見出しはユーザーが聞いたことの数だけでき、並びは話した順になる。
2. **最新のモデルは、頼めば組み直せるし、問題も自分で見つけられる。** 「主目的に沿って組み直して」の一言で、資料の冒頭に目的が書かれた割合は 0/6 から 6/6 に上がった。書いた本人に「見ていない同僚にとって読みやすいか」と聞くと、5点中3点を付け、「目的が冒頭にない」と正しく指摘した。足りないのは能力ではなく、書く前に読み手を決める工程と、書いた後に読み手として読み返す工程である。
3. **実際に読みにくくなった資料は、追記で育っていた。** 過去のセッションでいちばん典型的だったのは、Issue に調査結果を2回に分けて追記した資料だった。経緯順に並び、分量の55%が途中で退けた案に使われ、撤回されていない古い推奨が残っていた。初見の読者はそれを現行の推奨だと読んだ。

対策は「対策」の節にまとめた。読み手と、その人が決めることを書いて頼む。結論が変わったら追記せず書き直させる。書いた後に初見の読者として読み返させる。

## 仮説の判定

ユーザーの3つの仮説と、追加で立てた6つの仮説を、過去セッションと実験で確かめた。数値は「実験」の節による。

| # | 仮説 | 判定 | 根拠 |
|---|---|---|---|
| 1 | 「まとめて」だと愚直にまとめてしまう | **支持。最も効く** | 「主目的に沿って組み直して」と頼むだけで、目的の明示が 0/6→6/6、結論の初出位置が 12%→4%、初見読者の目的の理解が 1.3→2.0（2点満点）。組み直す力はあり、頼まれないと使わない |
| 2 | AIは分岐が残っていても自分は読めるので、組み直す必要を感じない | **半分支持** | 初見役のAIは、構成の良し悪しにかかわらず中身をほぼ同じだけ読み取れた。構成の悪さはAI自身にはコストにならない。一方、書いた本人に初見の同僚の立場で採点させると、問題を正しく指摘した。分からないのではなく、書くときにその点検をしない |
| 3 | セッションの流れに引きずられる（手抜き） | **単純な形では不支持** | 会話を順不同にして渡しても、出力は元の順に並べ直され、「調査の流れ」「途中で覆った判断」という節まで立った。会話を第三者の記録として渡すと、経緯への言及はむしろ増えた（3件→8〜11件）。流れは「どの結論が最新か」を決める足場として使われ、それが本文に漏れる |
| 4 | 資料を追記で育てる | **支持。実例で最も強い** | 実際の Issue スレッドは追記2本で経緯順、退けた案が分量の55%、撤回されていない推奨が残った。同じ時点で一から「まとめて」と頼むと、退けた案は24%に下がった |
| 5 | 目的が会話の中で言葉にならないまま、問いが移っていく | **支持（事例の比較のみ）** | 目的が最後まで言われなかったホスティング移行の調査が最も崩れた。最優先の要件が会話中で明言された模擬セッションは、「まとめて」だけでも結論が冒頭に来た。ただしその要件も冒頭の目的としては書かれず、2本のうち1本では初見の読者が見落とした |
| 6 | ユーザーの質問1つが見出し1つになる | **観察された** | 脇道だった質問（マッチングの方式、無料枠の上限）が、本筋と同じ高さの見出しで並ぶ。組み直した版でも、退けた案が分量の15〜20%を占める |
| 7 | 「読み手のため」を、説明を足すことだと解釈する | **支持** | 「見ていない人が読む資料として」と頼むと、長さが2倍（5.0k字→10.4k字）になり、経緯への言及も2倍以上になった。冒頭に目的が書かれたのは 3/5 にとどまった |
| 8 | 長いセッションでは、AI自身の記憶が時系列の要約に置き換わる | **仕組みは確認、効果は未検証** | Claude Code が会話を圧縮するときの指示は「各メッセージを時系列に分析する（Chronologically analyze each message）」で始まり、試した案・保留した案とその理由を「長くなっても」残すよう求めている。調べたセッションでは圧縮が起きていなかった |
| 9 | 人は忘れることで枝を落とす。AIは全部覚えている | **未検証** | 人は作業記憶が限られるので、時間がたつと要点だけが残る。AIは会話の全文を同じ鮮明さで持つ。今回の実験では測れていない |

### 人とAIの差をどう説明するか

書き方の研究では、この差は人とAIの差というより、熟練した書き手と初心者の差として知られている。Flower（1979）は、初心者の文章が自分の発見の順に沿って並ぶことを「書き手本位の文章（writer-based prose）」と呼んだ。Bereiter と Scardamalia（1987）は、知っていることを順に書き出す「知識の語り（knowledge telling）」と、読み手に向けた目標から内容を組み替える「知識の変形（knowledge transforming）」を分けた。

AIの「まとめて」は前者に当たる。熟練した人は頼まれなくても読み手を想定する。AIは頼まれたときだけそうする。仮説1・2・7の結果はこの見方と合う。

## 対策

効いた順に並べる。

1. **読み手と、その人が決めることを書いて頼む。** 「見ていない人向けに」だけだと説明が増えて長くなる。決めることまで書くと、目的と結論が冒頭に来る。

   ```
   このセッションを見ていない〇〇さんが、△△を決めるための資料にして。
   冒頭に目的と結論。退けた案は理由を1行ずつ付けて末尾に。
   経緯（いつ何が分かったか）は書かない。
   ```

2. **結論が変わったら、追記ではなく書き直しを頼む。** 「前のコメントに足すのではなく、全体を1本に書き直して差し替えて」と言う。追記は前の結論を残したまま差分だけを書くので、どれが現行の推奨かが読み手に分からなくなる。
3. **書いた後に、初見の読者として読み返させる。** 「このセッションを見ていない同僚として読んで、迷う箇所を直して」と頼む。書いた本人は問題を正しく見つけられた。
4. **長いセッションでは、途中で目的を言葉にしておく。** 「今の目的は〇〇を決めること」と一度書いておくと、まとめの軸になる。
5. **スキルにするなら、まとめる前に宣言を置く。** [aidoc-less-is-more](../../skills/aidoc-less-is-more/SKILL.md) のステップ1（読み手・目的・行動・結論を書き出して確認する）がそのまま使える。今回の結果は、このスキルが宣言を最初に置き、検証では捕まらない誤りとして扱っている理由を裏付けている。

## 根拠

### 過去のセッションの実例

直近のクラウドセッション約100件から、長い調査の後にまとめを作ったものを探し、4件を全文取り出した。

| セッション | 中身 | まとめの形 |
|---|---|---|
| **A. ホスティング移行の調査**（5往復、約1時間15分） | 「Vercel の関数を Supabase Edge Functions に移したら影響は」から始まり、「一部の関数だけ AWS に出せるか」「全部 AWS に移すならフロントはどう置くか」へ問いが移った。移行したい理由は最後まで言葉にならなかった | 調査結果を Issue に2回追記した。**典型例** |
| **B. スコア集計仕様の見直し**（21往復、約4.5時間） | 13往復かけて集計式を詰め、終盤で期間別ランキングの扱いが2回ひっくり返った | 文書の規約を確かめてから技術メモを書いた。結論→根拠の順で、読みやすかった |
| C. テスト結果の横断まとめ | 4本のテスト報告をまとめた。会話の分岐は少ない | 作業報告に「訂正が2つあります」の節が入った |
| D. 外部レポートの検証 | 1本の文書を検証した。調査の分岐は少ない | 該当しない |

Aの Issue スレッドの2本目は、「『og だけAWSに出す』を調べていて、それより大きい話が見えたので追記します」で始まる。1本目の結論（Supabase への部分移行ならこの順番で）は撤回されないまま残り、2本目で AWS と Cloudflare の案が加わった。下の表は、このスレッドと、同じ時点で一から頼み直した2つの版の大見出しを上から順に並べ、それぞれの役割を付けたものである。

| | 実物（Issue に2回追記） | C1「まとめて」 | C2「主目的に沿って組み直して」 |
|---:|---|---|---|
| 1 | 〔1本目〕前提の訂正 — 経緯 | 前提の訂正 — 経緯 | **結論 — 目的・結論** |
| 2 | 現状の棚卸し — 本筋 | 3つの選択肢の比較 — 本筋 | 前提の訂正 — 経緯 |
| 3 | issue本文の表の判定 — 退けた案 | Supabase 移行の難所 — 退けた案 | **判断軸 — 目的・結論** |
| 4 | 表に無い項目 — 退けた案 | og だけ AWS に出す案 — 退けた案 | 選択肢比較 — 本筋 |
| 5 | まとめ：判断材料 — 退けた案 | AWS 完結案 — 本筋 | Supabase 案（不採用理由）— 退けた案 |
| 6 | 未確認 — 未決 | その他の代替案 — 本筋 | 脱 Vercel の API 層 — 本筋 |
| 7 | 〔2本目〕なぜ og だけでなくフロントごとか — 経緯 | 未検証 — 未決 | AWS 完結案のフロント — 本筋 |
| 8 | フロントのホスティング — 本筋 | **推奨 — 目的・結論** | Cloudflare 案 — 本筋 |
| 9 | 失うもの — 本筋 | | **推奨する進め方 — 目的・結論** |
| 10 | 代替案 — 本筋 | | 要 PoC — 未決 |
| 11 | 未確認 — 未決 | | |

「まとめて」の版は、会話で出た順（Supabase → og だけ AWS → AWS 完結）に見出しが並び、推奨は最後の節にある。途中で退けた「og だけ AWS に出す案」も独立した節になっている。組み直した版は、結論と判断軸が冒頭に来て、退けた案は不採用理由の節に寄せられた。

### 実験

#### 方法

3つのセッションの「まとめる直前」までの会話を用意し、同じモデル（Claude Opus 5.5）に5つの条件でまとめを書かせた。

| セッション | 使った範囲 |
|---|---|
| A. ホスティング移行の調査（実セッション） | 最後の依頼「代替案系も含めて、書いてみて」の手前まで（3往復） |
| B. スコア集計仕様の見直し（実セッション） | 「整理して」と頼む手前まで（13往復） |
| S. 模擬セッション（[simulated/](simulated/)） | 8往復すべて。ユーザーの発言だけを台本にし、AIは実際に Web を検索して答えた |

模擬セッションの題材は、個人開発のクイズアプリにリアルタイム対戦を入れる方法である。退けられる案（WebRTC の P2P、Cloudflare Durable Objects）、脇道（マッチングの方式、無料枠の上限）、後から言われる最優先の要件（不正対策）、増やしたくないもの（サービスの数）を台本に仕込んだ。

| 条件 | 渡し方 | 最後の依頼 |
|---|---|---|
| C1 | 会話を履歴として再開する | ここまでの調査をまとめて |
| C2 | 同上 | ここまでの調査を、主目的に沿って構成を組み直してまとめて |
| C3 | 同上 | ここまでの調査を、このセッションを見ていない人が読む資料としてまとめて |
| C4 | 新しいセッションに会話の記録を文書として渡す | この調査をまとめて |
| C5 | C4 と同じだが、往復の順番を並べ替えて渡す | この調査をまとめて |

各条件を A と B で2回ずつ、S で1〜2回、計27本書かせた。評価は3つ。

- **初見の読者**: セッションを見ていないモデルが資料だけを読み、目的・結論・退けた案・次の行動を答え、読みやすさを5段階で付ける。
- **判定役**: 正解（目的・現時点の結論・退けた案）と元の会話を持つモデルが、構成と読者の答えを採点する。
- **書いた本人**: まとめを書いたセッションに続けて、「見ていない同僚にとって」の読みやすさを採点させる。

#### 結果

3つのセッションを合わせた条件ごとの平均である。

| 条件 | 本数 | 冒頭に目的 | 結論の初出位置 | 退けた案の分量 | 経緯への言及 | 初見読者の目的の理解（0〜2） | 長さ |
|---|---:|---:|---:|---:|---:|---:|---:|
| C1 まとめて | 6 | **0/6** | 12% | 16% | 3.0件 | 1.3 | 5.0k字 |
| C2 主目的に沿って組み直して | 6 | **6/6** | 4% | 16% | 3.7件 | **2.0** | 8.1k字 |
| C3 見ていない人向けに | 5 | 3/5 | 5% | 19% | 7.2件 | 1.8 | **10.4k字** |
| C4 記録を文書として渡す | 5 | 1/5 | 6% | 20% | 8.0件 | 1.6 | 4.6k字 |
| C5 C4 の順番を並べ替え | 5 | 1/5 | 11% | 20% | **11.2件** | 1.6 | 4.2k字 |
| 実物（A の Issue スレッド） | 1 | あり | 28% | **55%** | 9件 | 2.0 | 19.2k字 |
| 実物（B の技術メモ） | 1 | あり | 8% | 8% | 6件 | 1.0 | 7.1k字 |

書いた本人の自己採点は、どの条件でも平均 3.0〜3.4 だった。初見の読者の採点（3.4〜4.0）より低い。自分の資料を甘く見る傾向は見られなかった。

セッションごとに見ると、崩れ方はセッションで大きく違った。

- **A（目的が言葉にならないまま問いが移った）** では、C1 の2本とも冒頭に目的がなく、結論の初出は平均18%、退けた案が24%を占めた。
- **B と S（会話の中で方針や最優先の要件がはっきりした）** では、C1 でも退けた案は B で15%、S で10% にとどまり、B の2本はどちらも結論→根拠の並びだった。それでも冒頭に目的を書いた版は無かった。S の C1 の1本では、初見の読者が「不正対策が最優先」「サービスを増やさない」という二つの前提を答えられなかった。

### 文献と仕組み

- Flower, L. (1979). Writer-Based Prose: A Cognitive Basis for Problems in Writing. *College English*, 41(1), 19–37. 初心者の文章が自分の発見の順に並ぶことを示した。
- Bereiter, C., & Scardamalia, M. (1987). *The Psychology of Written Composition*. 「知識の語り」と「知識の変形」を分けた。
- Liu, N. F. et al. (2024). [Lost in the Middle: How Language Models Use Long Contexts](https://arxiv.org/abs/2307.03172). *TACL* 12. 長い入力の中ほどにある情報ほど使われにくい。
- Wan, D. et al. (2025). [On Positional Bias of Faithfulness for Long-form Summarization](https://aclanthology.org/2025.naacl-long.442). *NAACL*. 要約は入力の冒頭と末尾に忠実で、中ほどを落としやすい。
- Singhal, P. et al. (2023). [A Long Way to Go: Investigating Length Correlations in RLHF](https://arxiv.org/abs/2310.03716). 人の好みで学習した報酬は、長い応答を高く評価しやすい。仮説7の背景として挙げる。
- Panickssery, A. et al. (2024). [LLM Evaluators Recognize and Favor Their Own Generations](https://arxiv.org/abs/2404.13076). *NeurIPS*. モデルは自分の出力を高く評価しやすい。今回の自己採点では、この傾向は見られなかった。
- Claude Code の会話圧縮の指示（CLI 2.1.302 に含まれる文面）。"Chronologically analyze each message and section of the conversation" で始まり、"any possibilities, options, or approaches that were raised, tried, or set aside, and why" を "even at the cost of length" で残すよう求めている。作業を続けるための要約としては正しい設計だが、そのまま人向けの資料の下敷きにすると経緯順になる。

## この調査の限界

- 本数が少ない（3セッション、各条件1〜2本）。差は方向として読み、細かい数値の差は読まない。
- 初見の読者も判定役もAI（Claude Opus 5.5）である。AIの読者は構成が悪くても中身を読み取れるので、人が感じる読みにくさを小さく見積もっている可能性が高い。A の10本は Haiku 5.5 にも読ませたが、どれにも3点を付け、差が出なかった。
- 再開したセッションには、ユーザーの発言とAIの本文だけを入れ、ツールの実行結果は入れていない。実際のセッションのAIは、検索結果やコードの中身も覚えている。
- 正解（目的・結論・退けた案）は、この調査で会話を読んで決めたものである。
- モデルは Claude Opus 5.5 だけを使った。ユーザーが感じている読みにくさには、内部用語の未定義や情報の密度も含まれているはずだが、今回は構成だけを測った。初見の読者は、ほぼすべての資料で未定義の用語を迷う箇所に挙げていた。

## 再現する

[harness/](harness/) に、実験に使ったスクリプトと評価の指示文を置いた。標準ライブラリと `claude` CLI だけで動く。

1. クラウドのセッションを `list_events` で取り出し、[session_transcript.py](../../skills/semantic-structure/scripts/session_transcript.py) の `collect` で `work/sessions/<名前>/records.jsonl` を作る。
2. 正解を `work/gt_<名前>.md` に書く（[simulated/answer-key.md](simulated/answer-key.md) が例）。
3. 条件ごとにまとめを書かせる: `harness/run_condition.sh <名前> <まとめる直前の往復番号> C1 1`
4. 評価する: `harness/eval_summary.sh work/runs/<名前>_C1_s1 <名前> <往復番号>`
5. 集計する: `harness/aggregate.py work`

[results.tsv](results.tsv) は全29本（27本と実物2本）の評価値である。セッション名は A・B・S に置き換えた。実セッションの会話とまとめの本文は、本番の数値や非公開の設計を含むので入れていない。模擬セッションは会話と7本のまとめを [simulated/](simulated/) に入れた。

1回の実験は使用量が大きい。今回は27本の生成と約100回の評価で、5時間あたりの使用上限に一度達した。
